**技术决策**
- 前端 React 18 + TS + Vite + AntD + Recharts；后端 FastAPI + SQLAlchemy 2（同步 Session + yield 依赖）；
  PostgreSQL 16（全文 + JSONB 属性）、Milvus（语义，tenant_id 为 partition key）、
  Redis（缓存/限流/Celery broker+result/进度 pub-sub）、Celery、MinIO、nginx。
- 用户指定的「deepseek v4.1 flash」对应官方 model id `deepseek-flash`；
  **DeepSeek API 无 /embeddings**，因此 LLM 与 Embedding 拆成两个 Provider：
  生成走外部 DeepSeek（可 SSE 流式），向量走可配置的 OpenAI 兼容外部服务；
  默认 `stub` 为确定性特征哈希伪向量，仅用于无密钥跑通链路。
- Celery broker 用 Redis（按用户要求）而非设计文档的 RabbitMQ，用 acks_late +
  reject_on_worker_lost + visibility_timeout + PG 任务台账 + beat 心跳捞回补可靠性。
- 解析用 pypdf + 规则语义分块，但固定了 page_no/section_path/block_type/source_level 契约，
  换 MinerU 不动下游；Agent 编排用线性 NodeRegistry + ToolRegistry，预留 LangGraph 替换点。

**重点模块：大文件与批量上传**
分片 8MiB 断点续传 → MinIO compose 服务端合并 → 流式 SHA256（大文件用 `skip:` 前缀让服务端算权威校验和）
→ 秒传 → Celery chain/chord（>100MB 且 >200 页按页级 chord 并行，heavy 队列）
→ 进度四层模型 batch(体积加权)/file/stage(权重)/unit
→ PG 真值 + Redis pub/sub 实时 + SSE（快照 + Last-Event-ID + 心跳 + 轮询降级）
→ 幂等 chunk_id=uuid5、软删三方联动、每日差集对账。

## 按 TokenPlan 限速文档改造限流处理
- 上游口径：RPM 50（生成模型）/ TPM 2,000,000 / 5h·7d 墨点额度，同用户全部 key 合并计算。
- **关键：两种 429 必须分开**
  - `rate_limit_exceeded`（Anthropic 侧 `rate_limit_error`）→ 可退避重试；
  - `quota_exceeded`（墨点不足）→ **不能自动重试**，否则只是白烧时间。
  - 原实现把两者一视同仁、固定退避 3/6/9s、无抖动，属真缺陷。
- 改法：`providers.classify_429()` 细分；`providers.backoff_seconds()` 改成 1/2/4s + 抖动
  （尊重 `Retry-After`，上限 30s）；quota 直接抛 `quota_exceeded`；
  `rag.stream_answer` 把它映射成 `degrade_reason=quota_exceeded` + 专用兜底文案；
  前端加对应提示（建议换模型/换供应商）。
- 两条硬约束写进注释与文档：**流式一旦开始吐字不重试**（避免重复内容）；
  **抖动防惊群**（限流恢复瞬间多请求同时打）。
- 新增 5 条 pytest（classify quota/rate、backoff 含 Retry-After 与抖动、quota 快速失败不 sleep、
  rate 重试 3 次、rag 映射 quota reason）→ **36/36**。
- 边界诚实说明（已写 README）：切片是单进程，**没做全局并发闸/令牌桶**，
  只做单次请求的退避与不重试判断；生产应在网关层按 RPM 限流 + Celery 排队。
- 回归：pytest 36/36、e2e 33/33（15s，minimax-m3 快）、demo 16/16、eval 14。
