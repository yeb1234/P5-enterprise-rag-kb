## v1.2.0 · 公开检索基准 publicbench（CmedqaRetrieval）

**为什么加**：自建 9 题评估只能回答「管道通不通」，回答不了「检索算法选得对不对」。
后者需要公认数据集 + 同数据基线 + 调参/测试切分。

**数据**：CmedqaRetrieval（C-MTEB/MTEB）100001 passage / 3999 query / 7449 qrels，
从 `hf-mirror.com` 下 3 个 parquet；按 query-id 哈希切 2429 调参 / 1570 测试。

**测试集 nDCG@10**：BM25 16.29% → 向量 bge-m3 **33.93%**（+17.63 点）；
向量+前缀 31.05%、加权融合 w=0.85 31.98%——都比纯向量差。
重排接纯向量候选（同 400 条子集）：32.79% → top20 **36.09%**、top50 36.02%（差 0.06 点=噪声）。

**三个参数怎么收敛的（结论都不好看）**
1. BM25 词项预算 12→30→100：nDCG 11.13→14.95→**15.18%**。原来只取 12 项，等于自己把基线砍弱 4 个点——
   基线弱一点，向量增益就好看一点，那是自欺。
2. 融合权重 0.5→0.7→0.85：24.73→28.28→30.46%，单调升，终点还是纯向量。
   → **BM25 在这份数据上只贡献噪声，正确做法是不融合**，而不是把权重调小意思一下。
3. 重排深度 top20 与 top50 只差 0.06 点 → 说法是「并列，按成本取浅的」，不是「调出最优深度」。

**四个工程坑**
- 10 万×1024 Python float 要 3GB+ → 预分配 float32；
- 倒排项 1800 万条，`list[tuple]` 超 1GB → `array('i')` 平铺 `[idx,tf,…]` 降到 120MB；
- 429 是窗口限速，重试 4 次跨不过去 → 单独给 13 次、封顶 30s；4 路并发只快 1.4 倍却把重试打满 → 用 2 路；
- **`_pick_terms` 用 `set()` + 只按 df 排序**：Python 字符串哈希种子随机 →
  同一份数据两次跑出 0.1098 / 0.1105。改成 (df, 词项) 全序。
  第一版回归用例「两个种子跑一遍比结果」是假绿（旧代码照样通过），改成断言「等于按全序取前 N 项」才真能抓住。

**口径**：绝对值与 C-MTEB 榜不可比（第三方 API 嵌入、重排只对候选 top-k、无官方清洗），只讲相对差异。
「本轮耗时 83s」是缓存命中时间，冷跑约 75 分钟（向量化 60min）——报告里已写清，避免面试被追问时露怯。

**顺带**：`.env` 换成新的硅基流动 key（用户提供，嵌入与重排共用），
暴露了 `test_settings` 两个用例的隔离缺口（只 patch RERANK_API_KEY，会带走真值）→ 补 `delenv` + 新增优先级用例。

回归 255 passed + demo 16/16，冻结区零 diff；tag `v1.2.0` 已推 origin。
