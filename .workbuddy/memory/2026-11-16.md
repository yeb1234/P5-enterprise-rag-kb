**为什么加**：自建 9 题评估只能回答「管道通不通」，回答不了「检索算法选得对不对」。

**测试集 nDCG@10**：BM25 16.29% → 向量 bge-m3 **33.93%**（+17.63 点）；

重排接纯向量候选（同 400 条子集）：32.79% → top20 **36.09%**、top50 36.02%（差 0.06 点=噪声）。

**三个参数怎么收敛的（结论都不好看）**
1. BM25 词项预算 12→30→100：nDCG 11.13→14.95→**15.18%**。原来只取 12 项，等于自己把基线砍弱 4 个点——
   基线弱一点，向量增益就好看一点，那是自欺。
2. 融合权重 0.5→0.7→0.85：24.73→28.28→30.46%，单调升，终点还是纯向量。
   → **BM25 在这份数据上只贡献噪声，正确做法是不融合**，而不是把权重调小意思一下。
3. 重排深度 top20 与 top50 只差 0.06 点 → 说法是「并列，按成本取浅的」，不是「调出最优深度」。

**四个工程坑**
- 10 万×1024 Python float 要 3GB+ → 预分配 float32；
- 倒排项 1800 万条，`list[tuple]` 超 1GB → `array('i')` 平铺 `[idx,tf,…]` 降到 120MB；

  同一份数据两次跑出 0.1098 / 0.1105。改成 (df, 词项) 全序。
  第一版回归用例「两个种子跑一遍比结果」是假绿（旧代码照样通过），改成断言「等于按全序取前 N 项」才真能抓住。

## 深夜收尾②：三阶段延迟探针 → v1.2.1

**1. 为什么要加探针**
报告里重排耗时一直显示 `0.0s`——因为 `RerankCache` 全命中，`time.time()` 差值为 0。
**缓存命中记成 0 会让「重排免费」这种假结论进报告**，而重排恰恰是唯一数量级明显贵的环节。
所以在扫参之后独立加一段现场真调 API 的探针（`--latency-probes`，默认 20 次）。

**2. 实测（本机单线程，每条 query）**
BM25 **110.31 ms** · 向量 **2.57 ms**（批量 GEMM 摊薄；单条单独算 12.6 ms）· 重排 **357.37 ms**（1 次 HTTP 含网络往返）。
**反直觉结论：词法基线比向量检索慢 40 倍。** BM25 在 Python 里扫倒排项逐个累加分数，向量检索是一次 BLAS 矩阵乘。
所以「用词法兜底更省资源」这句话在 10 万文档规模上**不成立——既更不准，又更慢**。
小语料上确实反过来，分水岭是「语料能否常驻内存」。

## 追加：向量存储选型沉淀（`production/08-vector-store-decision.md`）

**先纠正的事实**：现在既不是 pgvector 也不是 Milvus，是「PG 文本列里存 JSON + Python 逐个算余弦」，
无 ANN 索引。`rag.py` 路径：`_load_ready_chunks()` 全表取文本 → 词法/权限缩候选 →
按 `chunk_id IN (...)` 取 `vec` 文本 → `_cosine()` 纯 Python 循环。Milvus 里 83 条（`kb_chunks`）没进主链路。

**三个实测常数（本机，可复跑）**
- 单条向量文本 **22,739 字符 ≈ 22.2 KB**（`vector(1024)` 二进制只要 4 KB，**文本胖 5.5×**）
- `json.loads` **0.19 ms**/条；纯 Python cosine(1024) **0.071 ms**/对
- 外推：1 万候选 2.6 s、10 万候选 **25.6 s**；而同一份 10 万数据 numpy 批量 GEMM 是 **2.57 ms** → **差 1 万倍**
- 差的是「JSON 文本 + Python 循环」，不是算法

**选型判据（不是 QPS）**：① 过滤与排序能否在一次查询里完成（权限可见集 `ANY($2)`）；
② 向量与业务数据是否共享事务边界（幽灵向量是已经交过的学费）；③ 运维新增组件数（Milvus = etcd+MinIO+milvus 三件套）。
规模算术：1024 维 × 100 万 = 4.1GB，HNSW 再 ×1.3；1000 万才轮到独立向量库。

**推荐**：走 pgvector（半天，改一条 SQL + 一列 + 一个索引），Milvus 降为备选并保留「为什么不用」的证据。
**未执行**：换镜像（现在是 PG 16.16 Alpine，`pg_available_extensions` 里没有 `vector`；
`pgvector/pgvector:pg16` 要走 dump/restore，别直接换镜像赌数据目录兼容）、`hnsw.ef_search` 调参、删 `vec` 列。
**#1 目标已在清单里改成「待定」**，拍板后再同步。

提交见下一次；CHANGELOG 也加了「2026-11-16 追加 · 向量存储选型」一节。

## v1.3.0：向量层切 pgvector（主链路改动）

**决策**：用户原话「彻底清理掉 Milvus，只用 PGVector，换镜像」，同时又担心「以后没机会练 Milvus」。
处理方式不是二选一，而是**分层**：主链路切 pgvector；Milvus 三件套移进 `profiles:["milvus"]`，
默认 `up` 不再启动，需要对照实验时 `--profile milvus up -d`。学习价值保留在「可选对照」里，
复杂度从主链路里拿掉。默认服务数 5 → 2（postgres + redis）。

**镜像路线（先踩空一次）**：`postgres:16-alpine` 源里确实有 `postgresql-pgvector-0.8.1-r0`，
但官方 postgres 镜像的 PG 是**源码编译在 `/usr/local`**，apk 包把扩展装到 `/usr/share/postgresql18/`
（顺手拉了 PG18 当依赖）→ 装完是「PG18 的扩展 + PG16 的服务端」，`CREATE EXTENSION` 照样失败。
**结论：官方 postgres 镜像加扩展只能换镜像，不能靠 apk。** 最终用 `pgvector/pgvector:pg16`（同为 16.16），
dump/restore 迁到新卷 `kb-infra_pgdata_v2`，旧卷 `kb-infra_pgdata` 保留为回滚快照。

**第二个坑**：扩展是**库级**的，装不进业务 schema。测试 schema `SET search_path TO "kb_test_x"` 之后，
DDL 在 `embedding vector(1024)` 报 `type vector does not exist`，SQL 里 `a <=> b` 报
`operator does not exist: vector <=> vector`。先试 `public.vector` 能过类型关但过不了操作符关 →
最终改 `SET search_path TO "<schema>", public`（`pgkit.connect` 与 `cache/tests/conftest.py` 两处）。

**实测**（143 候选、1024 维、同一 query）：
- 旧路径：取 JSON 56.98ms + 纯 Python 余弦 12.47ms = **69.45ms**
- 新路径：pgvector 一条 SQL（复用连接，10 次）**median 2.18ms**（min 1.73 / max 3.92）
- **约 32×**。但要说准：143 行时 planner 仍走 Seq Scan + Sort，**这 32 倍不是 HNSW 的功劳**，
  是「计算搬进 PG + 二进制列（4KB vs 22.2KB）」的功劳。
- 回填 174 条 + 建 HNSW 索引共 **0.39 秒**；`CREATE EXTENSION` 装到 0.8.7。

**A13 对拍**：分数最大差 **8e-08**、top-10 集合重合 **10/10**、top-4 **3/4**、顺序**不完全一致**。

## v1.3.1 · 连接层接入 SQLAlchemy Engine（池化）

起因：「SQLAlchemy 没用的话记得给系统用上」。核查：`backend/` 有 SQLAlchemy 2.0 + Alembic（真 ORM），
`webapp/` 连工程都没装。结论是**接池不接 ORM**——138 处调用点是按 SQL 文本写的，
改 ORM 是重写而不是接入。

**改法**：`connect()` → `engine.raw_connection()`；`PgConn.close()` → `fairy.close()`（还池）。
全仓 138 处 `finally: conn.close()` 零改动就从「每次重连」变成「归还」。

**实测（143 候选 pgvector SQL，15 次中位）**
- 改前直连 **18.59ms** → 改后 **3.77ms**（约 4.9×）
- `connect()+close()` 从「新建 TCP + PG 后端认证」→ **0.42ms**
- **口径纪律**：v1.3.0 的 2.18ms 是「只算 SQL」，3.77ms 是「端到端含取连接」。
  69.45 → 3.77 真实倍数约 **18×**，说成 32× 不准确。32× 是「算得少」，18× 是「连得省」。

**池化引入的一个真实新风险（已实测、已修）**
没有池时每次 `connect()` 都是新会话，任何会话级 `SET` 随连接消失；有池之后会话状态跨借用人存活：
`connect(autocommit=True)` → `SET search_path TO pg_catalog` → `close()`，下一个借用人
`SHOW search_path` 拿到 `pg_catalog`。`connect_args={"options": ...}` **管不住**（只在建连时生效）。
修法：`WEBAPP_DB_SCHEMA` 存在时在 checkout 再补一条 `SET` 复核，代价 1.4ms/次（两次往返），
**只在 schema 隔离场景付这个钱，生产零开销**。双向对拍：有复核 `public,public` / 绕过 `pg_catalog`。

**踩坑**：`create_engine("postgresql://...")` → `ModuleNotFoundError: psycopg2`（默认方言），
必须 `postgresql+psycopg://`。另：`test_connect_close_reuses_same_backend_connection` 单跑绿、
全量红——池里有多条连接，不该断言「连续两次同 pid」，改为「借还 N 次的不同后端数 ≤ 池上限」。

**新增 5 项池化单测**（`webapp/tests/test_pgkit_pool.py`）：池化是不可见行为，功能测试全绿
证明不了池在复用，所以直接查 `pg_backend_pid()`。单测 259 → **264**。

**回归**：264 passed、backend 26、eval+evalbench 30、demo 16/16、e2e 33/33 DEMO_READY、
`verify_infra` INFRA_READY、冻结区零 diff。容器内 `sqlalchemy 2.0.57`，两次取连接同一 pid。
提交 `4415754`（代码）/ `35443be`（文档），tag `v1.3.1`，已推 origin。

**文档同步修正**（v1.3.0 之后没跟着改的过期描述）：07 §0「向量召回仍读 PG 文本列」、
§11.3 面试口径按文本列写、§6.5.2 坑二把 search_path 写死为 SET——都已改。
07 #4 连接池标为已完成，闭环 3 → 4 项、未做 17 → 16 项、§11 分档 18 → 16 项。

**仍未定**：演示容器 `kb-webapp` 检索实际走词法（`settings.get_all()` 以 DB `app_settings`
为准，`-e WEBAPP_EMBEDDING_PROVIDER=offline` 只改 DEFAULTS，容器又没 key → 401 降级）。

## v1.3.2 · 运行日志：stdout JSON + 每请求 trace_id + 容器日志上限

起因：「上线的项目得做日志管理系统吧」。判断是**缺的不是采集平台，是日志基本卫生**。

**动手前核到的三个洞（都有证据）**
1. **容器日志无上限**：`docker-compose.yml` 有 `x-logging` 锚点（10m×3），但 `run-demo.sh`
   走 `docker run`，`docker inspect` 的 `LogConfig.Config` 是**空**的 → json-file 默认无限。
   这是「上线第一天写满磁盘」那条。
2. **用户原文进日志**：`/api/search/preview` 是 GET（`routers_ops.py:89`），uvicorn 默认
   访问日志打印**完整 URL** → 搜索词明文落盘。审计表存原文是设计，访问日志留痕是泄漏。
3. **成功请求没有 trace_id**：原来只在错误分支 `uuid4()`；且 `_gateway_error` 自己生成，
   与中间件不同源 → 「有 id 但串不起来」，比没有更难查。
   顺带：健康检查 `GET /` 每 30 秒一行，一天 2880 行噪声。

**改法**
- 新 `webapp/logging_setup.py`：`JsonFormatter`（ts/level/logger/msg/trace_id + 白名单扩展）、
  `configure_logging()`（清掉 uvicorn handler 统一走 JSON）、`safe_trace_id()`
  （只收 8–32 位 hex，防日志注入）、`ensure_trace_id()`。
- `main.py` 新增 `access_log` 中间件（**最外层**，后注册的在外）：定 id → ContextVar →
  响应头 → 一行 JSON；`path` 只取 `url.path`，**不含 query**；静默路径 <400 降 DEBUG。
- `_gateway_error` / 429 契约改用 `ensure_trace_id()`。
- `run-demo.sh` 补 `--log-opt max-size=10m --log-opt max-file=3`。
- `version` 1.3.0 → 1.3.2（1.3.1 漏同步 version 字符串，一并补）。

**实测**：响应头 `x-trace-id` 与日志 `trace_id` 同值；健康检查 2880 行/天 → **0**；
`LogConfig` `json-file map[]` → `local map[max-file:3 max-size:10m]`；日志是单行 JSON。

**7 项契约单测**（`webapp/tests/test_logging.py`）：404 也带 id / 合法 id 沿用 / 非法 id 替换 /
query 不进日志 / **错误体+响应头+日志三者同 id** / 静默路径 / JSON 单行固定字段。
单测 264 → **271**。conftest 加 `WEBAPP_LOG_LEVEL=WARNING` 防刷屏。

**坑**：`trace_id` 不在 `LogRecord` 上，是 formatter 从 ContextVar 注入的 →
测试必须断言**格式化后的输出**，用裸 record 断言会 `AttributeError`。

**明确没做**：集中采集（Loki/CLS）、日志留存与合规轮转、`user_id` 归因
（中间件在鉴权前执行拿不到用户）、span 采集。`latency_ms` 只到响应头返回，不含流式总时长。
另：`04-monitoring.md` 原文写的 `TraceIdMiddleware` **这个类从来不存在**，是编制时设想，已删。

提交 `3c5f86e`（代码）/ `e90ff8a`（文档），tag `v1.3.2`，已推 origin。
