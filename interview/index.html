04 / Architecture

分 layer 看：哪些真跑，哪些是替身

同一个项目里并存四种不同完成度的东西，面试时最容易讲混，所以显式分层。

backend/ 生产骨架

06 / Interview Q&A

面试常问，逐条给答法

点击展开。每条都留了「能讲」与「不能讲」的边界，避免把设计说成落地。

为什么这个项目不做多租户？

能讲：定位是单组织内部知识库，边界应该是「部门树」而不是「租户」；引入租户会同时带来隔离、计费、配额、迁移四组约束，超出「把 RAG 链路讲通」的目标。当前 backend 已有 Department（物化路径 path）、User.department_id、ACLGrant 与 decide()，webapp 本轮把成本 / 限流的统计维度从 tenant 对齐为 department。

不能讲：不说「已实现多租户隔离」，也不说「已实现完整多部门权限」。backend 的 tenant_id / TenantRepository 是历史命名技术债，webapp 演示切片没有部门表、没有行级 ACL。完整 13 步清理方案已写好但代码尚未改造。

去掉 tenant 之后，隔离强度是不是下降了？怎么解释？

能讲：主动承认下降，并给正确因果。is_partition_key=True 本来只是按值散列到固定 32 个分区的查询路由 / 性能机制，从来不是「一租户一分区」的硬隔离；原隔离落在 build_permission_expr() 里显式写死的 tenant_id == "..." 应用层表达式。真实变化是 expr 首条件从「静态、互斥、全库唯一的 tenant_id」变成「动态、层级、由部门拓扑算出的 id 列表」——候选集成了超集，算错或算空的影响面从跨组织扩大到跨部门乃至全库。

所以怎么补：权限判定收敛到 decide() 唯一权威、列表侧逐条复核、检索侧 filter_candidates() 二次校验，并用「列表与检索的一致性对拍」证明没漏。不能讲「只是换个字段名，隔离没变」。

429 限流怎么处理？两类有什么区别？

能讲：rate_limit_exceeded（频率超限）走 1/2/4s 指数退避 + 抖动，尊重 Retry-After（上限 30s，最多 3 次）；quota_exceeded（额度 / 墨点耗尽）不重试，直接提示换模型或供应商。流式一旦开始吐字就不再重试，避免重复内容。前端本轮也补齐了区分两类、展示业务错误码与等待秒数。

边界：限流是进程内滑动窗口，单实例有效；生产要换 Redis 令牌桶 + 网关层 + 全局并发闸，当前没有做压测与 RPM/TPM 全局闸。

为什么向量缓存的 key 一定要带模型名？

能讲：向量按 (chunk_id, model) 缓存在 chunk_embeddings。切模型后若沿用同一个 model 字符串，就会复用旧模型向量；维度不一致时 _cosine 会静默返回 0——检索看起来正常运行，实际全错，属于最难发现的假阴性。所以 settings.effective_embedding() 是端点 / 模型 / key / 缓存命名空间的唯一事实源，cache_key 含 provider + 模型名，并有单测锁定。

先按权限过滤还是先检索？为什么？

能讲：先过滤、再重排、再进模型。把越权内容送进上下文，即使最后不展示，也已经泄漏给模型并可能出现在输出里；而且重排与生成的算力会浪费在无权文档上。生产骨架用 Milvus expr 先缩候选，再用 filter_candidates() 逐条 decide() 二次校验（因为 expr 里的标量有限，需要从 PG 回查 owner_id / visibility / acl）。列表接口也必须逐条复核，分页在过滤之后。

不能讲：webapp 演示切片目前只有 admin 门禁 + owner 过滤，没有接入 decide()；这部分是 backend 已实现、演示切片未实现。

怎么证明答案不是模型编的？

能讲：三层。① 提示词要求只依据参考片段、无答案时明确说「知识库中未找到相关内容」；② chat_sources 把回答关联到 citation → chunk → 原文，SSE 的 meta / done 事件带 sources，前端来源卡片可点开原文；③ 检索为空时主动拒答并标 retrieval_empty，不拼接兜底文案。

边界：目前只到分块级引用，逐句 grounding 高亮与自动事实核验没做。评估里的拒答判定也是规则级组合判定，不是模型级事实验证。

大文件 / 批量上传怎么保证进度不丢？

能讲：上传入异步队列（生产是 Celery 双队列 + RabbitMQ/Redis 分层，演示切片是进程内队列），SSE 回推进度与繁忙队列位置；PG 是状态真值、Redis 只是实时通道，Redis 失效可以从 PG 重建快照；删除走软删 + 异步清理 + 每日对账；对象 key 与进度 key 分治，进度 key 不含身份、按全局 batch_id 分片，所以转岗后 SSE 重连也能命中。

V4.1 Flash 是推理模型，为什么默认关掉思考？

能讲：检索问答要的是首 token 延迟，不是长链推理。V4 系列默认先吐 reasoning，实测冷启动 + reasoning 会让端到端到 59.7s；max_tokens 给小还会把预算全花在思考上、正文为空。所以默认注入 thinking={"type":"disabled"}（沿用 backend 骨架同名字段），并保留「完整推理」档可切；零正文、已出正文后中断、内联 <think> 各有独立降级标记。

必须诚实：Discovery 网关是否识别该字段尚未实测。代码只报告「请求里带了什么」和「usage 里有没有观察到 reasoning_tokens」，不宣称已确认生效；不识别时由前端过滤内联思考块兜底。

评估体系为什么分成 eval/ 和 evalbench/ 两套？

能讲：eval/ 是契约未定时的冻结占位：14 个版本化对象、__TBC__ 槽位、comparable=false、real_api 档被契约门禁阻断，绝不拿它出质量结论。等真实 API 细节明确后，另起 evalbench/ 做平行工作台：自建 12 条中文样本、提示词 v1→v2→v3、参数 A/B/C、多模型对比，每轮独立 Git 分支并回写 config_snapshot 的 branch/commit。

边界：样本是自建的（参考 RGB / SQuAD 2.0 的任务与指标口径），不是官方数据抽样；comparable=false 的离线 run 不进任何质量结论，质量基线仍未冻结。

SQLite + 进程内队列能叫生产实现吗？

能讲：明确说「这是演示替身」。webapp/ 的价值是零依赖把链路跑通、可复现、可讲解；生产骨架在 backend/，用 PG / Milvus / Redis + Celery / MinIO，并有 Docker Compose 编排。面试时把两者分开介绍，反而能体现清楚「什么跑通了、什么是替身」。

不能讲：把演示切片的性能数字当生产指标，或说「已经具备高可用」。

A / B / C 三档交付怎么界定？

能讲：A 档是「设计 + 规则文档 + 架构预留」，B 档是「可运行演示切片 + 单测」，C 档是「生产加固 + 真实压测 / 账单 / SLO / 灰度」。当前项目定位在 B 档 + 一部分 A 档预留；C 档的监控告警、容灾演练、SSO、真实供应商账单校准、屏幕阅读器实测都明确列在「未做」清单里。

这句话是面试里的护城河：「列出尚未完成」不等于「本次要补完」，把上线级事项拉进本期既做不完，也必然把「只设计」说成「已落地」。

如果继续往下做，下一步优先补什么？

能讲：按 docs/capability-priority.md 的高优先级：① 把 backend 已实现的部门树与 decide() 下沉到演示切片并补 A13 一致性对拍（当前最大的越权缺口在列表侧缺逐条复核）；② Redis 令牌桶替换进程内滑动窗口；③ trace→span 结构化观测；④ 评测 CI 闸门与质量基线。

已定方案、代码尚未实施的 13 步改造顺序见 docs/org-model-change-plan.md §5.11，六个一票否决项见 §8.5。
