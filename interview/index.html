LLM 路由快照：跟着这次选择走的「单文件」

用户要求「LLM、对应的快照时间版本、提示词、参数等都要同步单文件跟着这个 LLM 走； 没有就空占位」。落地是每次路由选择生成一个物理 manifest，与同次入库 JSON 双向摘要互引； 换模型 / 提示词 / 参数都会改变 snapshot_version 进而改变 run_id，旧 manifest 不复用。

{
  "schema_version": "showcase-manifest@1.0",
  "run_id": "<sha256(文件摘要 + params_hash + snapshot_version)[:20]>",
  "created_at": "2026-11-15T00:00:00Z",   // 固定逻辑时间，非挂钟
  "route": {
    "tier": "pro",                        // 复杂档 difficulty=0.735，连续 2 次命中后
    "trigger": "difficulty_threshold",
    "difficulty": 0.735,
    "hysteresis": { "enter": 0.60, "exit": 0.40,
                    "consecutive_hits": 2, "state": "pro" },
    "fallback_chain": ["pro", "standard", "fallback"],
    "model": "",                          // 空占位：未选定供应商
    "model_snapshot_at": null,            // 空占位
    "prompt": "", "prompt_version": "",   // 空占位
    "params": {},                         // 空占位
    "placeholder": true,
    "cost_hint": { "estimated": false, "note": "仅路由决策，未发起外部调用" }
  },
  "ingest_ref": { "path": "out/<run_id>.ingest.json", "sha256": "…" },
  "offline": true, "external_request_count": 0
}

诚实边界：选出 Pro 档不代表调用了 Pro 模型。 本轮演示一律离线、不发起外部 LLM 调用，所以模型 / 快照时间 / 提示词 / 参数按用户要求保持空占位， 绝不填编造值；在线填真值属「只设计」。阈值与权重均为演示起始值，非压测结论。 另外滞回要求连续 2 次命中：单次复杂档解析是 standard(1/2)，同一份文件再跑一次才升 pro(2/2)； 路由状态按「文件摘要 + 参数哈希」隔离，不串用户，进程重启清零。

已实现 可运行 · 有测试

演示切片 webapp/ 与后端骨架中真实可跑、可复现的部分。

SQLite 与进程内队列是 PG / Celery 的演示替身，页面内已明确标注。

只设计 生产基础设施 · 未接入

要分层说，不能一句「没做」糊过去：backend/ 骨架里算法与契约层有代码、有单测； 真实 PG / Milvus / Redis / Celery 集群没接、没集成测。下面逐条标清测到哪一层。

  • 混合检索：rrf_fuse() + decide() 召回前 expr / 召回后逐条复核，契约层已实测； PG tsvector 全文、真实 Milvus expr 执行、端到端 MRR/NDCG 未测
  • 进度：阶段权重单调性、体积加权、取消排除 已实测（纯函数）； Celery 批次/页级 chord、Redis pub/sub 快照与断线重连 未测
  • 部门权限：decide() 的越权红线 8 项（显式 deny / 跨部门 / 子树 / 敏感度上限）已实测； 完整部门树拓扑 visible_department_ids()、逐段落/逐行 ACL 未落地
  • 完整 ACLGrant、跨部门显式授权、trace→span 全链路、审计留存合规、全局并发闸：只设计
实测证据：python -m pytest -q backend/tests → 26 passed （原 16 项纯函数 + 本轮新增 test_retrieval_contract.py 10 项「先过滤→再融合」对拍，含 A13 双向一致性）。 逐段落 ACL 仅保留开关预留（默认关闭），不假装已启用；演示切片是 SQLite + 进程内队列替身。

12 / 冲突

事实冲突：不让模型自己挑

两份文档打架信谁？标准答法
13 / 缓存

双层缓存 + 版本感知失效

L1 内存 LRU（重启清空）+ L2 SQLite（重启可恢复）。缓存 key 有 13 段：查询、模型、embedding、top_k、rerank、授权快照、数据版本、策略版本等；缺哪段就对应一类事故（串权限、串模型、旧答案）。文档 / 授权 / 策略变化只递增版本让旧 key 自然不命中（懒失效），命中时仍复核三重版本字段。

TTL 不是权限控制 · 先过滤后写

06

面试常问 Q&A

点击展开。回答刻意保留「取舍与代价」，不把演示切片讲成上线系统 —— 这也是本项目最想训练的答题习惯。

为什么不用多租户？多用户多部门怎么隔离？

当前定位是单组织内的多用户多部门，跨组织隔离这层用不上，留着反而让每次查询都多带一个静态分区键。多租户仅作为未来研发方向写入文档，本次不实现。

去掉 tenant 后，部门树成为唯一组织边界（Department.parent_id + path + level），对外统一表述为单组织 + 部门树逻辑隔离。

但要强调一句：唯一组织边界 ≠ 唯一可见范围来源。可见范围仍由部门/子树、owner、显式授权、角色、敏感度上限五类叠加，最终 allow/deny 一律由 decide() 逐条复核，不能把检索表达式简化成「只按 department 过滤」。

隔离强度下降怎么解释？会不会被质疑「把安全做弱了」？

要主动承认隔离强度确实下降了，不藏取舍，但因果要讲准：

① 原来的 is_partition_key=True 只是把字段值散列到固定 32 个分区的查询路由 / 性能机制，从来不是「一租户一分区」的硬隔离 —— build_permission_expr() 里本来就显式写死了 tenant_id == "…" 应用层表达式。所以不是「拆掉了一道原本存在的硬隔离」。

② 真实下降在于 expr 首条件的性质变化：从「静态、互斥、全库唯一、只由依赖注入产生的 tenant_id」换成「动态、层级、可变、由 visible_department_ids() 按拓扑算出的部门 id 列表」。后者是超集、依赖应用侧一次拓扑计算；算错或算空时影响面从跨组织扩大为跨部门乃至全库。

③ 因此补偿手段是安全必需而非可选优化：列表侧与检索侧都逐条过 decide()，并用「列表集合 ↔ 检索召回集合」双向一致性对拍证明没漏。

429 有两类，分别怎么处理？为什么额度耗尽不能重试？

rate_limit_exceeded（频率超了，等会儿能好）：指数退避 1s / 2s / 4s + 随机抖动，有 Retry-After 就听它（上限 30 s），最多 3 次。抖动是为了避免限流恢复瞬间多个请求同时打过去造成惊群。

quota_exceeded（墨点 / 额度用尽）：不重试，直接降级为本地拼接回答并标记 degrade_reason=quota_exceeded，前端提示换模型或换供应商。重试只会继续消耗注定失败的请求。

两条硬约束：流式一旦开始吐字就不再重试（否则用户看到重复内容）；单次请求级退避之外，全局并发闸 / 队列吸收突发属于设计，不在演示切片里。

为什么向量缓存 key 要带模型名？

cache_key 含 provider + 模型名，向量按 (chunk_id, cache_key) 缓存。不同 embedding 模型的向量维度和语义空间都不同，若切模型后复用了旧向量，余弦相似度会静默归零 / 失真 —— 没有异常、没有报错，只是检索结果悄悄变差，最难排查。

带模型名后切模型天然隔离，旧向量不会被命中。生产侧更进一步：换 embedding 模型必须重建 Milvus collection 并全量重算，代码里做了维度校验并给出明确报错。

同理，去 tenant 后缓存/进度/对象 key 改为「静态组织命名空间 + principal 授权快照」，转岗或授权变更后旧快照缓存不可命中；成本/用量台账按 department_id 事件快照，不随转岗回溯重写。

A / B / C 档边界怎么划？现在算哪一档？

A 档（当前基线）：离线可跑、闭环可演示、降级可见。注册登录 → 上传排队 → 流式问答 → badcase 采集 → 管理员完成度与导出串成一条闭环。

B 档（面试期加固）：真实 embedding / 中文分词 / Rerank / 压测 / 越权用例集 / trace 全链路。本项目已接入真实外部模型与 Rerank，属于「A 档偏 B」，但压测、越权用例集、trace 全链路仍未做，不能说成 B 档完成。

C 档（团队质量工作）：容灾演练、容量基线、审计留存合规、监控告警、灰度回滚 —— 是一个人的加班替代不了的。

一句话边界：这是「架构验证版」，不是「上线版」；链路完整、接口可跑、约束渗透到表结构与代码分层，但没有压测、没有容灾演练、没有全量回归。

SSE 为什么用 fetch stream 而不是 EventSource？断线怎么恢复？

EventSource 不能自定义 Authorization 头。企业系统不该把 JWT 放到 query string —— 会被 nginx 日志、浏览器历史、代理记录留下来。fetch 可以带 Bearer，也能拿到断流异常。

断线时携带 resume_from 重连，服务端跳过已发 token，最多 3 次；按 conversation_id 幂等，聊天日志只写一次。已吐出正文后才中断的情形单独标 stream_interrupted，只提示「以上为已收到的部分内容」，绝不把降级文案拼在真答案后面。

另有两处细节：部分网关结尾会发 choices: [] 的纯 usage 块，流式解析跳过空 choices，避免把正常回答误判为 model_error；推理模型可能只吐 reasoning_content，此时标 empty_model_output 并用检索片段兜底，不出空白气泡。

检索为空 / 模型报错 / 后端挂了，前端分别怎么表现？

检索为空：degraded=true + 明确「没有找到」的拒答话术，不编造。格式不支持：文档状态 error + 具体原因，不静默丢弃。繁忙：橙色横幅显示「处理中 N / 排队 M」+ 侧栏状态点变黄 + 文档行排队进度。

模型报错 / 限流：提供者内部退避 3 次；仍失败则 rag.stream_answer 捕获异常，不改 SSE 流、不丢本次问答，回退本地拼接并标 degraded=model_error。嵌入不可用回退词法排序并标 retrieval_mode=lexical(fallback)。

后端不可达：红色横幅，每 2.5 s 探测，恢复后提示并自动刷新数据。令牌失效：统一 401 拦截，退回登录页。原则是所有降级都「留痕 + 可见」，绝不静默失败。

badcase 为什么要「采集与查看权限分离」？完成度怎么保证对得上？

普通用户可以采集 badcase（POST /api/badcases 返回 201），但查看 / 导出 / 完成度仅 admin（接口同样 403）。这样一线用户能低成本反馈问题，又不会看到全组织的评测数据。

字段齐全：question / answer / verdict / issue_desc / source / created_at / eval_task_id / status / created_by。创建时校验 eval_task_id 存在，不存在直接 400。

完成度由「该任务关联的 badcase 记录数」派生，不是独立计数器：已完成 = 关联记录数，待处理 = max(0, 目标数 − 已完成)，完成率在服务端钳制到 [0,1]。所以不会出现「记录查不到但进度涨了」或「进度超过 100%」。导出与列表共用同一套筛选参数。

eval/ 为什么要冻结？evalbench 做了真实评估为什么不算质量结论？

eval/ 的 14 个版本化对象是评测体系的事实源：禁原地修改，已产生 run 的对象必须升版本；变体只在内存生效。占位档位结果一律 comparable=false，质量结论 NOT_COMPARABLE，禁止据此冻结阈值；真实 API 的地址、鉴权、模型名与配额仍是 __TBC__。

evalbench/ 是独立体系，不 import backend、不改冻结对象，做多提示词/多参数/多模型对比与逐轮 Git 分支收敛。它的结果是链路可跑通的证据，不是质量基线。

冻结校验用 git diff --exit-code -- eval/ demo/ + python demo/selftest.py（16/16、7 字段与 run_id=RUN-095a2a4a40c6 全一致）；config_snapshot_hash 由 14 个对象规范化哈希产生，零 diff 即哈希不变，无需新增校验脚本。

SQLite + 进程内队列，会不会被质疑「这不就是个玩具」？

关键在契约一致 + 页面诚实标注。演示切片用 SQLite 作唯一真值（对应 PG 的 ingest_jobs / 审计台账）、进程内信号量队列作 Celery + Redis broker 的替身，用 2.5 s 轮询 + SSE 心跳展示同一套状态语义。

页面里有一张「组件替身映射：演示切片 vs 生产架构」表，逐行写清「本切片（真实可跑）/ 生产架构（设计）」；view-system 还列出 A/B/C 档与「明确不做」清单。换掉替身就是真链路，但绝不声称切片实现了 PG / Milvus / Celery / 完整 ACL。

对应的验证：33 项端到端自测覆盖登录鉴权、admin 门禁 403、繁忙排队、格式降级、流式与续传索引连续、检索为空/模型报错降级、badcase 字段完整性、完成度前后一致、统计权限分离等；这些断言校验的是行为与契约，不是替身的性能。

i18n「中文原文即 key」有什么坑？无 value 的 <option> 为什么危险？

做法：中文模式直接返回原文（零替换、零性能损耗、不改任何既有数据/表单值）；英文模式用 TreeWalker 扫文本节点 + 属性，MutationObserver 覆盖动态 innerHTML；动态文案加 data-i18n="中文原文" 才能可逆重设。

坑：用户数据容器必须放进 SKIP_SELECTORS（问题 / 答案 / 文件名），否则翻译会把数据当界面文案改掉；语言/主题/模式三份 localStorage 独立持久化，互不覆盖；theme.js 必须在 <head> 同步执行、配合 kb-boot 首帧禁过渡，才不会有主题闪烁。

无 value 的 option：提交值默认取显示文本。若不先把中文原文固化到 value，切成英文后 badcase 判定提交值会变成英文，直接写坏后端判定。引擎在扫描到这类 option 时会把原文写进 value；新增下拉一律显式写 value 更稳妥。另外改 JS/CSS 要四处 ?v= 同步升版，否则浏览器命中旧缓存。

6 套主题色 × 明暗正交是怎么做到的？无障碍怎么保证？

CSS 变量分三层：:root 放尺寸/字体/动效常量；html[data-theme="..."] 放 6 套主题色的 accent 与 rgb 三元组；html[data-mode="light|dark"] 放中性色、状态色与 primary 映射。两个维度正交 → 任意主题色可与任意模式自由组合（12 种）。

深色模式的状态色单独调过高对比（--danger-ink / --warn-ink / --success-ink 等），不是简单反色；docs/CHANGELOG.md 记录过 13 组对比度数值核算（均 ≥ 4.76，WCAG AA 正文口径），以该记录为准。

另有全局 :focus-visible 描边、prefers-reduced-motion 关闭动画、760 px 以下侧栏转横向滚动 / 顶栏 sticky / 卡片单列、英文模式侧栏加宽到 258 px。屏幕阅读器实测仍属未做，只做了键盘可达与 ARIA 基线，不会说成「已完成无障碍实测」。

文档解析为什么分三层？90:10 是怎么定的？多模态这层怎么证明是真的？

三层：P0 自研（纯标准库 + 可选 pypdf/Pillow）处理有文本层 PDF、纯文本、图片容器头与表格结构；P1 收费 OCR / 版面解析处理扫描件与复杂表；P2 多模态 LLM 传图处理疑难页。三者实现同一个 ParseStrategy 接口，下游 ChunkSpec(page_no, section_path, block_type, confidence, source_level) 契约完全不动——换供应商只改一个策略类，不用动 chunks 表、Milvus schema 和引用契约。

90:10 不是随机分流。固定比例随机抽样既不能保证疑难页被送到最贵链路，又会让能自研解决的页白付钱。这里的 0.10 是上限 / 熔断线：质量门禁只在本页「零字符 / 无文本层 / 置信度低于 0.75 / 表格检查未全过」时才升级；VisionBudget.slots = max(1, ceil(页数 × 0.10))，20 页就是 2 个名额，用完显式标 escalation_budget_exceeded 并回退上一级结果。正常文档应该是 0% 触发。选 10% 而不是 20% 是因为 P2 最慢最贵，10% 足够覆盖长尾疑难页；阈值是演示默认经验起始值，需用真实语料校准，不是压测结论。

怎么证明多模态是真的：先读 /models 的 input_modalities（10 个模型里 6 个支持 image），再用 双图对照排除「靠猜或复述提示词」：图 A（浅蓝底/深蓝字 73492/CODE-A）答 "73492 on a light blue background..."，图 B（浅黄底/红字 18620/CODE-B）答 "The image shows the number 18620 in dark red..."，两次回答不同且都精确命中数字、背景色、标签。完整解析链路复跑得到 reason=vision_applied / degraded=None，upstream 里能核对模型名与 token 用量。低思考档 thinking={"type":"disabled"} 也做了参数对照：推理 token 55 → 0、耗时 979 ms → 467 ms，而元数据里的布尔 reasoning 参数实测无效。

边界：这是功能连通性实测，不是准确率结论；P1 收费 OCR 仍未接通；PARSING_OFFLINE=1 或调用失败时 structured_fallback() 只输出可测事实并明确标「非视觉理解」，绝不编造图片内容，降级时还会把 P0 正文拼回去不整页丢掉。图片里的精确数字仍应以 OCR 结果为准。

现场怎么看：侧栏「解析实验室」上传同一份文件、切换 auto / local_only / multimodal / off，逐页轨迹表会并排显示级别、置信度、耗时、升级自、预算拦截与原因。这是把技术深度讲清楚的关键证据。待补端点清单在 docs/parsing/07-api-contracts.md。

知识库两份文档互相打架，RAG 信谁？「信相似度最高的」错在哪？

错在哪：向量相似度里没有来源权威度、生效期、适用范围。模型挑来源时还会受位置偏差（靠前的注意力更高）、语气强弱（「revenue of $4.2M」比「following restatement… is $6.8M」更像事实）、词法重合影响。一份群聊截图不该因为分数高就覆盖公司制度。

正确分层：① 检索前用元数据硬过滤（权限 / 地区 / 版本 / 已过期 / 未生效）；② 检索后把片段抽成 claim，按「主体 | 属性 | scope」分组，只有归一化取值互斥或肯定/否定相反才报冲突；③ 冲突图求连通分量，每簇独立裁决——先业务权威注册表，再生效期但强制 needs_review，都不行就并列两个版本 + 原文 + 转人工，不发明 tie-breaking 规则；④ 生成层收到 EvidenceRecord.conflict_signal，必须显式披露分歧，不能把互斥片段无序塞进上下文。

现场证据：「知识治理」页能看到婚假 10 天 vs 15 天走 trust_newer_with_review / 需复核，报销上限 5000 vs 8000 元走 trust_higher_authority；负向对照里 GB 地区不算冲突、接口超时同值不算冲突。展开 resolution_log 能看到被淘汰断言仍留痕。

边界：这是规则级实现，不是 NLI 模型级识别；权威注册表的业务审批流未做；合成场景不是质量基线。

怎么防止 AI 拿过期政策回答？新鲜度会不会把老文档全干掉？

不会：有效分 = 相关分 × (1 − blend + blend × decay)，decay = max(floor, 0.5^(年龄/半衰期))。默认 blend=0.65、floor=0.10，一篇高度相关的老文档仍会保留，只是排序下降；每个数都能在前端表里手算。

最新 ≠ 适用：年龄优先用 last_verified_at（人工复核）而不是入库时间；valid_from 在未来的文档标「未生效」并排除（不是判过期）；expires_at 已过按 demote / exclude / warn 三档处置；地区、套餐、产品版本放 scope，不同 scope 取值不同是适用性差异、不是冲突。适用性门控是硬约束，不受新鲜度开关影响——开关只关时间衰减。

现场证据：开启新鲜度排序 D2→D4→D3→D1→D6，仅关衰减恢复 D1→D2→D3→D4→D6；D5 未生效被排除，D6 已过期降权但仍在报告里。把过期处置从 demote 改成 exclude，D6 会从候选消失。

边界：真实检索链的重排默认关闭、只在 top_k 内生效，生产应在 SQL / Milvus expr 阶段先做召回前硬过滤；幽灵向量、CDC 近实时增量、跨缓存版本感知失效、金标/金丝雀回归集均未做。

缓存 key 怎么设计？文档更新后旧答案怎么办？

key 的每一段对应一类事故：查询哈希、org 命名空间、缓存类型、embedding 模型、生成模型、top_k、检索模式、rerank、新鲜度开关、授权快照、数据版本、策略版本、schema 版本。缺 embedding 模型名会复用旧向量（维度不一致时余弦静默归零），缺授权快照会跨用户串权限，缺数据版本会在文档删除后继续返回旧片段。

失效不是只靠 TTL：文档增删改 → 递增 data_version；转岗 / 角色 / ACLGrant 变更 → 递增 grant_version；策略变更 → 更新 policy_version。做法是懒失效：只递增版本，旧 key 自然不命中，不做批量删除；TTL 到期再回收空间。每次命中仍比对三重版本字段——TTL 不是权限控制，写缓存前也必须先把越权片段过滤掉。

现场证据：「缓存与恢复」页能看到 key 的 13 段拆解、命中率与失效原因分布；点「运行缓存演示」会看到首次 miss → 权限过滤前后条数 → 清 L1 后从 L2 命中 → 数据版本变化后新 key 未命中。

边界：答案缓存 / 语义缓存未做，检索结果缓存默认不接主问答链路；SQLite 单文件不是生产 Redis，阈值是演示经验起始值。

服务器重启会丢什么？怎么证明重启后状态正常？

先分三类：① 可安全丢弃——限流滑动窗口、解析轨迹 deque、SSE 连接，丢了只是窗口重置，不产生错误数据；② 可从真值重建——队列活跃/排队态、进度快照，靠 documents.status 扫描并幂等重投；③ 必须持久化——配置与策略、预算、用量台账、文档与 chunk_embeddings、会话，落 SQLite 与 runtime_state。真值层先行，所以连 SIGKILL 都不怕。

启动 7 项自检：schema 就绪、易失状态声明、孤儿任务重投、幽灵向量对账（chunk_embeddings 中已无对应分块的行删掉）、文档指纹校验（变化则递增数据版本）、策略恢复、过期缓存与容量清理。本报告 healthy=True 且逐项给分类与结论；本轮还修了「删文档只删 chunks 不删向量」这个真实幽灵向量缺陷，属于源头治理。

怎么证明：隔离库做两次真实进程启停——先改策略（半衰期 45 / blend 0.5）、写 1 条缓存、埋 1 个 analyzing 孤儿任务和 1 条幽灵向量；强停后重启：boot_count 1→2、重投 1、清理 1、策略 45/0.5 完整恢复、L2 条目仍在、无 500。强停时 last_shutdown_at 没写入，正好反证「关闭钩子不可靠，必须靠真值层」。现场可在「缓存与恢复」页点「模拟重启」复现。

边界：这是功能连通性实证，不是压测或 SLA 结论；没有持续看门狗 / 死信队列 / 心跳 lease；演示切片的 SQLite + 进程内队列不是生产 Redis/Celery。

PII 脱敏为什么不能只在展示层做？流式输出怎么防漏？

因为原文会走别的出口：chunks 是检索、向量缓存、来源卡片、chat_sources 的共同真值源；一旦原文进了分块，展示层打码只是自欺欺人，审计日志、badcase 的 CSV 导出、模型上下文里都还是明文。所以做成一层统一规则、四个出口：入库前在分块前脱敏（异常 fail-closed 阻断整份入库）、进模型前脱敏问题与片段、输出前过流式闸、日志与导出前脱敏 target/detail 与全部导出字段。次序上先按原文检索再脱敏，否则词法召回会被打码破坏。

误报比漏报更容易被追问：\d{17}[\dXx] 会把订单号当身份证，所以必须过 ISO 7064 MOD 11-2 校验位和出生日期；1[3-9]\d{9} 会命中长号子串，所以加前后数字边界；16–19 位纯数字要过 Luhn 且末尾跟 X 时不判成银行卡；中文姓名/工号/护照只认带字段名词的写法。本轮实跑还抓到一个真缺陷：校验位非法的身份证前 17 位恰好通过 Luhn，被误报成银行卡，已修。演示样本全部换成按算法算出的合法校验位，不用随手编的号码。

流式是真难点：SSE 逐 token 下发时，18 位身份证可能跨多个 chunk。只保留尾部 24 个字符不够——标识符起点落在可下发区、终点还在保留区时，前 10 位会先发出去，发出去就撤不回来。现在的做法是找出横跨下发边界的连续候选串，把边界收缩到它的起点整串扣住，等它完整进缓冲区再扫描。为了不破坏断线续传的 token 索引连续性，保持「一个原始 token 一个包」、index 用原始索引，扣住的尾部由 done.tail 补齐、前端在 done 时追加。

现场证据 + 边界：「内容安全 / PII」页可一键跑 9 条合成样本、4 条负向对照、四出口链路与逐字符流式验证（leaked=false），台账按出口显示真实命中数且只存类别与数量。诚实标注：规则级检测不是模型级 NER；backend 骨架未接本包；可逆 token 默认关闭；默认哈希盐是演示占位值；真实断线重连时尾部可能少几个字，生产应把续传游标改成基于安全输出字节偏移。

你说这些「只设计」，那到底测没测？

先分两层，别一句「没做」糊过去：① 算法 / 契约层——backend/ 骨架里是有代码、有单测的；② 基础设施集成层——真实 PG tsvector、Milvus 集群、Redis pub/sub、Celery broker/chord 确实没接、没集成测。演示切片是 SQLite + 进程内队列替身，替身跑通不等于生产组件测过。

实测命令与数字：python -m pytest -q backend/tests → 26 passed。原有 16 项覆盖 rrf_fuse() 双路去重与排名、decide() 的八条越权红线（显式 deny 优先 / 跨部门拒绝 / 部门管理员覆盖子树 / 敏感度上限 / 精细权限开关默认关）、阶段进度单调性与体积加权。本轮又补了 backend/tests/test_retrieval_contract.py 的 10 项离线对拍：把「召回前 expr 收窄 → 召回后逐条 decide() → RRF 融合」的顺序纪律锁住，其中 A13 双向一致性验证 expr 排除的候选不会被 decide() 放行，以及融合不能把被过滤的片段重新带回来（对照实验里不过滤时跨部门片段会排第一）。全部离线可跑、不连真库。

明确没测，也不假装测过：真实 PG 全文/BM25 与真实 Milvus expr 执行、混合检索的 MRR/NDCG 与 P95 延迟、Redis 快照的断线重连、Celery 页级 chord 与失败重试、完整部门树拓扑 visible_department_ids()、逐段落/逐行 ACL、trace→span 全链路与全局并发闸。原因是这些组件在本仓没有接入，也没有评估集和压测环境；拿 SQLite 替身的通过结果去说「生产测过了」是失真。

面试标准答法：先把卡片上的四项按「已实测（契约层）／未测（集成层）」拆开，报出可复跑命令和 26 passed，再主动列出没测清单和缺什么才能测（真实集群 + 评估集 + 压测），最后说明演示替身与生产实现的边界。把「只设计」当挡箭牌会被追问穿，分层说清楚反而加分。
