# 检索参数收敛与链路性能改造

> 数据集：CmedqaRetrieval（`mteb/CmedqaRetrieval`，C-MTEB 六个检索任务之一，官方 qrels）
> 规模：200 题；检索池 3000 篇（3221 chunk）与 12000 篇（12840 chunk）各一套；`seed=42`
> 生成侧：CMRC 2018 validation，40 题，848 篇文档池
> 运行日期：2026-11-18

## 结论：最佳参数版本

| 参数 | 取值 | 依据 |
|---|---|---|
| `top_k` | **5** | `hit@k` 拐点：hit@4 0.810 → hit@5 0.830 → hit@10 0.875，后 5 条只多 4.5pt 却让上下文翻倍；生成侧 top5 与 top10 正确率同为 1.000 |
| `rerank_depth` | **20** | 3000 池与 12000 池的 nDCG@10 / R@10 双峰都在 20；把时延纳入后复核（§2.4）仍是 20：R@5 比 depth10 高 1.16～1.87pt，多付 106～117ms |
| `rerank` | **external（on）** | R@1 +3.9pt、nDCG +3.7pt，R@10 不变（只在候选内改顺序）；关掉省 382ms 但 R@5 −5.23pt（§2.4） |
| query 向量缓存 | **on**（LRU 512 / TTL 1800s） | 同一句话重复问省 325ms（p50 855→529ms）；只缓存向量不缓存结果，权限/门禁每次都跑（§1.6） |
| 自适应重排 | **on**（`s1−s2 ≥ 0.05` 跳过） | 跳过 24~29% 的 rerank，均值省 10~14%；质量变化在抖动内、R@1 略升（2026-11-27 复跑 p95 未见稳定下降） |

已落为默认值：`webapp/rag.py` 的 `TOP_K = 5`、`RERANK_DEPTH = 20`、`ADAPTIVE_RERANK_MARGIN = 0.05`、`retrieve(..., rerank_depth=RERANK_DEPTH)`；缓存入口 `webapp/providers.py` 的 `embed_query()`。

**3000 池、200 题、top_k=5、depth=20、缓存 + 自适应重排全开**：nDCG@10 0.6742 / R@1 0.4284 / R@5 0.7419 / MRR@10 0.7102，检索 mean **701ms**、p50 786ms、p95 916ms。12000 池同配：nDCG@10 0.5566 / R@5 0.6136 / mean 919ms。**对外报数必须带池规模**——0.67 是小池红利，0.56 才是大池真实水位。

> 2026-11-27 复核：同一代码重跑 3000 池 nDCG 0.6747 / R@5 0.7419 / mean 625ms；12000 池 0.5547 / 0.6086 / mean 850ms。均值收益复现，但 p95 在两套池都没有稳定下降（3000 池 865 vs 856ms，12000 池 1097 vs 1002ms）。本文件保留 2026-11-18 的原始记录，最新结论见 `docs/retrieval-param-review-2026-11-27.md`。

## 一、性能改造：真瓶颈不是词法门禁

### 1.1 「下推词法门禁」的实测结果与我的预期相反

最初判断门禁是瓶颈（13k chunk × 20 个中文二元组 ≈ 26 万次子串扫描全在 Python）。下推后逐条比对 20 个 query、3221 条 chunk，**分数零差异**（`strpos(lower(text), t) > 0` 与 `t in text.lower()` 等价），但速度：

| 方案 | 3221 条耗时 | 说明 |
|---|---|---|
| Python 全池算分（原实现） | 47ms | 内存里做 `in`，CPython 的字符串查找很快 |
| SQL 打分版（12 个 `CASE ... strpos`） | 106ms | 全表被扫 12 遍 |
| **SQL 布尔版（`OR ... LIKE ... LIMIT 1`）** | **0.9ms** | 命中即停 |

**打分版比 Python 还慢。** 真正有效的是布尔版——因为 `retrieve` 只需要「池里有没有命中」这一个二值判断：

```python
# 门禁一旦命中，候选就放宽到全池，排序交给向量；
# 命中几条、哪几条都不进入后续计算。
candidates = pool if (gated and use_vector) else gated
```

所以「只把命中集拉回 Python」这个做法在这里**不能做**：它会把候选从全池缩成命中集，而跨语言/改述场景（中文问英文 PDF）零词法重叠的文档将失去进入向量排序的机会——这是 2026-11-16 多格式评估实测过的 0 召回事故。下推保留了这个语义，只把判定搬进 SQL。

### 1.2 真瓶颈：为了「检查有没有缺向量」，把全池向量拉回了 Python

`_semantic_rank_pg` 里有一行：

```python
_get_or_compute_embeddings(candidates, cfg)  # 保证候选都有向量
```

排序本身在 SQL 里做（`1 - (embedding <=> ?::vector)`），Python 侧根本不需要这些浮点数。但这个函数会把**每个候选**的 1024 维向量 `json.loads` 回来，只为判断"有没有缺失"：

| 组件 | 3221 条耗时 |
|---|---|
| `_get_or_compute_embeddings`（全量加载 JSON） | **1081ms（占 75%）** |
| 向量 SQL 排序 | ~50ms（含上一步则 1430ms） |
| 全池加载含正文 | 28ms |
| Python 词法门禁 | 47ms |

改为 `_ensure_embeddings`：只查「哪些 chunk_id 已有向量」（同样的表、只取 id 不取向量），缺的才补算并双写。同规模 **15.5ms**。

### 1.3 端到端结果

| 检索池 | 改造前 | 改造后 | 提升 |
|---|---|---|---|
| 3221 chunk | 1969ms | **697ms** | 2.82× |
| 12840 chunk | 6279ms | **875ms** | **7.18×** |

剩余耗时的大头是 query embedding 的外部调用（约 570ms，3221 池实测）。当时写的是「这部分没有再优化的空间——除非把 query 向量缓存或换本地模型」，**缓存这一层见 1.6，已经做了**。池越大，本次改造收益越大，因为省掉的是与池规模成正比的向量传输。

### 1.4 等价性验证（改实现不改结果）

| 验证 | 结果 |
|---|---|
| SQL 门禁 vs Python 门禁，20 query × 3221 chunk 逐条分数 | **0 条不一致** |
| 改造前后同参数 200 题 `nDCG@10` | 0.7057 vs 0.7053（逐题偏差 **0.000000**） |
| `ranked_ids` 前 5 名 | 17/20 完全一致，3 例差异只在第 6–10 位的同分换位 |
| `R@1 / R@5 / R@10` | 0.4409 / 0.7415 / 0.7993，**逐位相同** |
| `webapp/tests` 全量 | **139 passed** |

### 1.5 顺手修掉一个可复现性缺陷

`ORDER BY embedding <=> ?::vector` 没有次级键，同分 chunk 的顺序取决于表物理顺序。同一批数据两次导入（uuid 不同）就会换位，**同参数跑出两个 nDCG**（实测 0.7053 与 0.7079，差 0.0026）。

已加 `, chunk_id` 作次级键，候选加载加 `ORDER BY c.id`。现在同参数重跑，逐题偏差为 0。

### 1.6 query 向量缓存：把最后一段同步调用归零

改造后剩下的耗时分布变了。3220 chunk 池、`top_k=5`、`rerank_depth=20`、外部 rerank 开启，**暖相分段实测**（每题均摊）：

| 段 | 耗时 | 说明 |
|---|---|---|
| `rerank`（外部 /rerank HTTP） | **438.67ms** | 20 条候选，约 22ms/条 |
| `_semantic_rank`（含 `_ensure_embeddings` 23.48ms） | 61.46ms | pgvector 一条 SQL + 补缺向量 |
| `_load_light_chunks` | 18.69ms | 全池轻量列 |
| `get_all` / `_gate_hit` / `_attach_texts` | 3.56 / 3.47 / 3.75ms | 配置读表、门禁、回捞正文 |
| **合计** | **530.87ms** | 未归因 1.27ms |

冷相多出来的是 query embedding 那一次端点调用。给它加缓存后：

| 指标（20 题，3000 池 3220 chunk） | 冷相（每次回源） | 暖相（全命中） |
|---|---|---|
| `embed_query` 单独 p50 | 281.25ms | **0.01ms** |
| `retrieve` 全段 p50 | 854.69ms | **529.42ms** |
| `retrieve` p90 | 917.90ms | 556.98ms |
| 省 | — | **325.27ms（p50）** |

实现放在 `providers.embed_query()`：`(cache_key, sha1(原文))` 作键，LRU 512 条 + TTL 1800s，取出返回副本。`_semantic_rank_py` 与 `_semantic_rank_pg` 两条路径都改走它。

**边界（这是它不越界的前提）**：只缓存**一句话的向量**，不缓存检索结果。权限过滤、词法门禁、`data_version` 每次都照跑，所以不存在「拿 TTL 当权限控制」的问题；键里带 `cache_key`，`local:` 与 `external:` 两个命名空间天然隔离（同名 bge-m3 跨实现余弦只有 0.977，混用等于换模型不换向量）。

**等价性验证**：

| 断言 | 结果 |
|---|---|
| 缓存往返（放进去 vs 取出来） | **逐位相同** |
| 暖相连跑两遍 top_k | **逐位相同** |
| 冷相 vs 暖相 20 题指标 | R@1 0.5600、R@5 0.7883、MRR@10 0.7917、nDCG@10 0.7574 —— **两侧完全相同** |
| `webapp/tests/test_query_cache.py` | 5 passed（命中/命名空间隔离/副本/TTL/LRU/命中率） |

**一次没解释清的现象，查清了才算完**：第一次跑冷/暖对比时，20 题里有 1 题（q18）top5 第 5 名翻转，rerank 分数从 0.0099 变 0.0101。三项排查：

1. 同文本连续调 embed 端点 5 次，向量最大分量差 **0.00253**；但另一次实测差 **0.0000**——**端点对同一文本并非总是返回同一向量**（batch 内两条完全相同，所以不是 padding，是跨请求层面的动态批/分片）。
2. 该题第 20/21 名的 embed 分数间距只有 **8.04e-05**。
3. 排序对抖动其实很钝：拿 5 个抖动向量重排 3220 条，**3220 名全同**；两次独立 retrieve 的 rerank 输入 20 条集合与顺序也**完全相同**。

结论：抖动幅度偶尔跨过 8e-05 的边界就会换一位名次，属**端点性质，与缓存无关**；指标层面 20 题完全一致。所以留的是「缓存往返 + 暖相自洽 + 指标等价」三条断言，没有把「冷相=暖相逐位相同」写成断言——那个断言本身是错的，因为冷相每次都在向一个非确定端点要向量。

**诚实说清收益口径**：缓存只对「同一句话第二次问」有效。冷启动的不同 query 一分钱不省，所以 529ms 不能当线上 P99 汇报，线上收益 = 重复率 × 325ms。真正确定的好处是**评测扫参**：同一批 query 隔几秒换一组参数重跑，以前每轮重付 `N × 281ms`（200 题 = 56s），现在只有第一轮付。

## 二、参数收敛：`rerank_depth`

原实现是 `hits = candidates[:top_k]` 之后才 rerank，重排只能在最终几条里换顺序，**第 11 名再好也进不来**。新增 `rerank_depth` 参数把「从多少条里挑」与「挑完留几条」解耦（默认值等于 `top_k`，即原行为）。

### 2.1 3000 池（3221 chunk，200 题）

| depth | nDCG@10 | R@1 | R@5 | R@10 | MRR@10 | p50 |
|---|---|---|---|---|---|---|
| 10（原行为） | 0.7057 | **0.4409** | 0.7415 | 0.7993 | **0.7230** | 697ms |
| 15 | 0.7090 | 0.4209 | 0.7365 | 0.8300 | 0.7145 | 784ms |
| **20** | **0.7135** | 0.4209 | 0.7481 | **0.8450** | 0.7138 | 821ms |
| 25 | 0.7098 | 0.4209 | 0.7456 | 0.8365 | 0.7122 | 853ms |
| 30 | 0.7068 | 0.4159 | 0.7506 | 0.8365 | 0.7082 | 927ms |

### 2.2 12000 池（12840 chunk，200 题）

| depth | nDCG@10 | R@1 | R@5 | R@10 | MRR@10 | p50 |
|---|---|---|---|---|---|---|
| 10 | 0.5769 | 0.3505 | 0.5918 | 0.6652 | 0.6110 | 875ms |
| **20** | **0.5958** | 0.3405 | **0.6111** | **0.7173** | **0.6180** | 1000ms |

### 2.3 三条结论

**① 20 是双峰，不是越多越好。** nDCG@10 和 R@10 都在 20 取到最大值，25/30 反而回落。加深深度的代价是 rerank 输入变长（延迟 697→927ms），超过 20 条后排序质量不再提升。

**② 池越大，解耦越值钱。**

| 指标 | 3000 池（d10→d20） | 12000 池（d10→d20） |
|---|---|---|
| nDCG@10 | +0.78pt | **+1.89pt** |
| R@10 | +4.57pt | **+5.21pt** |
| R@5 | +0.66pt | **+1.93pt** |

大池里相关块更容易被向量排序挤到 11–20 名，重排解耦正好能捞回来。这也说明**小池上调参得出的结论会低估该参数的价值**。

**③ R@1 下降是标注假象，不是重排选错。** d=10→20 有 4 题从「top1 命中」变成「top1 未命中」，0 题反向。逐个查这 4 题发现：新 top1 **全部来自旧排名的 10 名之外**，且都是单 gold 题。抽样看内容：

- 第 1 题问「纤维蛋白原 1.401 很低吗……之前体检说是宫颈病变需要治疗吗」，标注 gold 只回答纤维蛋白原那一半；重排后的新 top1 答的是**宫颈病变要不要治疗**——query 的另一半，并不算错。
- 第 2 题问「做完爱后肚子痛，会怀孕吗」，标注 gold 说「不一定，排卵期机会大」；新 top1 说「怀孕可能性很大，建议买试纸」——语义一致，结论措辞不同。

Cmedqa 每题平均只有 1.82 个 gold，标注不完备 + 医疗问答里大量近义表述，使 R@1 系统性低估重排。**只人工核对了 4 题中的 2 题，其余 2 题未逐一确认。**

### 2.4 补测：把时延也算进去（`top_k=5`，200 题）

2.1/2.2 只按质量选深度。但重排是外部调用、**开销与深度近似线性（约 22ms/条）**，所以补了一轮「质量 × 时延」的二维对比。三组都在同一个 3000 池上（3221 chunk），只有深度与开关不同：

| 组 | nDCG@10 | R@1 | R@5 | MRR@10 | p50 | p95 |
|---|---|---|---|---|---|---|
| rerank off | 0.6280 | 0.4017 | 0.6958 | 0.6694 | **328ms** | 403ms |
| depth 5 | 0.6497 | 0.4334 | 0.6958 | 0.6978 | 563ms | 663ms |
| depth 10 | **0.6769** | **0.4359** | 0.7365 | **0.7115** | 604ms | 723ms |
| **depth 20** | 0.6754 | 0.4209 | **0.7481** | 0.7039 | 710ms | 822ms |

12000 池（12840 chunk）复核 depth 10 vs 20：

| 组 | nDCG@10 | R@1 | R@5 | MRR@10 | p50 |
|---|---|---|---|---|---|
| depth 10 | 0.5483 | **0.3505** | 0.5924 | 0.6028 | 840ms |
| **depth 20** | **0.5551** | 0.3405 | **0.6111** | **0.6068** | 957ms |

三条读数：

1. **rerank 值得开。** 关掉省 382ms，代价是 nDCG −4.74pt、R@5 −5.23pt。这一档差距远超噪声（200 题里 1 题 ≈ 0.5pt）。
2. **depth 20 仍是最优。** 3000 池上 depth 10 与 20 的 nDCG 差 0.0015（≈0.3 题，纯噪声），但 R@5（决定生成上下文的那个指标）20 比 10 高 1.16pt，12000 池高 1.87pt —— **池越大差距越大**，与 12000 池 R@10 +5.21pt 的老结论同向。多付的 106～117ms 买的是「池长大以后才兑现的召回余量」。
3. **depth 5 是伪节约。** 只 rerank 最终 5 条，nDCG 掉到 0.6497（比 d20 低 2.6pt），省下 147ms 不值。

所以 `RERANK_DEPTH=20` 不改。

### 2.5 自适应重排：什么情况下可以不花那 440ms

§1.6 量出 rerank 占暖相 **83%（438.67ms / 20 条）**，是最值得动的一刀。但「直接关掉」不成立（§2.4：R@5 −5.23pt）。

观察到的机会：**rerank 的价值不均匀**。它的作用是把「向量排不进前几」的相关块捞上来，前提是候选分数挤在一起；一旦向量第一名大幅领先，重排只是在候选内微调第 4/5 名的次序。于是加一道前置判定：

```
向量排序后取 s1、s2（cosine 相似度）；若 s1 − s2 ≥ τ 则跳过 rerank，直接用向量顺序。
```

**判据怎么选的（不是拍脑袋）**：一轮采集把「rerank 开」与「rerank 关」两套 top-20 顺序与分数都存下来，之后几十个阈值全部离线扫，不重复烧 API。然后对比四类判据，只有两个值得留下：

| 判据 | τ | 3000 池：跳过 / ΔnDCG / ΔR@5 | 12000 池：跳过 / ΔnDCG / ΔR@5 |
|---|---|---|---|
| **相对间距 `s1−s2`** | **0.05** | 29.0% / **−0.12pt** / −0.62pt | 24.0% / **−0.16pt** / −0.42pt |
| 绝对置信度 `s1` | 0.72 | 50.5% / −0.57pt / **+0.15pt** | 57.0% / **−1.16pt** / **−0.60pt** |
| 绝对置信度 `s1` | 0.70 | 59.0% / −1.92pt / −1.87pt | 67.5% / −2.28pt / −1.47pt |
| top1 与第 5 名间距 | 0.10 | 28.0% / −0.43pt / −1.12pt | — |

**绝对阈值 `s1≥0.72` 在小池上明显更划算（省 44%、ΔR@5 还是正的），但换到 12000 池就翻符号（ΔR@5 −0.60pt、ΔnDCG −1.16pt）。** 原因是绝对相似度的尺度绑定模型与语料（bge-m3 + 中文医疗 passage，0.72 这个数换模型就失效），而间距是尺度无关的。所以**否掉绝对阈值，采用 `s1−s2 ≥ 0.05`**。

诊断支撑（3000 池里 `s1≥0.72` 的 101 题）：向量第一名本来就是 gold 的有 82 题；重排把 top1 换掉 21 题，其中 R@1 涨 5 跌 4、R@5 涨 8 跌 5 —— **在「向量已经很确定」的题上，重排接近抛硬币，却要付 440ms。**

端到端结果（`rag.ADAPTIVE_RERANK_MARGIN` 生效，200 题，`top_k=5`/`depth=20`）：

| 池 | 跳过率 | 跳过组 mean | 未跳组 mean | 整体 mean | 对照 | 省 | nDCG@10 | R@5 |
|---|---|---|---|---|---|---|---|---|
| 3000 | 29.0% | 388ms | 829ms | **701ms** | 814ms（同会话 gate=0） | **13.9%** | 0.6742 vs 0.6731 | 0.7419 vs 0.7431 |
| 12000 | 24.5% | 592ms | 1025ms | **919ms** | 1025ms（估：未跑 gate=0 对照，取未跳组均值） | **10.3%** | 0.5566 vs 0.5551 | 0.6136 vs 0.6111 |

**p50 几乎不动（782→786ms / 957→964ms），别拿 p50 报收益**：跳过率不到 50%，中位数必然落在「仍在重排」那一峰；收益看均值（−14% / −10%）与 p95（1025→916ms）。

后悔量（跳过组里有多少题本来会被重排改好）：3000 池 58 题里 R@5 涨 1 跌 5、R@1 涨 2 跌 0；12000 池 48 题里 R@5 涨 0 跌 2、R@1 涨 1 跌 0。**丢的都是多 gold 题的「部分召回」，没有一题丢掉唯一 gold。**

**折半验证（防「在同一批题上挑阈值」）**：τ 是在同一份 200 题上扫出来的，所以再切一次前 100 / 后 100，只用前半选 τ、后半独立验：

| 池 | 前半选出的 τ | 前半跳过 | 后半跳过 | 后半 ΔnDCG | 后半 ΔR@1 | 后半 ΔR@5 |
|---|---|---|---|---|---|---|
| 3000 | **0.050** | 30.0% | 28.0% | −0.25pt | +1.00pt | **−0.75pt** |
| 12000 | 0.045 | 28.0% | 30.0% | −0.60pt | 0.00pt | **−1.00pt** |

前半独立选出来的 0.050 与最终取值一致（说明不是挑出来的好看值），但**样本外代价比样本内大**：R@5 实际是 −0.75 ~ −1.00pt（约 2 题 / 200），不是样本内的 −0.42 ~ −0.62pt。**这就是该规则的真实价格：1~2 题的部分召回，换 10~14% 的检索均值。**

**一个自己踩的坑，写在这里免得复现**：离线合成延迟时，关重排那一遍复用了上一遍的 query 向量缓存，`lat_off` 只测到 106ms，而线上跳过组真实要 388ms（它还欠一次 embed）——合成出来的「省 25%」是虚的，端到端只有 13.9%。脚本已改成关重排前清空 query 缓存，**延迟一律以端到端为准，离线只用来扫判据**。

落地：`rag.ADAPTIVE_RERANK_MARGIN`（默认 0.05，`WEBAPP_ADAPTIVE_RERANK_MARGIN=0` 关闭），判定在 rerank 之前，单条候选直接跳过（重排无从改顺序），词法回退路径没有向量分则**不判定**（没有依据就不省）。留痕在 `meta["rerank"]`：`skipped:margin=0.061` / `skipped:single` / `applied:external`。

## 三、`top_k` 收敛：5 条

### 3.1 `hit@k` 曲线（depth=20，200 题）

| k | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 10 |
|---|---|---|---|---|---|---|---|---|---|
| hit@k | 0.625 | 0.720 | 0.785 | 0.805 | **0.830** | 0.850 | 0.870 | 0.885 | 0.900 |
| 增量 | — | +9.5 | +6.5 | +2.0 | **+2.5** | +2.0 | +2.0 | +1.5 | +1.5 |

1→3 名贡献了绝大部分收益（+16pt），3→5 只有 +4.5pt，5→10 再 +7pt 但要付双倍上下文。

### 3.2 生成侧：5 与 10 没有差别

CMRC 2018，40 题，848 篇池，`depth=20`：

| 组 | top_k | 正确率 | F1 | 答案字数 | 上下文条数 |
|---|---|---|---|---|---|
| 旧 A（改造前） | 4 | 0.975 | 0.373 | 54.5 | 4 |
| 旧 B（改造前） | 8 | 0.975 | 0.368 | 55.8 | 8 |
| 旧 C（改造前，+阈值） | 4 | 1.000 | 0.365 | 55.3 | 1.2 |
| **G5** | **5** | **1.000** | 0.365 | 56.3 | 5 |
| G10 | 10 | 1.000 | 0.373 | 56.0 | 10 |

正确率、F1、答案长度三者几乎不动。**所以选 5 不是为了「更准」，而是同样的效果下少一半上下文**——这是成本决策，不是质量提升，报告里不该把它写成收益。

## 四、必须说清的局限

1. **抽样评估，不是官方榜单成绩。** 200 题、3000/12000 池，`seed=42`。分数不能与 `publicbench` 全量 10 万池的 33.93% 直接比较。
2. **单次运行，无方差估计。** 200 题里 1 题 ≈ 0.5pt，所以 0.7135 与 0.7090 这类差距**不能称为提升**；能站得住的只有 d10→d20 这个 4–5pt 量级的差。
3. **CMRC 的检索维度无区分度**（问题照抄原文，rank1 恒为 1.000），生成侧只验证了「top_k 不影响正确率」，没验证「检索变好会不会让答案变好」。
4. **Cmedqa 医疗语料模板化**（大量「建议去医院检查」），对语义区分度的考验可能弱于法律/技术语料。
5. **rerank 是外部服务**，分数存在微抖（同参数重跑 nDCG 差 0.0004），跨天复现会有小幅漂移。**embed 端点同样抖**：同一句话两次调用，向量最大分量差实测 0.0000～0.00253，而边界处的分数间距只有 8.04e-05，所以偶尔会出现第 20/21 名互换（20 题里 1 次，指标不受影响）。要绝对可复现只能用本地模型或固定向量快照。
6. 只测检索与生成正确率，**没测权限过滤、PII 脱敏、缓存一致性**——那些是另一套对照实验。
7. **自适应重排的跳过率是语料相关的。** 24~30% 来自「Cmedqa 口语 query vs 医疗 passage」这个分布（s1−s2 的 p50 只有 0.024）；若语料同质化、候选分数普遍更平，跳过率会掉。换 embedding 模型必须重标定 τ（间距虽尺度无关，但分布会变）。

### 复现命令

```bash
# 3000 池建库（含入库 + 向量化）
python webapp/eval_retrieval_cmedqa.py --label N1 --schema kb_conv_cmedqa \
  --doc-pool 3000 --cases 200 --top-k 10 --rerank external

# 同库复用，扫深度
for D in 15 20 25 30; do
  python webapp/eval_retrieval_cmedqa.py --label N$D --schema kb_conv_cmedqa --reuse \
    --doc-pool 3000 --cases 200 --top-k 10 --rerank external --rerank-depth $D
done

# 12000 池复核
python webapp/eval_retrieval_cmedqa.py --label M10 --schema kb_conv12k \
  --doc-pool 12000 --cases 200 --top-k 10 --rerank external
python webapp/eval_retrieval_cmedqa.py --label M20 --schema kb_conv12k --reuse \
  --doc-pool 12000 --cases 200 --top-k 10 --rerank external --rerank-depth 20

# 生成侧
python webapp/eval_chain_cmrc.py --label G5  --doc-pool 848 --cases 40 --top-k 5  --rerank-depth 20 --rerank external
python webapp/eval_chain_cmrc.py --label G10 --doc-pool 848 --cases 40 --top-k 10 --rerank-depth 20 --rerank external

# query 向量缓存：冷/暖对比 + 分段耗时（自己建池、自己 DROP）
python -m webapp.eval_query_cache_bench --docs 3000 --cases 20 --rerank external --segments

# 自适应重排：一题两遍采集 → 离线扫阈值（复用已入库的池，200 题约 4 分钟）
python -m webapp.eval_adaptive_rerank --schema kb_depth --docs 3000 --recollect
python -m webapp.eval_adaptive_rerank --schema kb_depth12k --docs 12000 --recollect \
  --records webapp/out/adaptive_rerank_12k_records.jsonl --json-out webapp/out/adaptive_rerank_12k.json

# 自适应重排：端到端（开 / 关对照）
python -m webapp.eval_retrieval_cmedqa --schema kb_depth --reuse --cases 200 --doc-pool 3000 \
  --top-k 5 --rerank-depth 20 --rerank external --keep-schema --label AD05 --no-resume
WEBAPP_ADAPTIVE_RERANK_MARGIN=0 python -m webapp.eval_retrieval_cmedqa --schema kb_depth --reuse \
  --cases 200 --doc-pool 3000 --top-k 5 --rerank-depth 20 --rerank external --keep-schema \
  --label AD0 --no-resume

# 清理
python webapp/eval_retrieval_cmedqa.py --schema kb_conv_cmedqa --cleanup
python webapp/eval_retrieval_cmedqa.py --schema kb_conv12k --cleanup
```

数据文件：`webapp/out/cmedqa_{N1,N15,N20,N25,N30,M10,M20}*.json`、`webapp/out/cmrc_chain_{G5,G10}.json`。
