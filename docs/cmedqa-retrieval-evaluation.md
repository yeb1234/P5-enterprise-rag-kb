# CmedqaRetrieval 检索链路评估（C-MTEB 公开集）

> 一句话：**换了一个真正能测检索的公开集，链路 nDCG@10 从"看不出差异"变成"看得出差异"，并量出了两个真实短板——检索延迟随池规模线性增长、rerank 深度被 top_k 绑死。**

评估日期：2026-11-18 ｜ 跑批器：`webapp/eval_retrieval_cmedqa.py` ｜ 数据：`webapp/out/cmedqa_{A..E}*.json`

---

## 1. 为什么换数据集

上一轮用 CMRC2018 测链路，结果是 Recall 全 1.000（40/40 rank=1）。查了原因：**CMRC 的问题几乎照抄原文**（"由哪两个公司合作开发"），关键词唯一，词法检索必然命中，检索维度没有区分度。

这次换成 **CmedqaRetrieval**，两者差别是决定性的：

| | CMRC2018 | CmedqaRetrieval |
|---|---|---|
| query 与金标文档的关系 | 问题抄原文，术语完全重合 | 口语 vs 医学术语，**表述完全不同** |
| 二元组 Jaccard（中位） | — | **0.024** |
| query 原文出现在金标里 | 大量 | **0 / 20** |
| 能否测出检索能力 | ❌ Recall 恒 1.0 | ✅ 有区分度 |

实例（数据集原文）：

```
Q   : 我的女儿十五岁了，没来月经，乳房也发育不好，是否需要检查治疗？
ground: 女孩儿一般十三或者十四岁左右可以出现月经。如果第二性征没有发育。
        比如乳房没有发育。就需要去医院检查内分泌情况。同时做b超检查卵巢附件…
```

同一个意思，一个说"没来月经"，一个说"十三四岁出现月经"。词法撞不上，只能靠语义——这才是"文档检索"要解决的场景。

## 2. 数据集来源与规模

| 项 | 内容 |
|---|---|
| 基准 | **CmedqaRetrieval**，C-MTEB（中文 MTEB 榜）六个检索任务之一 |
| 官方仓库 | `mteb/CmedqaRetrieval`（MTEB 官方同名镜像） |
| 下载源 | `hf-mirror.com`（国内可直连，无需代理） |
| 许可证 | 见 MTEB 数据集卡片 |
| 全量 | 100,001 passage / 3,999 query / 7,449 相关性对 |
| 标注 | 标准 `qrels`（query-id / corpus-id / score），带官方相关性判定 |

**本轮用量（seed=42 固定可复现）**：200 个 query + 其全部金标 passage（去重 364 篇）+ 随机填充干扰文档到 3000 篇（另有一组 12000 篇）。每题保证至少 1 篇金标在池内，随机基线 hit@10 ≈ 0.3%。

全量 10 万篇的向量要算约 60 分钟，对"小批量验证"不划算，故抽样。**因此本报告分数不可与 `evalfmt/publicbench` 的 33.93% 直接比较**（那套是全量 10 万池、离线纯向量）。

## 3. 指标口径

直接复用 `evalfmt/publicbench.py::metrics_for_ranking`，与已有 nDCG 报告同口径：二值相关性、`Recall@k = |topk ∩ gold| / |gold|`、`nDCG@10`、`MRR@10`。

两点必须说明，否则数字会被误读：

1. **chunk 先按 doc 去重**再算指标。一篇 passage 可能被切成多块，不去重的话一篇长文档能靠多个 chunk 霸占 top-10，那是 chunk 级虚高，不是 passage 级成绩。
2. **`Recall@k` 是多金标覆盖率**，不是"至少命中一个"。200 题里 85 题有多个金标（最多 19 个），分母是 `|gold|`，所以 `Recall@10` 天然被压低。为此报告**同时给 `hit@k`（至少命中 1 个）**——这才是用户视角的"检索到了没有"。

## 4. 五组结果

| 组 | 检索池 | top_k | rerank | nDCG@10 | hit@1 | hit@5 | hit@10 | Recall@10 | p50 | p95 |
|---|---|---|---|---|---|---|---|---|---|---|
| **A** | 3000 | 10 | **开** | **0.7079** | **0.645** | 0.835 | 0.880 | 0.8043 | 1914ms | 2185ms |
| B | 3000 | 10 | 关 | 0.6702 | 0.600 | 0.795 | 0.880 | 0.8043 | **1681ms** | 1852ms |
| C | 3000 | 10 | 关（绕门禁） | 0.6703 | 0.600 | 0.795 | 0.880 | 0.8043 | 1822ms | 2150ms |
| D | 3000 | 30 | 开 | 0.7067 | 0.620 | 0.835 | **0.895** | 0.8365 | 2264ms | 2512ms |
| **E** | **12000** | 10 | 开 | **0.5775** | 0.535 | 0.705 | 0.765 | 0.6708 | **6279ms** | 6523ms |

空召回率：五组**全部为 0.000**（200 题无一被词法门禁判空）。
检索模式：五组全部 `hybrid: lexical_gate + pgvector`，无一次 embedding 降级。

## 5. 四条结论（每条都有对照）

### 5.1 rerank 有效，且只作用于"排序"不作用于"召回"

A vs B：nDCG@10 **+3.77pt**（0.6702 → 0.7079），hit@1 **+4.5pt**（0.600 → 0.645），MRR@10 +4.44pt。

而 **hit@10 与 Recall@10 一个点都没变**（0.880 / 0.8043 完全相同）。这不是巧合，是代码决定的：

```python
hits = candidates[:top_k]      # 先截断到 top_k
if hits and rp != "off":
    ...                        # 再在这 top_k 条内重排
```

**重排只能在已经截断的候选里调整顺序，不可能把第 20 名提进前 10。** 所以它天然只能提升"排在第一的是不是对的"，不能提升"有没有检索到"。

这 3.77pt 的代价是 **+233ms（+14%）**，可以接受。

### 5.2 词法门禁在本数据上零损失——但它是"熔断器"不是"过滤器"

C 组（绕过门禁、直接全池向量排序）与 B 组（走门禁）**逐项完全相同**：0.6703 vs 0.6702、hit@1 都是 0.600、Recall@10 都是 0.8043。

根因在 `rag.retrieve` 的这句：

```python
candidates = pool if (gated and emb["kind"] != "offline") else gated
```

门禁只要有**任何**词法命中，候选集就直接放成**全池**，交给向量排序。所以门禁不参与过滤，只决定"全放"还是"全拦"（后者返回空列表 → 触发 `retrieval_empty` 拒答）。

本数据空召回 0/200，说明这个边界判断在医疗口语 query 上从未触发。**这是好消息（没有误杀），但也说明门禁在这个场景下没有起到"减少候选"的作用**——它省不了任何计算。

### 5.3 加深 rerank 深度没有收益，反而伤了 top1

D vs A：把 top_k 从 10 加到 30，让 rerank 有 30 个候选可挑——

- nDCG@10：0.7067 vs 0.7079（**-0.12pt，在 200 题的噪声范围内**）
- hit@1：0.620 vs 0.645（**-2.5pt，变差了**）
- 延迟：2264ms vs 1914ms（**+18%**）

D 的 hit@10 更高（0.895 vs 0.880）只是因为候选从 10 条变 30 条、前 10 更容易含金标，**跟重排质量无关**。

结论：**top_k=10、rerank 深度=10 是这份数据上的最优配置**，不需要解耦。加宽只会变慢并引入更多混淆候选（医疗问答大量同模板回答，候选越多越容易挑错）。

### 5.4 池规模是最大变量：3000 → 12000，nDCG 掉 13pt

E 组与 A 组配置完全相同，只把池从 3000 扩到 12000（4 倍）：

| | 3000 池（A） | 12000 池（E） | 变化 |
|---|---|---|---|
| nDCG@10 | 0.7079 | 0.5775 | **-13.0pt** |
| hit@1 | 0.645 | 0.535 | -11.0pt |
| hit@10 | 0.880 | 0.765 | -11.5pt |
| p50 延迟 | 1914ms | 6279ms | **+228%** |

**这直接说明 A 组 0.71 是小池红利，不能当作系统真实水平。** 检索难度随池规模快速增长——干扰文档越多，"看起来像"的错答案就越多。要对外说数字，必须同时说清池子多大。

## 6. 顺带量出的两个工程短板

### 6.1 检索延迟随池规模近似线性增长，瓶颈在词法门禁

| 池规模 | chunk 数 | p50 延迟 |
|---|---|---|
| 3000 passage | 3,221 | 1914ms |
| 12000 passage | 12,840 | 6279ms |

chunk 数涨 3.99 倍，延迟涨 3.28 倍——近似线性。按此外推 10 万 chunk 约 50 秒，**完全不可用**。

根因在 `rag._load_ready_chunks()`：每次检索都把**全池 chunk 文本**（12000 条 × 约 250 字）拉进 Python，逐条算二元组重叠分。向量排序那一侧早已下推 SQL（pgvector 一条 SQL 完成过滤+排序，143 候选 69ms → 2.2ms），**但词法门禁这一层还留在 Python 里全表扫描**，它现在是瓶颈。

修法方向明确（本轮未做，只写方向）：把词法命中判定下推成 SQL（`text LIKE ANY(...)` 或建 `pg_trgm` / 倒排表），只把命中集拉回 Python。按项目此前把向量排序下推 SQL 的经验（32× 提速），这一层同样有数量级空间。

### 6.2 rerank 调用深度被 top_k 绑死（已由 5.1 / 5.3 双向验证）

`retrieve` 里 rerank 与 top_k 是同一个旋钮。想做"召回 30、重排 30、只返回 10"这种标准两阶段检索，当前代码结构做不到——必须解耦 `rerank_depth` 与 `top_k`。

不过 5.3 的数据表明**在这份数据上解耦也没有收益**，所以这条是"结构上不灵活"，不是"当前有损失"。**别把潜在的改进说成已量化的收益。**

## 7. 局限（必须一并说明）

1. **抽样，非官方全量成绩**。200 query / 3000~12000 passage，与 C-MTEB 榜单（100,001 passage 全量）不可比。若要对标，需要全量入库（约 60 分钟向量 + 更高内存）。
2. **不可与 `evalfmt/publicbench` 的 33.93% 直接比较**。那套是全量 10 万池的离线纯向量打分（numpy 余弦，无链路），池大 8~33 倍、无 rerank、无词法门禁。
3. **单次运行，无方差估计**。200 题，1 题 ≈ 0.5pt。0.6702 与 0.6703、0.7079 与 0.7067 这类差异都在噪声内，**不要报"提升 0.01"**。有意义的差异只有 rerank 的 +3.77pt 和池规模的 -13pt。
4. **没有任何生成侧指标**。本报告只测检索，不测"答案对不对"。生成侧另见 `docs/cmrc-chain-evaluation.md`。
5. **医疗领域单一**。Cmedqa 是医疗问答，模板化严重（大量"建议去医院检查"式回答），对语义区分度的考验可能低于法律/技术类语料。换领域结论可能不同。
6. **R@k 口径受多金标影响**。85/200 题有多个金标，`Recall@k` 会被系统性压低，看数请看 `hit@k`。

## 8. 复现

```bash
# 首次会从 hf-mirror 拉 3 个 parquet（约 59MB）
python webapp/eval_retrieval_cmedqa.py --download

# A 组：3000 池 / top10 / rerank 开（线上真实配置）
python webapp/eval_retrieval_cmedqa.py --label A --schema kb_ret_eval \
    --doc-pool 3000 --cases 200 --top-k 10 --rerank external

# B/C/D 复用同一份入库与向量（省掉重算 3000+ 条向量）
python webapp/eval_retrieval_cmedqa.py --label B --schema kb_ret_eval --reuse --rerank off
python webapp/eval_retrieval_cmedqa.py --label C --schema kb_ret_eval --reuse --rerank off --nogate
python webapp/eval_retrieval_cmedqa.py --label D --schema kb_ret_eval --reuse --top-k 30

# 清理
python webapp/eval_retrieval_cmedqa.py --schema kb_ret_eval --cleanup
```

跑批器支持**断点续跑**（每 20 题原子落盘 partial，中断后自动跳过已完成题）。这不是过度设计：本轮 D 组两次在跑到第 25 / 75 题时 Docker Desktop 整体重启导致 PG 断连，加断点前两次共浪费 16 分钟。

## 9. 一句话总结

**这条链路的检索能力在 3000 篇池子上是 nDCG@10=0.71 / hit@1=64.5%，其中 rerank 贡献 +3.8pt；但换成 12000 篇就掉到 0.58 且延迟 6.3 秒——真正的短板不是排序质量，是检索延迟随池规模线性增长。**
