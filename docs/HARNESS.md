# YEBSPEC · 通用 Harness 开发规约

> **用途**：新建任何项目时，把本文连同「最小文件骨架」一起复制过去，10 分钟建立工程纪律。
> **来源**：从「P5 企业级知识库项目」两天高强度迭代里提炼的真实踩坑，不是通用教科书。
> **适用**：一人维护 / 学习与面试导向 / 需要频繁迭代又不能把完成度说歪的项目。
> **版本**：`YEBSPEC@1.0`（2026-11-14）

---

## 0. 三步用起来

1. 复制 `docs/HARNESS.md` 到新项目，改标题里的项目名。
2. 按 §2 建立最小文件骨架（5 个文件），把 §1 的规则编号写进 `MEMORY.md` 顶部。
3. 每次交付前跑 §4 的闸门清单；每次踩新坑就在 §6 追加一条，规则编号递增。

**核心思想只有一句**：把「完成度」和「验证证据」当成版本化资产来管理，而不是靠记忆和口头声明。

## 1. 规则总表（Y1–Y22）

每条给：规则 → 为什么 → 可验证方式。编号稳定，跨项目引用时写 `Y7` 即可。

### A. 完成度与诚实边界

| # | 规则 | 为什么 | 验证 |
|---|---|---|---|
| **Y1** | 所有能力标三态：`已实现` / `只设计` / `未做`。同义词（已落地/占位/未接通）要在文档开头列图例对照 | 不同成员的措辞差异会被读成结论冲突 | `grep -c` 三态标记，文档开头有对照表 |
| **Y2** | 禁止把「设计写了」「接口留了」「开关加了」写成「已实现」。判定标准是**有可运行代码 + 有实跑证据** | 面试 / 交付时最容易被一问就穿 | 每个「已实现」旁边要有文件路径或命令输出 |
| **Y3** | 「列出未完成」≠「本次要补完」。每期明确写 `Won't` 清单并给理由 | 范围蔓延必然导致把只设计说成落地 | 有 `## 本期明确不做` 章节 |
| **Y4** | 不知道就 `__TBC__`，不推断填写。适用：外部接口地址、鉴权、请求响应结构、配额、错误码、模型版本、价格、压测数字、P95 | 编造的字段无法核实，且会污染后续所有结论 | `grep -rn "https\?://" docs/` 只出现可核实来源；`__TBC__` 槽位集中登记 |
| **Y5** | 降级必须留痕且**不假装用了**。不可用时返回 `None` / 标 `*_unavailable`，绝不返回看起来成功的占位结果 | 假成功会让检索/评估结论建立在假数据上 | 单测覆盖「依赖不可用」路径，断言 `degraded` 非空 |

### B. 事实源与冻结区

| # | 规则 | 为什么 | 验证 |
|---|---|---|---|
| **Y6** | 每类事实指定**唯一事实源**：场景用 `scenario.json`、结果用 `out/*.json`、配置用 `effective_*()` 函数、展示页数字由脚本生成 | 手写 HTML 里的数字一定会和真实结果漂移 | 展示页生成脚本存在，且不手写数字 |
| **Y7** | 冻结区（已产生 run / 已发布基线 / 契约占位）**绝对不动**；改评分口径要 `rescore` 生成新 run，旧 run 保留前后对照 | 原地改历史会让所有对比失效 | `git diff --exit-code -- <冻结目录>/` 返回 0 |
| **Y8** | 历史日志 / 已提交条目**不回改**；状态变化用新增「最终回填」章节覆盖，原表保留追溯 | 既保证可追溯，又避免交付物里留「进行中」 | 文档里有「主理人最终状态回填」段 |
| **Y9** | 数据迁移写**显式迁移**，且数据操作用原生 SQL，不在迁移里 import 新 ORM 模型 | `env.py` 已加载新模型，ORM 读不到旧结构 | 迁移有 `downgrade` 且注明「结构可逆、数据语义不可逆」 |

### C. 配置、命名空间与缓存

| # | 规则 | 为什么 | 验证 |
|---|---|---|---|
| **Y10** | 不同子系统共用 `.env` 时，配置键**必须加前缀隔离**。同名枚举互斥会让另一个服务启动校验失败 | `extra="ignore"` 只忽略未知键，同名键仍参与校验 | 每个键有唯一前缀；启动两个子系统都成功 |
| **Y11** | 端点和模型共同决定缓存命名空间。切模型必须让旧缓存天然失效 | 维度不一致时余弦会**静默归零**，检索看似正常实则全错 | 单测断言不同模型的 `cache_key` 不同 |
| **Y12** | 缓存、进度、对象 key 按**数据性质分治**：授权快照要「旧 key 不命中」，进度快照要「key 恒定、转岗后 SSE 不断连」 | 把两类 key 用同一套规则会同时破坏安全与可用性 | 两类 key 各有独立规格与行为断言 |
| **Y13** | 状态真值落持久层，实时通道只做推送；通道失效可从真值重建 | Redis 挂了不能丢任务状态 | 有「从 PG/SQLite 重建快照」的路径 |

### D. 验证与确定性

| # | 规则 | 为什么 | 验证 |
|---|---|---|---|
| **Y14** | 判定逻辑写成纯函数 + 显式规则 + 单测，不靠运行时推断 | 规则藏在 if 里，改一处就悄悄变 | 纯函数可脱离服务单独 import 跑 |
| **Y15** | 单测**强制离线**：临时库 + 强制 offline provider + `autouse` fixture 隔离产物目录 | 否则一次测试就会消耗真实流量、污染 runs 目录 | `pytest` 全程零网络；`git status` 无新增产物 |
| **Y16** | 报「全绿」前先证覆盖，报「有问题」前先证伪自己。误报和漏报都要留痕纠正 | 本项目两轮里纠正过 6 条误报（onclick 未定义 / Dockerfile 全缺 / React 骨架不完整 / …） | 有「被实查推翻的误报」记录段 |
| **Y17** | 端到端产物若会被脚本覆盖，先备份再跑，跑完**按字节还原** | 否则真实配置下的事实源被离线结果顶掉 | `cmp -s backup report` 通过 |
| **Y18** | 迁移函数要覆盖三种输入：全新库 / 旧结构库 / **半迁移态**；用内存库验证，不写磁盘 | 半迁移态最容易静默残留旧列 | 三态单测 + 二次执行幂等断言 |
| **Y19** | 提交前跑确定性检查清单：冻结区 diff、密钥扫描、`git diff --check`、语法、全量回归 | 靠人记一定会漏 | 有一份可直接复制的命令块 |

### E. 协作与交付

| # | 规则 | 为什么 | 验证 |
|---|---|---|---|
| **Y20** | 并行成员**写文件边界互斥**；报告「已落盘」必须附 `ls -l` / `wc -c` 证据，主理人再实查一次 | 本项目出现过成员两次报告完成、文件其实从未写入 | 交付前逐个 `test -f` 核实 |
| **Y21** | 成员报告与实查冲突时，以**实查**为准，并把纠正过程写进文档留痕；不编造「已撤回」动作 | 纠正本身也是可讲的工程严谨性 | 有「主理人复核记录」章节 |
| **Y22** | 交付前过一次「伪阻断闸门」：不把可自决的活包装成「需你确认」，不把最优步藏在「如需…告诉我」里，结论自己拍板 | 缓干比没干更难被发现 | 交付消息末尾有逐项快照 |

## 2. 最小文件骨架（复制到新项目）

```
<project>/
├── README.md                      # 入口 + 文档索引 + 三态声明
├── .env.example                   # 所有配置键（带前缀），值留空
├── .gitignore                     # .env / 产物 / 缓存 / 依赖
├── docs/
│   ├── HARNESS.md                 # 本文
│   ├── CHANGELOG.md               # 版本坐标 / 改动清单 / 缺陷修正 / 验证快照
│   └── acceptance-report.md       # 可量化验收标准 + 实测回填
├── .workbuddy/memory/             # 项目记忆（不要删）
│   ├── MEMORY.md                  # 长期约定：规则编号 + 硬约束 + 目录入口
│   └── YYYY-MM-DD.md              # 每日工作日志（append-only）
└── tests/                         # conftest 强制离线 + 隔离库
```

`MEMORY.md` 顶部建议固定写：

```markdown
## 铁律（改动时别破）
- 遵守 YEBSPEC Y1–Y22（见 docs/HARNESS.md）
- 冻结区：<列出目录>，改前必跑 git diff --exit-code
- 配置前缀：<列出>，禁止扁平同名
- 三态标注：已实现 / 只设计 / 未做，不夸大
```

## 3. 开局 10 分钟检查清单

- [ ] 定位写清楚：是「上线交付」还是「学习/面试骨架」？A/B/C 档边界写进 README
- [ ] 冻结区圈出来，加进 `.gitignore` 或提交前检查命令
- [ ] 所有外部 API 未核实字段登记为 `__TBC__`，不填猜测值
- [ ] 配置键加前缀，`.env.example` 值留空，`.env` 进 gitignore
- [ ] 事实源定下来：结果 JSON / 场景 JSON / 唯一配置函数
- [ ] 测试 conftest 强制离线 + 临时库，产物目录 monkeypatch 到 tmp
- [ ] 降级路径有 `degraded` 标记与单测
- [ ] 一条端到端自测脚本（`selftest.py`），输出结构化报告
- [ ] Git 规范：type 白名单、每个逻辑版本一次提交、已发布历史不回改
- [ ] 定一条「交付前闸门」并写进 MEMORY.md

## 4. 每次交付前闸门（可直接复制）

**命令闸门**
```bash
git status --short                                  # 确认没有意外文件
git diff --exit-code -- <冻结目录>/                 # Y7
git grep -nE 'sk-[A-Za-z0-9]{20,}' -- . || true    # 密钥
git -c core.whitespace=cr-at-eol diff --check      # 注意：CRLF 仓库要带 cr-at-eol
python -m pytest -q                                 # 全量
node --check <前端文件>                             # 若有前端
```

> 踩坑记录：本项目 `index.html` / `style.css` 是 CRLF、`app.js` / `i18n.js` 是 LF，
> 且 `core.autocrlf=false`。裸 `git diff --check` 会把 CRLF 的 `\r` 误判为
> trailing whitespace，必须带 `-c core.whitespace=cr-at-eol`。

**行为闸门**（逐条扫你**整条**回复，包括最后一句）
1. 有没有把 agent 能自己查到的信息反问给用户？
2. 已识别的子问题是否全部 `executed`，有没有 `diagnosed-only` 还留着？
3. 最高价值的那一步做了吗，还是被包装成「可选 / 回头再说」？
4. 尾巴里有没有「如需…告诉我」「你定」「不阻塞」这类延后信号？
5. 结论是自己拍板的吗？数值有实跑证据吗？
6. 约束性文本里有没有给自己留开脱钩子的从句？

## 5. 常见反模式（本项目真实踩过）

| 反模式 | 后果 | 正解（对应规则） |
|---|---|---|
| 凭印象说「工作区有 `gen_dict.py`」 | 按不存在的生成器写方案，机械四步全部不可执行 | 先实查，再写步骤（Y16 / Y20） |
| 文件名 `queue.py` 放在脚本目录 | 遮蔽标准库 `queue`，TestClient 起不来 | 顶层包命名避开标准库 |
| 共享 `EMBEDDING_PROVIDER` 扁平键 | 两个子系统枚举互斥，backend 启动校验失败 | 前缀隔离（Y10） |
| 切 embedding 模型不换 cache_key | 余弦静默归零，检索全错但「看起来正常」 | 命名空间含模型名（Y11） |
| 把 `tenant_id` 机械全局替换成 `department_id` | 对象 key / 用量台账 / SSE 快照全错位 | 按数据性质分治（Y12） |
| 索引写进 `CREATE TABLE IF NOT EXISTS` 的 SCHEMA | 旧库执行时列还不存在，`executescript` 整体失败，迁移根本跑不到 | 索引移到迁移函数末尾幂等创建（Y18） |
| 推理模型 `max_tokens=24` 探活 | 6 个模型全空正文，被误归因成「推理模型专属」 | 先证伪自己再下结论（Y16） |
| 网关流末尾 `choices: []` 取 `[0]` | `IndexError` 把正常回答判成 `model_error` | 跳过空 choices |
| 429 一律退避重试 | 额度耗尽时白烧时间 | 分 `rate_limit_exceeded` / `quota_exceeded` 两类 |
| 测试 `finally` 里发恢复请求 | 恢复请求自己被刚设的限流挡下，规则残留污染后续测试 | 先清窗口再恢复（Y15） |
| 并行成员各自「已落盘」 | 实际文件从未写入，或被并发覆盖 | 主理人逐个 `test -f` 复核（Y20） |
| 把成员口头转述当成文档结论去纠正 | 编造「已撤回」动作 | 以实查为准，留痕即可（Y21） |

## 6. 从本项目带走的六条最值钱的经验

1. **把「为什么」写进代码注释**：本项目里每个非直觉设计（缓存 key 带模型名、进度 key 不带部门、索引不放 SCHEMA）都有注释解释取舍，面试时能直接指着讲。
2. **可观测即技术深度**：逐页解析轨迹、评估 run 的 config_snapshot、来源追溯卡片——把黑盒决策变成能指给人看的表，比讲概念有力得多。
3. **降级路径本身是卖点**：`PARSING_OFFLINE=1` 或外部调用失败时只输出「图片结构事实」并明确标「非视觉理解」，比硬凑一个假成功更能体现工程判断。
4. **阈值要有性质**：90:10 不是随机分流而是熔断线，正常文档 0% 触发；这样考官追问「为什么是 10%」时有依据可讲。
5. **冻结区 + 前后对照**：提示词/参数/模型每次迭代开独立分支与 run，改动不原地覆盖，旧结果保留做对照，结论可追溯。
6. **诚实边界写在最前面**：先说清哪些没做，再讲做了什么。把 A 档说成 C 档，是这类项目最容易翻车的地方。

## 7. 维护本规约

- 每踩一个新坑：在 §5 追加一行，若属新类别则在 §1 增编号（`Y23` 起），并同步 `MEMORY.md` 的编号区间。
- 规则只增不改编号；作废旧规则标「已作废，见 Yxx」而不是删掉。
- 复制到新项目时，§5 的本项目实例可以删，但 §1 规则表与 §4 闸门必须保留。

> **一句话**：让「做了什么、没做什么、凭什么这么说」在任何时刻都能用文件和命令回答，而不是靠记忆。
