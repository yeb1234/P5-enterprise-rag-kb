## 2. 入库新鲜度（Ingestion Freshness）

### 2.1 文档级元数据该有哪些

新鲜度不是「一个时间戳」，而是一组各司其职的字段。下表「本项目落点」列依据实读 `backend/app/models/knowledge.py`、`webapp/rag.py` 得出。

| 字段（英文键名） | 中文说明 | 解决什么 | 本项目落点 |
|---|---|---|---|
| `created_at` | 创建时间 | 追溯文档来源年龄 | `TimestampMixin` 已具备 |
| `updated_at` | 最近内容修改时间 | 计算文档年龄、驱动增量重建 | `TimestampMixin` 已具备 |
| `published_at` | 发布时间 | 「何时发布」，**不可**代替生效时间 | **需补齐** |
| `valid_from` | 生效起始时间 | 排除「尚未生效」的未来政策 | **需补齐**（可落 `attributes` JSONB） |
| `valid_until` / `expires_at` | 失效时间 | 硬过滤已过期内容（报价、促销、年度政策） | `documents.expire_at` **已预留** |
| `last_verified_at` | 最后核实时点 | 识别「没被改动、却已过期」；不由编辑自动推进 | **需补齐** |
| `version` / `current_version` | 版本号 | 混合版本检索、幂等 upsert、回滚与回放 | `documents.current_version`、`chunks.version_no`、`document_versions.version_no` **已预留** |
| `content fingerprint` / `checksum` | 内容指纹 | 变更检测（改标题/标签不必重嵌入）、秒传去重、答案溯源 | `documents.checksum`、`document_versions.checksum` **已预留** |
| `superseded_by` | 被谁取代 | 显式废止链，避免旧版仅靠时间被猜成「过时」 | **需补齐** |
| `document_class` | 内容类型分档 | 决定衰减率与复核周期（合规零容忍、参考 30 天、背景 90 天） | **需补齐** |
| `source_authority` | 来源权威度 | 平衡「新但低质」与「旧但权威」；见 §3.5 | **需补齐**（治理层，勿与解析 `confidence` 混用） |
| 适用范围字段 `region` / `plan` / `product` / `department` | 地区 / 套餐 / 产品 / 部门 | 决定「对谁有效」，是适用性问题而非时间问题 | `sensitivity` / `department_id` / `attributes` **部分具备** |
| `source_id` / `source_uri` | 来源标识 | 删除传播、引用回溯、受影响答案反查 | `documents.source_uri` **已预留** |
| `owner_id` | 负责人 | 过期告警能路由到人，而非无人认领 | `documents.owner_id` **已预留** |
| `indexed_at` | 最近索引时点 | 计算「源变更→可检索」的传播延迟 | `documents.indexed_at` **已预留** |
| `status` | 状态（草稿 / 已生效 / 已废止） | 「已废止」版本不得因措辞相似被召回 | `documents.status` **已预留** |

> 关键区分：`published_at`（发布时间）与 `valid_from`（生效时间）必须分开存。公开来源反复强调**不能仅凭最新时间戳推断适用性**（S3、S15、S16）。

### 2.2 新鲜度与相关性的三种组合方式

**(1) 硬过滤（hard filter，最优先）**

在向量打分**之前**用元数据排除候选：`valid_until < now` 的直接剔除、`valid_from > now` 的排除、权限 / 地区 / 版本不匹配排除。公开来源的判词是：下游再怎么 rerank 也修不好一个已经被召回进来的过期文档（S6）。硬过滤天然可解释、可审计，且与本项目 `webapp/rag.py` 的「词法门禁先挡一道」同构。

**(2) 时间衰减（time decay，软信号，需可复算）**

公开资料给出两种写法，**参数含义不同，不可混用**（S7、S8、S9）：

```
写法 A（以半衰期 H 为参数，LobeHub / TianPan 口径）：
    w(age) = 0.5 ^ (age_days / H)
    blended_score = α · cos(q, d) + (1 − α) · w(age)

写法 B（以时间常数 halfLife 为参数，MIF Spec 口径）：
    strength(t) = e ^ (−t / halfLife)
```

可复算辨析：`0.5^(t/H) = e^(−ln2 · t/H) ≈ e^(−0.6931·t/H)`。因此只有当 `halfLife = H / ln2 ≈ 1.4427·H` 时两式才等价；同样叫「half-life」，写法 B 的衰减比写法 A 慢约 1.44 倍。**落地时必须写明用哪一个、参数的单位与量纲**，否则阈值无法跨系统对齐。

**示意算例（纯算术，参数为假设值，仅用于演示公式可复算；非本项目实测、非推荐值）**：取写法 A、`H = 180` 天（公开示例中「软件文档 180 天」一档，S7）、`α = 0.8`（公开示例默认值，S7/S8）。

| 文档 | 假设 `cos` | 假设 `age_days` | `w = 0.5^(age/180)` | `blended = 0.8·cos + 0.2·w` |
|---|---|---|---|---|
| 旧文档 A | 0.90 | 180 | `0.5^1 = 0.5` | `0.72 + 0.10 = 0.82` |
| 新文档 B | 0.85 | 0 | `0.5^0 = 1.0` | `0.68 + 0.20 = 0.88` |
| 中龄文档 C | 0.90 | 90 | `0.5^0.5 ≈ 0.7071` | `0.72 + 0.1414 ≈ 0.8614` |

结论可手算复核：**相关性更高的旧文档 A（0.90）被时间衰减拉到 0.82，反被相关性略低但更新的 B（0.85 → 0.88）超过**。这正是衰减项「能翻转排序」的意义，也是它必须可由评测集校准、不能拍脑袋定 `H` 与 `α` 的原因。公开资料明确写「用评测集调，不要猜」（S7/S8：「Tune with the eval set; do not guess.」）。

按内容类型的半衰期分档（**公开经验值，非本项目实测，需用本项目真实语料校准**）：新闻 7–30 天、软件文档 180 天、内部 wiki 365 天、法规 5–10 年、医疗指南 3–5 年（S7/S8）；MIF Spec 另给 `P7D / P14D / P30D / P90D` 的 TTL 默认值并声明「非强制」（S9）。

**(3) 分层排序（tiered ranking）**

公开来源普遍建议**不要硬压成一个万能公式**（S14、S15）：先用硬规则分层（适用 / 已生效 / 权威等级 / 未废止），层内再用相关性分数排序；业务规则用硬过滤 + 分层反而比加权求和更容易向审核方解释。三层可组合为「先过滤 → 再衰减打分 → 再按权威层复核」。

### 2.3 为什么不能只按最新时间戳推断适用性

这是面试最容易被追问、也最能体现判断力的地方（S3、S14、S15、S16）：

| 反例 | 为什么「最新的赢」是错的 |
|---|---|
| 旧合同仍适用某群体 | 老客户按旧价、某地区按旧细则，时间戳旧但对该用户**仍然适用** |
| 未来生效政策 | 下月才生效的新制度 `valid_from` 在未来，今天不能执行 |
| 总部通用规则 vs 地区细则 | 今天发布的通用通知不能覆盖仍在有效期内的上海地区细则 |
| 版本 / 套餐 / 产品差异 | 「500 次/分钟」可能是 v2 套餐，v1 套餐仍按 100 次 |
| 审批状态 | 更新的草稿 / 群聊传闻比正式制度新，但权威度低、不可执行 |

根因是**双时态（bi-temporal）混淆**（S9）：`recordedAt`（事务时间，何时录入系统）与 `validFrom / validUntil`（有效时间，事实何时为真）是两个独立维度；单看 `updated_at` 只能回答「何时改过」，回答不了「对谁、在何时为真」。另有公开来源把正确性拆成三问，值得直接沿用（S3）：**相关性**（找对资料）、**适用性与新鲜度**（选对版本/范围）、**忠实度**（答案如实反映资料）——三者是不同检查，一个聚合分数会互相掩盖。

### 2.4 工业做法（可核实的公开实践）

- **幽灵向量（ghost vector）**：源文档下架 / 404 / API 版本退役后，批处理流水线常把孤立向量留在索引里数天，用户得到指向已不存在事物的「权威」答案（S1、S2、S6）。对策是把源侧消失作为可检测信号，并连带动量淘汰。
- **删除作为一等事件（delete as a first-class event）**：每一份从源语料退出的文档都必须对应一次索引删除；删除要按 `source_id` + `version` 跨检索缓存、rerank 特征缓存、答案缓存一并失效（S2、S5）。
- **缓存版本感知读取（version-aware read）**：在快速元数据存储里保存最新版本或墓碑状态，拒绝使用「文档版本已不匹配」的缓存检索结果（S5）。公开来源的判词很锋利：改 prompt 修不好一个忽略策略版本的缓存 key（S3）。
- **软删保留审计（soft delete）**：快速硬删提升移除速度，但丢失可审计性、使故障恢复更难；做法是保留软删足够久以支持回放、合规复核与跨文件修复（S5、S6）。这与本项目 `Document` / `Chunk` 继承 `SoftDeleteMixin`、向量视为可重建派生数据、每日 `reconcile_vectors` 对账（`docs/kb-capability-checklist.md` G4）**天然同构**。
- **检索语料漂移（retrieval-corpus drift）**：文档被重切分、重嵌入、轮替，同一问题本月与上月命中完全不同段落，知识库「在你脚下移动」（S1、S4）。仅监控「索引中文档年龄」不够，要看「检索结果里的文档年龄」（见 §2.5）。
- **增量索引与变更检测**：四种信号——时间戳监控、`checksum` 哈希比较、版本控制（git merge 触发）、事件驱动 webhook / CDC；公开建议「事件驱动增量 + 周期性全量重建兜底删除传播」（S1、S5、S6）。重嵌入策略应区分「元数据变更只 patch」与「正文跨 diff 阈值才重切重嵌」，避免无意义算力消耗（S5）。
- **受控传播验证**：在预发环境改一份测试文档里的独特事实，发布期望版本，测量服务路径何时开始返回它；这测的是**传播链路**而非「索引任务成功状态」（S3）。
- **可回滚版本与灰度**：新版本先入待发布 / 影子索引，用历史问题 + 冲突问题跑新旧对比，再小流量切；出错切回检索别名与版本过滤，而非临时全量重解析（S15、S16）。

### 2.5 可观测指标（只定义口径，不给本项目数值）

| 指标（英文键名） | 中文说明与口径 | 告警 / 回归用途 |
|---|---|---|
| `retrieved_doc_age_distribution` | **检索结果**中文档的年龄分布（不是索引中全量文档的年龄）；按查询类别看 top-K 是否长期来自老文档 | 语料漂移与分层失效（S2、S3） |
| `stale-hit rate` | 命中过期 / 非适用版本 / 未带适用版本的答案占比 | 新鲜度合同是否生效（S5） |
| `delete_propagation_delay` | 源侧删除 → 索引 / 各层缓存不再返回该文档的时延 | 幽灵向量、墓碑传播（S5） |
| `cache_invalidation_latency` | 版本变更 → 相关缓存失效可观测的时延 | 版本感知读取是否生效（S5） |
| `expired_ratio` | 已过新鲜度窗口的索引文档占比 | 触发重建 / 降级（S1、S2） |
| `latest_version_backed_ratio` | 由最新适用文档版本支撑的答案占比 | 用户看到的是否为当前内容（S5） |
| `golden_set_regression` | 固定金标集按周期重跑，准确率下滑即过期信号 | 回归基线（S1、S2、S20） |
| `canary_set_daily` | 金丝雀集每日 / 每周自动重跑 | 早期预警（S1） |
| `unknown_applicability_ratio` | 无法确定适用范围 / 版本的答案占比 | 避免全局均值掩盖小群体高风险策略（S3） |

> **阈值统一标注**：公开资料中出现的经验线包括——受监管数据过期占比 > 5%、一般知识 > 10% 触发重建；综合新鲜度分数 < 85% 告警、< 70% 进入降级模式；金标集 30–50 题、金丝雀集 50–200 题；参考类 30 天 / 背景类 90 天复核周期（S1、S2、S6、S20）。以上**全部是公开经验值 / 案例参考，非本项目实测，且需用本项目真实语料校准后方可使用**；本报告不设任何 SLO 数字，不写延迟 / 吞吐 / 价格（与 `docs/parsing/05` §四「成本与延迟只做定性分析」一致）。
> 另有公开来源给出「陈旧嵌入最多使检索准确率下降约 20%」「语义基线在 as-of 正确性任务上得分 0.00、加时间项后 1.00」等数字（S4、S6）——**均为公开案例数字，非本项目实测，未独立核实原始实验，仅作定性佐证**。

## 3. 事实冲突检测（Fact Conflict Detection）

### 3.1 为什么「信相似度最高的」是错的

公开来源对这一点的剖析相当一致（S11、S14、S15、S16）：当上下文里存在多个看似合理的答案时，模型的选择被与事实正确性无关的因素左右——

| 偏差 | 表现 |
|---|---|
| 位置偏差（position bias） | 上下文靠前的片段获得更高注意力；检索分数略高的旧财报排在前面就被选中 |
| 语气强弱（language strength） | 「营收 420 万」这类直陈句压过「经重述后为 680 万」这类带条件但更准确的措辞 |
| 词法重合（lexical alignment） | 与 query 用词更贴近的答案得分更高，与权威度 / 时效无关 |
| 来源信号不可见 | **来源日期、权威等级、审计状态、废止关系对向量与生成模型都不可见** |

更根本的是：向量相似度回答「像不像」，不回答「该不该信」；词嵌入甚至会把「五」和「十」判为高度相似，而关键词检索能区分（Akamai 技术文，见 §7 备注）。中文面试原题的反驳最直白：「群聊截图可能和问题一字不差，正式制度只用了另一种表达，难道要让群聊覆盖公司制度？」（S14、S15、S16）。结论：RAG 缺的不是更好的相似度，而是**检索与生成之间一个专门的冲突检测 / 治理阶段**。

### 3.2 两阶段架构与 claim 级检测

- **两阶段**：① **入库离线检测**——分歧是源材料的属性、不是用户问题的属性，不必每次查询重新发现；入库时按实体 / 主题 / 适用范围聚类，把相似片段对交给交叉编码器或规则比对，把命中的冲突**保存下来**供查询时核对（S10、S12、S15）。② **在线检索兜底**——一次检索返回多个高分片段却对同一事实给出互斥结论时，把「存在冲突」作为**正式状态**传给生成层，而不是把片段混进 Prompt 赌模型选对（S10、S15）。
- **claim 级而非文档级**：两本长手册可能大部分一致、只在一个操作限值上打架；文档级比较太粗。应抽取问题相关断言，比较其**实体 / 属性 / 值 / 条件 / 适用期**五元组，并**为每个断言保留支持片段**（S10）。
- **归一化时别抹掉条件**：单位、否定、例外必须原样保留；把句子压成短摘要常会删掉「正是解释差异的那个条件」（S10）。NLI（自然语言推理）可标注「支持 / 矛盾 / 中立」，但标签是**输入，不是自动裁决**（S10）。
- **公开建议的实现顺序**：先做受控元数据、一致过滤、版本处理、去重、claim 级引用；只有当标注事故显示简单手段仍留下实质冲突时，才上证据图 / 检测器，避免小系统背上多智能体辩论的复杂度（S10）。

### 3.3 规则级检测（确定性优先）

公开实现给出三条可直接复刻的启发式（S11）：

1. **数值冲突**：两篇主题相似、却含有**不重叠的有意义数值**即标记。为防误报，**必须过滤年份 1900–2099 与裸小整数 1–9**——否则「2023 年报」与「2024 年报」、「第 1 步」与「第 2 步」会被当成冲突。示例：`$4.2M` 与 `$6.8M` 命中，`2024` 与 `2025` 不命中。
2. **否定 / 方向词不对称（contradiction signal asymmetry）**：两篇主题相似文档在「否定词（no / not / none / 不再 / 取消）」与「方向词（increase / decrease / prior / new / 上调 / 废止）」上分布不对称即标记。示例：一份写「不再要求固定到岗」、另一份无此否定，即提示冲突。
3. **主题相似度门控（topic similarity gate）**：仅当 `topic_sim` 超过阈值才比较，避免把不相干文档乱判为冲突。公开实现用 `topic_sim >= 0.68`，并明确标注该值是**针对特定嵌入模型（all-MiniLM-L6-v2）在特定实验里校准的**（S11）——**公开经验值，非本项目实测，需换本项目嵌入模型重新校准**。

> **模型级检测的定位**：自然语言表述复杂时可用模型做「矛盾候选识别」，或让轻量模型输出结构化冲突分类；但公开来源一致强调——**模型输出只作告警线索，不自动决定谁胜出**（S10、S14、S15）。裁决必须来自可解释、可审核、可回滚的规则与注册表。

### 3.4 冲突分类（不要一刀切）

CONFLICTS 基准（arXiv 2506.08500，Google Research 等；本次经二手解读页与中文摘要页命中，见 §7 S18/S19）给出五类并为每类定义「期望的模型行为」（**以下为公开论文转述，未独立核实原文，非本项目实测**）：

| 类型 | 中文说明 | 期望行为 |
|---|---|---|
| `no conflict` | 无冲突、来源一致 | 直接自信作答 |
| `complementary` | 互补信息（各说一部分，都对但不完整） | 综合 / 多跳合成，**不要二选一** |
| `conflicting opinions` | 观点 / 研究结果分歧 | 中立并列各方，不站队 |
| `freshness` | 过时信息导致冲突 | 优先最新，并说明时间性质 |
| `misinformation` | 主动矛盾 / 错误信息（不可靠来源、未核查、投毒注入） |  disregards 低可信来源、以已核实来源为准；医疗 / 法务 / 财务需显式升级 |

另有公开来源把「互补 / 观点 / 新鲜度 / 错误信息 / 主动矛盾」并列，并强调互补型应触发「合成」而非「选择」（S12、S17）。**一刀切地「取最新」会把互补信息丢掉、把观点分歧伪装成事实裁决**（S12、S19）。

### 3.5 来源权威注册表与按簇独立裁决

- **来源权威注册表（authority registry）**：由**业务负责人**按领域定义来源等级、覆盖关系与审批流；财务 / 法务 / 产品 / 售后各有自己的效力层级。公开来源明确警告：**权威顺序不能由开发人员拍脑袋写成全公司统一常量**（S14、S15、S16）。这与本项目「`decide()` 为唯一授权真值」「配置外置」的工程取向一致，但权威度属知识治理层，不要塞进代码常量。
- **冲突图连通分量（cluster-aware recency）**：把冲突关系建成图，用 DFS 找连通分量，**每个簇独立保留时间戳最新的文档**；不冲突的文档原样通过，每个冲突簇恰好贡献一个胜者。公开实现指出：若从整个冲突集合里「只取全局最新一篇」，会误删其它独立簇里仍然有效的信息（S11）。

### 3.6 生成层契约（把裁决结果结构化地交出去）

不要给模型「一堆无序片段」让它自己和解（S10、S15）：

- **结构化 `evidence record`（证据记录）**：包含相关断言、各自支持片段、适用范围、生效期、裁决规则、**未决冲突**；原文片段与「应用指令」分开存放——检索到的材料是**不可信输入**，一段写着「忽略其它来源」的文字不得改变来源层级（S10）。
- **引用绑定到具体 claim**：段落旁挂一个引用并不能证明段内每句话都由该来源支撑；引用要绑定到它支撑的那条断言（S10）。两来源仍不兼容时**并列引用双方**、描述分歧、不混合取值。
- **无法裁决时诚实并列**：同等权威、同一适用范围且确实无法裁决，就明确写「当前知识库存在两个不同版本，A 文档规定 10 天、B 文档规定 15 天，暂无法确认哪一个有效」，附原文、请用户补充地区 / 版本、或转知识负责人审核（S14、S15、S16）。**不要让模型发明 tie-breaking（平局裁决）规则**（S10）。
- **拒答解释不能泄露受限文档**：只披露用户**有权访问**的证据；为解释拒答而暴露受限文档的标题或内容是越权（S10）。本项目 `docs/permission-model.md` 的「查询时按身份裁剪」与 `webapp/rag.py` 的检索为空拒答话术，是这条契约的现成落点。
- **只答被支持的部分**：证据只支持部分结论时，就只答那部分；不受影响的子问题仍可正常回答，未决冲突不必导致整题拒答（S10）。

### 3.7 评估与测试（把「会不会选错依据」单独考出来）

普通 RAG 测试集「一问一标准答案」测不出冲突能力，必须主动注入冲突样本（S10、S15、S16、S20）：

| 指标 | 中文说明 | 为什么要分开统计 |
|---|---|---|
| `correct_source_selection_rate` | 正确来源选择率 | 答案忠实也可能「忠实地引用了错的权威」（S10） |
| `effective_date_accuracy` | 生效日期 / 有效期判断准确率 | 单独暴露「未来生效政策被提前执行」 |
| `conflict_detection_rate` | 冲突检出率（含离线入库与在线检索） | 检测与裁决是两件事 |
| `citation_support` | 引用支持率（每条关键结论是否被所引证据支撑） | 段落级引用会掩盖断言级错误 |
| `unnecessary_abstention` | 无谓拒答率 | 与「缺失证据」「未决冲突」「权限拒绝」「无依据生成」**分开统计**，一个聚合拒答率会掩盖不同工程问题（S10） |

**必测的鲁棒性用例**（S10、S16）：
- **证据重排不应翻转结论**：改变片段顺序后模型不应改口（针对位置偏差）。
- **重复副本不应改变结果**：同一来源被重复灌入多份不应因「票数多」而胜出（语料不均衡测试）。
- **适用范围用例**：旧政策对某一群体仍有效、明天才生效的政策、缺失地区、两份同等权威材料冲突、源更新后缓存仍存活。
- **保留来源快照**：回归用例要连同当时的来源快照一起保存；拿今天可变索引重放，会掩盖原始故障或造出一个不同的故障（S3）。
- **线上记录**：答案引用过哪些 `source_id` 与版本；某文档被判有误时可反查受影响的历史答案（S16）。

> 评测框架参照：RAGAS 四指标（faithfulness / answer_relevancy / context_precision / context_recall）与「golden set 含语料外问题以测拒答路径」「CI 质量闸门」（S20）。公开阈值（如 faithfulness ≥ 0.90、context_recall ≥ 0.85）**是公开经验值，非本项目实测，需用本项目真实语料校准**；且本项目 `docs/kb-capability-checklist.md` 已明确 `eval/` 占位结果 `comparable=false` / `NOT_COMPARABLE` 不参与闸门，本报告不改动该口径。

## 4. 面试考点小节

> 以下 8 题均可在面试现场按「先纠问题 → 给裁决顺序 → 补工程闭环 → 收在诚实边界」的节奏作答。数字与阈值一律不报实测。

**Q1（中文原题）「知识库两份文档互相打架，RAG 信谁？」**

| | 答法 | 为什么 |
|---|---|---|
| ✗ 错误 1 | 「信向量相似度最高的那份」 | 相似度只说明「像不像」；群聊截图可能与问题一字不差却只是传闻，正式制度换了种表达就被盖过（S14/S15/S16） |
| ✗ 错误 2 | 「永远信发布时间最新的」 | 总部今天发的通用规则，覆盖不了仍在有效期内的上海地区细则；下月才生效的制度今天不能执行（S15/S16） |
| ✗ 错误 3 | 「把两份都给大模型，让它自己判断谁可信」 | 没给权威等级、版本状态、适用范围，模型拿什么判断？生产系统不能把知识治理责任甩给一次随机生成（S16） |
| ✓ 正确 | **先判断适用性，再比较权威度 / 版本状态 / 生效区间，最后才在合格候选里用相关性排序** | 这是可解释、可审核、可回滚的治理规则，而不是「选哪段文字」（S14/S15/S16） |

正确答法的完整闭环：入库存 `source_id` / `owner` / `version` / `status` / `published_at` / `valid_from` / `valid_until` / 适用范围 / 原文 / 文档 hash / 审批记录 → 检索先按用户、地区、产品、时间、权限**硬过滤**再召回排序 → 离线 + 在线双阶段冲突检测 → 生成逐条引用证据 → 无法裁决时**诚实并列两版本 + 原文 + 转人工**，不偷偷二选一 → 灰度索引 + 可回滚版本 → 用含旧版本、地区规则、低权威干扰文档的测试集专项评测。收尾可加一句：「这道题表面问模型选哪段，实际考知识库有没有一套能解释、能审核、能回滚的知识治理规则。」

**Q2「新鲜度怎么和相关性结合？半衰期怎么定？」** —— 三层：硬过滤（已过期 / 未生效 / 不适用直接排除）→ 时间衰减软信号（`w=0.5^(age/H)`，`blended=α·cos+(1−α)·w`）→ 分层排序（按权威层复核）。`H` 与 `α` 按内容类型分档、必须用评测集校准，不猜；并要点破 `0.5^(t/H)` 与 `e^(−t/halfLife)` 参数量纲不同、差约 1.44 倍（§2.2）。

**Q3「为什么不能只看最新时间戳？」** —— 双时态：事务时间 ≠ 有效时间。举三个反例：旧合同仍适用某群体、未来生效政策、地区 / 版本 / 套餐适用条件（§2.3）。

**Q4「幽灵向量是什么？文档删了为什么答案还在？」** —— 源侧删除后向量索引残留孤立向量；要把删除当一等事件，按 `source_id` + `version` 跨索引 / 检索缓存 / rerank 缓存 / 答案缓存传播失效，用墓碑 + 软删保留审计与回放，最终一致性 + 每日差集对账（§2.4）。

**Q5「冲突检测为什么做到 claim 级，不做文档级？」** —— 两本手册可能只在一个限值上打架；按实体 / 属性 / 值 / 条件 / 适用期抽取断言、保留支持片段，归一化时别把「否定 / 单位 / 例外」压掉（§3.2）。

**Q6「数值冲突规则怎么防误报？」** —— 过滤年份 1900–2099、裸小整数 1–9；再用否定 / 方向词不对称 + 主题相似度门控；门控阈值随嵌入模型变化，须重新校准；模型只出告警线索，不自动裁决（§3.3）。

**Q7「两份同等权威、同一范围，实在裁不了怎么办？」** —— 诚实并列两个版本 + 各自原文与生效日 + 请用户补地区 / 版本 + 转人工；不发明平局规则；不受影响的子问题照常答；拒答解释只披露用户有权访问的证据，不泄露受限文档标题（§3.6）。

**Q8「怎么评测冲突处理，怎么防止『看起来对』？」** —— 正确来源选择率、生效日期准确率、冲突检出、引用支持、无谓拒答**分开统计**；必测「证据重排不翻转结论」「重复副本不改变结果」「保留来源快照」；答案忠实度高也可能选错权威，别用一个聚合分数掩盖（§3.7）。

> 补充可问：`来源权威注册表谁维护？`（业务负责人按领域定义，不是开发写全局常量，§3.5）；`冲突要不要一律取最新？`（不，互补要合成、观点要并列、错误信息要升级，§3.4）。

## 5. 对本项目可落地的建议

### 5.9 与 `parsing/` 三级策略、90:10 预算闸门如何共存（不互相打乱口径）

1. **状态图例各管各的**：本报告三态（§0.1）只判断这两个新需求的落地程度；`docs/parsing/01–07` 的「已实现 / 只设计 / 未做」、`docs/kb-capability-checklist.md` 的四档，均**原样保留**，不换算、不覆盖。§5 表里凡描述既有能力，用「已在 / 已预留」等原义措辞，不把「架构预留」写成「已具备基础」的等价物。
2. **下游契约零改动**：`parsing/` 的 `ChunkSpec(page_no, section_path, block_type, confidence, source_level, parent_seq)` → `chunks` 表 / Milvus / 引用，是 01 篇明确「完全不动」的边界。本报告的新增元数据优先落 `Document` / `DocumentVersion` 既有预留字段与 `attributes` JSONB，**不新增解析侧字段、不改 `ChunkSpec`**，因此 P0 / P1 / P2 三级策略与质量门禁 `needs_upgrade` 逻辑无需改动。
3. **90:10 的性质与量纲不动**：`VISION_ESCALATION_RATIO = 0.10` 是**解析阶段「最贵链路最多占 10% 页」的熔断线**（`slots = max(1, ceil(页数 × 0.10))`），不是随机分流（05 篇 §1）。本报告的 `H` / `α` / 过期占比告警线 / `topic_sim` 门控属于**检索与入库治理层**，与解析页数**不同量纲、不复用同一常量、不合并成一个「预算」**。若未来冲突检测的模型级识别需要调用 LLM，其调用量应**另立闸门**，不得悄悄从 90:10 名额里扣，也不得把 `escalation_budget_exceeded` 复用成冲突检测的超限标记。
4. **同名不同义要隔开**：`source_level`(L1/L2/L3) 与 `confidence` 是**解析质量信号**；`source_authority` 是**知识治理层的权威等级**；`checksum` 是内容指纹、`version` 是版本标识。三者语义不同，禁止互相顶替或改名复用，否则口径即被打乱。
5. **`eval/` 冻结口径不被绕过**：05 篇明确「三态是讲解用图例，与 `eval/` 的 `__TBC__` / `NOT_COMPARABLE` / `real_api` 阻断口径相互独立，不改动、不绕过」。#8 的金标 / 金丝雀集是**新增评测数据**，只能以版本化对象新增，不能改动冻结对象、不能让占位结果参与闸门。
6. **诚实边界一致**：05 篇「成本与延迟只做定性分析，不写价格、不写 P95 / 吞吐 / 耗时实测数字」「阈值均为演示默认、需真实语料校准」；本报告 §2.5 / §0.3 完全沿用——只给指标口径，不给本项目数值，不设 SLO。
