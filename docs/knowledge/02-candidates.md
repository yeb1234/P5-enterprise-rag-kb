## 0. 定位、口径与判定依据

### 0.1 三态纪律（全文逐条遵守）

项目严格区分「**已实现 / 只设计 / 未做**」三态，本文每个候选只给一个主三态标签，并在标签后用实查证据说明边界。含义：

- **已实现**：仓库里能指到可运行的代码/表结构/接口，且已在演示链路中生效；若只是演示级替身，必须标注「（演示级）」。
- **只设计**：有字段、注释、设计文档、插件边界说明或架构预留位，但没有可运行的该功能逻辑。
- **未做**：连字段和预留位都没有，或虽有同名概念但属于另一能力，不能算作本功能已落地。

强调：**「纳入本期」只代表建议进入本期工作范围，绝不表示已实现**。本文不产出任何实测数字、价格、接口地址；所有「可量化验收方式」均为待执行的断言条件，不是跑出来的结果。

### 0.2 本期裁决三档

- **纳入本期**：建议本期做，优先选能在前端可视化、能用自建样本证明技术深度的能力。
- **只写设计**：本期只补设计说明与接口约定，不落码，通常因为成本偏高或依赖尚未就绪。
- **留在本期之外**：属于 A/B 档上线级事项或超出演示切片范围，明确不做，也不写成已完成。

### 0.3 契合度 / 成本判定口径

- 契合度「高 / 中 / 低」必须指到具体已有文件或字段（如 `chat_sources`、`parsing/`、`backend/app/services/version.py`），不写抽象口号。
- 成本「高 / 中 / 低」按演示切片口径估算：能复用已有表/函数且不动冻结区为低，需要新增链路但仍单库单进程为中，需要跨服务、外部依赖或迁移为高。

## 1. 联网检索确认的 2025–2026 高频考点

按团队要求做 4 次 WebSearch（检索日期均为 2026-11-14），中英文各覆盖，确认下列方向确实是当下企业 RAG / 知识库与面试的高频考点。可核实 URL 集中列于 §6，本节只归纳考点，不写实测数字。

1. **数据新鲜度与「失效/删除是一等公民」**：源站改版、文档删除后向量库没同步，系统照样自信地拿旧内容作答；要求按 `content hash + 修改时间` 做增量、幂等、可恢复的索引，并显式建模有效期与「谁覆盖谁」。（检索 1、检索 3）
2. **事实冲突与版本并存**：2024 版与 2026 版制度同时在库，余弦相似度不表达哪份有效；要求上下文组装阶段就解析重复版本、标记冲突，并按生效日期或权威层级给出可见、可测的裁决。（检索 1、检索 3）
3. **引用可验证 / 逐句 grounding / 弃答**：答案末尾挂个文档名是「装饰性引用」；要求把证据标识写进生成契约，答案拆成原子声明（atomic claim）逐条用忠实度判断器核对所引原文，证据不足就弃答。（检索 3、检索 4）
4. **近重复去重**：同一政策被多部门各传一份、仅页眉不同，静默降级不抛错；工业流水线普遍在清洗切块阶段用 MinHash LSH 丢掉近似重复段落。（检索 3）
5. **查询改写与多跳分解**：口语问法与文档措辞不一致、多跳问题需要拆子问题；HyDE、step-back、query expansion、RRF 融合是常见追问点。（检索 2、检索 3）
6. **评估与回归**：金标问题集、逐句忠实度 / citation accuracy / recall@k、LLM-as-judge 需与人工标定对齐、每次改动跑回归集；漂移靠检索分数分布、拒答率、用户反馈三类信号发现。（检索 1、检索 4）
7. **治理与合规**：PII 在入库前脱敏（redact before index）、日志里不能写敏感原文、ACL 在召回前过滤、答案与提示词缓存随删除/改版失效、索引版本化与金丝雀放量。（检索 3、检索 4）
8. **文档质量门控**：零字节文件、OCR 置信度低、提取不完整、内容密度不足的文档不会报错但会静默拉低检索质量；需要在摄取上游做质量评分与隔离队列。（检索 4）

结论：用户点名的「入库新鲜度 + 事实冲突检测」正处在第 1、2 条的核心位置，下面 14 个候选是围绕它俩向外延伸、且同样高频的能力。

## 2. 候选功能清单（14 项，统一结构）

每个条目固定 7 个字段：编号与名称、解决什么问题、面试官会怎么追问、与本项目契合度、实现成本、现状三态、本期裁决。名称给中文名 + 英文术语，英文键名首次出现均配中文说明。

### C01 近重复与文档去重（Near-duplicate Detection / MinHash · SimHash · 内容指纹 fingerprint）

**解决什么问题**：同一份《差旅报销办法》被三个部门各上传一次、仅页眉与落款不同，检索时三段几乎一样的内容同时进上下文，模型把旧标准和新标准混着引用，答案自相矛盾——这类「伪冲突」不去重就没法干净地做冲突检测。

**面试官会怎么追问**：① 精确去重和近重复去重差在哪，为什么 `sha256` 不够、要上 MinHash LSH？② 相似度阈值怎么定，误删唯一文档怎么办，去重要不要留审计痕？

**与本项目契合度**：高。`Document.checksum`（全文 `sha256`，`backend/app/models/knowledge.py:89`，带索引）、`DocumentVersion.checksum`（`knowledge.py:133`）和 `version.py:25` 的 `_checksum()` 已提供精确指纹与幂等基础；`Chunk`（`knowledge.py:141`）有 `seq`（分块序号）与 `version_no`（版本号）可承载分块级指纹。缺的只是 LSH 签名与判定逻辑。

**实现成本**：中。签名计算与指纹落库是增量工作，但要处理中文文本归一化、`parsing/` 三级解析产物（`source_level`，L1/L2/L3 解析层级）的对齐，以及「误删可回滚」，演示级可控、生产级不轻。

**现状三态**：**未做**（近重复检测）。精确内容指纹 `checksum` 已实现，但只用于版本快照校验与幂等，属另一能力，不能算近重复已落地；`observability.py` 的 `PLUGINS` 中无去重插件。

**本期裁决**：**纳入本期**。冲突检测最容易被「同一文档的重复副本」伪触发，先去重能让冲突判定干净；且能用自建样本在前端画相似度矩阵，技术深度可见。

### C02 引用可验证性与逐句 grounding（Citation Verifiability / Claim-level Grounding）

**解决什么问题**：回答末尾挂一个文档名，但点开原文发现那段根本没说这句话；面试官一句「怎么证明不是编的」就答不上来，尤其当两版制度冲突时，整段级引用无法说明答案到底采信了哪一版。

**面试官会怎么追问**：① 事后贴引用和「生成契约里就绑定证据 ID」差在哪？② 原子声明怎么拆，忠实度判断器（faithfulness judge）误判了怎么办，弃答阈值怎么校准？

**与本项目契合度**：高。`webapp/db.py:84-99` 的 `chat_sources`（问答来源追溯表）已落 `doc_id` / `chunk_id` / `chunk_idx` / `snippet` / `score` / `retrieval_mode`（检索方式）/ `rerank`（重排标记）/ `chunk_text`（命中分块全文），是引用链的真值载体；`webapp/routers_chat.py` 有 SSE 流式与来源卡片；`eval/compare_runs.py:24` 已有 `has_citation_marker`（是否带引用标记）指标位。

**实现成本**：中。需把答案按句拆成 claim、逐条回连 `chunk_text` 做蕴涵判断，并扩展 `chat_sources` 表与来源卡片前端；不动冻结区即可完成演示级。

**现状三态**：**只设计**（claim 级）。`observability.py:534-536` 的 `citation` 插件自述「已落地」但边界写明「只到分块级引用；未做答案逐句 grounding / 高亮定位」——分块级已实现，逐句 claim 级未做。

**本期裁决**：**纳入本期**。冲突检测的对象是「声明」而不是整段答案，只有把答案拆成原子声明、逐条挂引用，才能逐条比对矛盾；前端逐句高亮是最直观的演示面。

### C03 答案自洽性检查（Self-consistency / 多次采样投票与自我验证）

**解决什么问题**：同一个含冲突证据的问题，温度调高时模型这次说按旧办法、下次说按新办法，单次生成看不出不稳定，用户却已经拿到一个随机答案。

**面试官会怎么追问**：① 多次采样投票和「让模型自己复核证据」各解决什么，为什么不能只靠调低温度？② 多采样把 token 成本翻几倍，怎么和预算闸门共存、什么时候该直接弃答？

**与本项目契合度**：中。`docs/agent-extension.md:17` 的节点链 `guard → retrieve → permission_filter → assemble → generate → verify → persist` 里已有 `verify`（校验）节点的设计位；`webapp/providers.py` 已有非流式补全能力，可作为第二次调用通道。但 `routers_chat.py` 当前是单次生成。

**实现成本**：中偏高。多次采样会直接放大成本与延迟，且要给出可解释的「一致 / 不一致」判据，容易与三维限流、预算口径打架。

**现状三态**：**未做**。`verify` 只出现在设计文档的节点链里，仓库无多次采样或自我复核的可运行逻辑。

**本期裁决**：**只写设计**。它是很好的面试谈资，但演示收益不如 C02 直观，且会引入成本口径争议；本期把「自校验」作为 C02 忠实度判断的一个可选档位写进设计即可。

### C04 检索可解释性（Retrieval Explainability / 为什么召回这段 · 分数拆解）

**解决什么问题**：面试官问「为什么是这段排第一」，只能答「向量相似度最高」；新鲜度降权、冲突标记、rerank 到底各自出了多少力完全看不见，演示时无法把治理逻辑讲透。

**面试官会怎么追问**：① 词法门禁、向量分、rerank 分三段各自量纲不同，怎么摊开又不误导人？② 降级回退（embedding 不可用）时，前端怎么如实标注而不是假装用了向量？

**与本项目契合度**：高。`webapp/rag.py:261` 的 `search_debug()` 已经把「召回门禁 → 向量排序 → rerank / 降级」摊开，返回 `terms`（词法命中词）、`indexed_chunks`（已索引分块数）、`eligible_chunks`（可召回分块数）、`hit_count`、`retrieval_mode`、`fallback_reason`（回退原因）、`rerank`、`embedding`；`chat_sources` 也存了 `retrieval_mode` / `rerank`。

**实现成本**：低。`rag.py:243-251` 目前每条命中只输出一个最终 `score`，缺的是把 `_lex_score` / 向量分 / `_rerank` 三路分数分别带出并在前端分列展示，属于在已有调试页上加字段。

**现状三态**：**已实现（演示级）**（三阶段可解释）。逐 hit 的分数拆解未做，属同一能力的深化，不是另一功能。

**本期裁决**：**纳入本期**。它是 C01/C02/C11 的「放大镜」——新鲜度降权、引用核验、as-of 过滤做得对不对，全靠这张调试页摊开给人看；成本最低、可视化最省力。

### C05 查询改写与分解（Query Rewriting & Decomposition / 多跳 · Step-back · HyDE）

**解决什么问题**：员工问「去年那个报销新规现在还作数吗」，口语问法与文档里「差旅费用管理办法（2026 修订）」对不上，词法门禁直接判不相关而空召回；多跳问题（先查哪份文件、再查有效期）单次检索也拼不出答案。

**面试官会怎么追问**：① HyDE（假设性文档嵌入）和 step-back（退一步提问）分别适合哪类失败？② 改写后要不要把原问句一起检索，怎么防止改写把「不相关」硬凑成「相关」？

**与本项目契合度**：中。`webapp/rag.py:181` 的 `retrieve()` 直接用原问句 `_lexical_terms()` 生成词法门禁词，改写会动到「不相关不硬凑」这条核心口径；`providers.py` 有可用 LLM 通道，改造点集中。

**实现成本**：中。单次改写好做，多跳分解要引入子问题循环与结果归并，且必须证明没有破坏词法门禁的拒答语义。

**现状三态**：**未做**。`rag.py` 无改写、无分解、无 HyDE；`PLUGINS` 无对应项。

**本期裁决**：**只写设计**。它主要提升召回效果，而用户重点是演示技术深度、不是调效果；且与词法门禁口径有冲突风险，本期先给接口约定与「改写不绕过门禁」的约束说明。

### C06 增量索引与失效重灌（Incremental Indexing / 只重算变化的分块）

**解决什么问题**：文档改了一个段落，系统把整篇重新解析、重新嵌入，既慢又贵；或者反过来，改了却没重灌，`indexed_at`（索引时间）还停在旧值，答案继续引用过期段落。

**面试官会怎么追问**：① 整篇删旧块重灌 vs 分块级 diff 只更新变化块，各自的正确性与代价？② 怎么保证增量、幂等、可恢复三性，chunk hash 怎么和切块确定性绑定？

**与本项目契合度**：高。`version.py:4` 注释明确写「编辑文档不是 UPDATE 一行……触发增量重索引」；`Document` 预留 `indexed_at`（`knowledge.py:105`）、`current_version`（:93）、`checksum`（:89），`Chunk.version_no`（:151）与 `UniqueConstraint(document_id, version_no, seq)`（:167）已能定位「哪版哪块」；`version.py:71` 的 `compare()` 已有行级 diff 可复用思路。

**实现成本**：中偏高。行级 diff 到「分块级 diff」需要切块确定性保证，还要处理 Milvus 侧删旧块/写新块与 `indexed_at` 回写，演示切片里可用 SQLite + 本地向量替身，但链路不短。

**现状三态**：**只设计**。`observability.py:528-530` 的 `cache` 插件只做「按 `provider:模型` 隔离的分块向量缓存」，注释里的「增量重索引」是设计意图，无分块级 diff 重灌的可运行逻辑。

**本期裁决**：**只写设计**。它与新鲜度是同一问题的两面，值得讲；但本期优先把「新鲜度判定 + 冲突检测」做出来，增量重灌作为其失效动作的设计附录，不单独落码。

### C07 数据血缘与审计（Data Lineage & Provenance：回答 → 版本 → 解析策略 → 原始文件）

**解决什么问题**：审计问「这条回答依据的是哪一版、用哪套解析策略、来自哪个原始文件」，系统只能翻到「某文档某分块」；一旦两版制度冲突，无法说明答案采信的是哪一版，也无法复现事故。

**面试官会怎么追问**：① 血缘链要记到哪几层才够复现一次错误回答？② 只追加审计（append-only）和版本快照怎么配合，为什么不直接改历史记录？

**与本项目契合度**：高。四层材料分散但都在：`chat_sources`（`db.py:84`，回答→分块）、`DocumentVersion`（`knowledge.py:123`，不可变版本快照 + `restore()` 回滚，`version.py:108`）、`audit_logs`（`db.py:123`，只追加审计台账）、`parsing/strategies/`（三级解析策略）与 `Document.source_uri`（`knowledge.py:86`，原始文件对象键）。缺的只是把它们串成一条可查询的链。

**实现成本**：中。主要是补一张血缘关联表与一个「按 msg_id 回放整链」的查询，前端画链路图；不改冻结区、不动已有表语义。

**现状三态**：**只设计**。四层数据各自已实现，但「回答 → 版本 → 解析策略 → 原始文件」的串联与回放接口未做；`audit_logs` 注释（`db.py:122`）也自述「生产里还要接 trace_id、留存与脱敏策略」。

**本期裁决**：**纳入本期**。它是新鲜度与冲突检测的「地基」：冲突判定必须回答「哪两个版本、经过哪种解析、来自哪个原文件」，否则只是黑盒字符串比对；前端血缘链可视化 + 自建冲突样本最能体现工程深度。

### C08 文档质量分与低质量文档降权（Document Quality Score & Down-weighting）

**解决什么问题**：扫描件 OCR 只识别出半页、表格被切成乱码，这类文档不会抛异常，照常入库并可被检索，静默地把错误片段塞进上下文；面试里常被问「为什么管线不报错但答案变差」。

**面试官会怎么追问**：① 质量分用哪些信号（OCR 置信度、提取完整度、内容密度、编码有效性），阈值怎么定？② 低质量文档是打标签降权、进隔离队列，还是直接丢弃，三者怎么选？

**与本项目契合度**：高。`Chunk.confidence`（`knowledge.py:163`，分块置信度，默认 1.0）、`Chunk.source_level`（:161，L1/L2/L3 解析层级）、`Document.error_message`（:108）、`page_count` / `chunk_count`（:106-107）已是天然的质量信号位；`parsing/` 的三级解析升级本身就是置信度来源。

**实现成本**：中。计算与落库不难，难在「降权」要接进 `rag.py` 的排序且不破坏词法门禁口径，还要给出可解释的分数展示位。

**现状三态**：**只设计**。字段全是预留位（`confidence` 默认 1.0，无计算逻辑），`PLUGINS` 无质量分插件；`observability.py` 未列此项。

**本期裁决**：**只写设计**。与新鲜度/冲突检测相关（低质量解析常是「假冲突」来源），但独立成功能会稀释本期主线；先在 C07 血缘链里把 `source_level` / `confidence` 展示出来，评分与降权留设计。

### C09 敏感信息 / PII 在检索与日志中的脱敏（PII Redaction in Retrieval & Logs）

**解决什么问题**：合同里的身份证号、手机号随分块一起被嵌入并能在来源卡片里点开，`chat_logs` / `audit_logs` 又把含敏感原文的问答写进日志；一旦演示投屏或日志导出，合规红线当场被踩。

**面试官会怎么追问**：① 为什么必须「入库前脱敏」而不是「展示时打码」？② 检索日志、提示词、答案、审计台账四处各要脱敏到什么粒度，重标识映射（re-identification map）放哪？

**与本项目契合度**：中。`Document.sensitivity`（`knowledge.py:91`，敏感度）、`KnowledgeBase.default_sensitivity`（:47）、`Chunk.acl`（:162，段落级 ACL 预留位）已有分级概念；`webapp/db.py` 的 `chat_logs` / `audit_logs` 是明文文本列，脱敏要动到写入侧。

**实现成本**：中。规则级脱敏（正则 + 占位符）演示可控，但要做到检索、日志、来源卡片、导出四处一致且不破坏 `chunk_text` 的引用可核验性，需要通盘改写入链路。

**现状三态**：**未做**。`observability.py:546-548` 的 `guardrails` 插件 `status` 明确写「未做」，边界写「输入输出审核、越权内容拦截、审计脱敏检索均未完成」；`README.md:236` 把「PII 入库/召回/输出同规则」列为 P1 未来项。

**本期裁决**：**留在本期之外**。规则级脱敏本身不难，但「四处一致 + 合规口径」属于 A/B 档上线级事项，演示切片里做一半反而容易被追问成漏洞；本期只在 §4 不做清单中如实登记。

### C10 反馈闭环（Feedback Loop：badcase → 语料修正 → 回归集）

**解决什么问题**：用户点「答案有误」之后，badcase 进了台账就没人管，同一错误下周照样复现；面试常问「收集了反馈之后系统到底哪里变了」。

**面试官会怎么追问**：① 一条 badcase 要经过哪几步才算闭环，谁来决定改语料还是改提示词？② 修正后怎么证明没把别的问题改坏，回归集从哪来？

**与本项目契合度**：高。`webapp/db.py:103-118` 的 `badcases` 表有 `verdict`（判定结果）、`issue_desc`（问题说明）、`status`（pending/in_review/resolved）、`source`（chat/manual/eval）；`webapp/routers_badcase.py`、`routers_evaltest.py` 与评估工作台已能采集与查看；`observability.py` 的 `eval_gate` 插件有「版本化对象与前后对照」。

**实现成本**：中。采集与查看已现成，缺的是「resolved → 触发语料修正 → 把该问题沉淀成回归样本」的串接与状态机。

**现状三态**：**已实现（演示级，部分）**。badcase 采集、标注、评估工作台已落地；「语料修正 → 回归集」自动串接未做，`observability.py:537-539` 也写明「闸门接 CI、阈值冻结、质量基线仍未做」。

**本期裁决**：**只写设计**。闭环的最后一公里依赖回归集与基线冻结，而后两者是 §4 明确不做项；本期把「一条 badcase 如何变成一条回归样本」写成设计，不落码、不碰冻结区。

### C11 知识时效 as-of / 时间旅行查询（As-of Query / Time-travel Retrieval）

**解决什么问题**：法务问「按 2025-06-01 生效的版本，这条报销规则当时怎么规定的」，系统只会拿当前库里最新的段落作答；同一个问题在不同时间点答案本应不同，却无法复现历史口径。

**面试官会怎么追问**：① as-of 过滤放在召回前还是召回后，和 `expire_at`（失效时间）怎么配合？② 版本快照不可变和「时间点回放」是什么关系，回滚（restore）为什么必须是追加新版本而不是改历史？

**与本项目契合度**：高。`Document.expire_at`（`knowledge.py:104`）、`indexed_at`（:105）、`current_version`（:93）已预留时效字段；`DocumentVersion`（:123）是不可变快照，`version.py:108` 的 `restore()` 明确「回滚不是改历史，而是把旧内容作为新版本追加——审计链不断」，正是时间旅行需要的语义。

**实现成本**：中。需要在检索前按 as-of 时间筛选有效版本、并把「查询时间点」写进 `chat_sources` 以便回放；演示切片里可用自建的多版本样本直接证明。

**现状三态**：**只设计**。时效字段与不可变版本快照已实现，但按时间点过滤与回放未做；`PLUGINS` 无 as-of 项。

**本期裁决**：**纳入本期**。它与「入库新鲜度」是同构的对偶能力（一个管「现在还有效吗」，一个管「当时是什么样」），复用已有字段与版本快照，前端做一条可拖动的时间轴就能把深度讲透。

### C12 适用性元数据（Applicability Metadata：地区 / 套餐 / 产品版本）

**解决什么问题**：「华东区企业版 V3」的资费条款和「华北区基础版 V2」混在同一索引里，员工不问地区也照样召回别的区条款；部门维度管不到「这条知识适用于谁」，答案看着有引用、其实用错了对象。

**面试官会怎么追问**：① 适用性元数据过滤和权限过滤（ACL）有什么区别，能不能合并？② 元数据过滤放在向量相似度之前还是之后，为什么换顺序要重建索引？

**与本项目契合度**：中。`Document.attributes`（`knowledge.py:94`，JSONB 自定义属性 + GIN 索引 :116）就是为这类键值预留的；`visibility`（:44）、`sensitivity`（:91）、`department_id`（:81）、`KnowledgeBase.visibility` 已有分级别概念。生产骨架里字段齐、演示切片里 `documents` 表（`db.py:49`）很薄，需要补列。

**实现成本**：中。字段已有，缺的是「查询侧携带适用性条件 → 召回前过滤」的贯通，以及演示切片 SQLite 侧补元数据列。

**现状三态**：**只设计**。`attributes` 是预留位，无地区/套餐/产品版本的取值规范与过滤逻辑；`permission` 插件（`observability.py:540-542`）也自述「行级 ACL 未实现」。

**本期裁决**：**留在本期之外**。它更接近「部门/权限口径」这条已经做过专项变更的范围，本期再动容易打乱既有维度口径；作为 C07 血缘链里的一个展示字段提及即可，不单独立项。

### C13 答案缓存的版本感知失效（Version-aware Cache Invalidation）

**解决什么问题**：某问题的答案被缓存后，依据的文档改版或删除了，用户再问仍拿到旧答案；新鲜度做了半天，却败在一个没失效的缓存上。

**面试官会怎么追问**：① 缓存键该由哪些维度组成（问题、语料版本、检索配置、模型）？② 文档改版 / 删除 / 解析策略切换，分别该失效哪一层缓存，怎么避免「全量清空」这种粗暴做法？

**与本项目契合度**：中。`observability.py:528-530` 的 `cache` 插件已实现「分块向量缓存 `chunk_embeddings`，按 `provider:模型` 命名空间隔离」，注释点出「换 embedding 模型后旧向量怎么办」；`Document.current_version` / `indexed_at` 可作为失效信号源。但答案级缓存本身没有。

**实现成本**：中。答案级缓存要先有，才能谈「版本感知」；且失效事件要接到 C06 的增量重灌/删除动作上，跨两处链路。

**现状三态**：**未做**（答案级缓存与版本感知失效）。`chunk_embeddings` 的分块向量缓存已实现，但 `observability.py:529` 边界明确写「未做答案级语义缓存与缓存串部门治理」。

**本期裁决**：**只写设计**。它是「新鲜度落地后必须补的一刀」，很值得在面试里讲；本期先在 C06/C11 的设计里把「失效事件清单」写清楚，不落码。

### C14 检索语料漂移与金标 / 金丝雀回归集（Corpus Drift & Golden / Canary Regression）

**解决什么问题**：新文档不断入库、embedding 模型悄悄升级，没有任何报错，几周后检索分数整体下滑、拒答率上升，系统「静默退化」；没有基线就分不清是调好了还是调坏了。

**面试官会怎么追问**：① 漂移看哪三类信号（检索分数分布、拒答率、用户反馈）？② 金标集、金丝雀放量、CI 回归闸门三者怎么配合，为什么「演示跑通」不等于「质量没退化」？

**与本项目契合度**：中。`eval/`（冻结离线占位评测）、`evalbench/`（真实 API 评估工作台）已有「版本化对象与前后对照」（`observability.py:537-539`），`eval/compare_runs.py` 已有指标映射；`demo/scenario.json` 明确「质量指标 comparable=false、质量阈值未冻结」。

**实现成本**：高。要建领域金标集、定冻结阈值、接 CI 闸门与金丝雀流量，属于上线级工程；且直接触碰冻结区边界。

**现状三态**：**未做**。`observability.py:538` 边界写明「闸门接 CI、阈值冻结、质量基线仍未做」；`eval/README.md:79` 明确「不要把占位结果写进质量基线，也不要据此冻结质量阈值」。

**本期裁决**：**留在本期之外**。金标/基线冻结属于 A/B 档上线级事项，且与「冻结区零改动」纪律正面相撞；本期只保留「漂移信号有哪些」的知识点说明，不建集、不定阈值。

### 2.15 被合并 / 淘汰的候选及理由

- **HyDE、step-back 单独成项**：合并进 C05，三者都是查询侧改写，单列会重复计条目且演示收益重叠。
- **答案级语义缓存单独成项**：合并进 C13，与「版本感知失效」是同一缓存链路的两段。
- **多租户 / 行级 ACL 单独成项**：淘汰。项目本轮已做过「去多租户、改多用户多部门」专项变更（`docs/architecture-review.md`、`docs/change-manifest.md`），再列会与既有范围口径打架，相关字段只在 C12 提及。
- **真实压测、监控告警 SLO、SSO/OIDC、真实账单校准、屏幕阅读器实测、质量基线冻结**：淘汰出候选清单，统一登记在 §4「明确不做清单」，不写成已完成。
- **逐句高亮定位**：合并进 C02，它是 claim 级引用的展示层，不是独立功能。

## 3. Top 5 推荐纳入本期（排序 + 依赖关系 + 可量化验收方式）

排序原则：用户重点是**演示技术深度，不是调效果**；优先选能在前端可视化、能用自建样本证明、且与「入库新鲜度 / 事实冲突检测」有直接依赖或互补的能力。以下 5 项均为「建议纳入本期」，**不代表已实现**；验收方式全部是待执行的断言条件，不是实测结果。

### 第 1 名 · C07 数据血缘与审计

- **为什么现在做**：它是新鲜度与冲突检测的公共底座——不先说清「哪两个版本、经过哪套解析、来自哪个原文件」，冲突检测只能是黑盒字符串比对，新鲜度也只剩一个时间戳。四层数据都已存在，串联成本最低、讲起来最有层次。
- **与新鲜度 / 冲突检测的依赖关系**：冲突判定输出必须带「版本 + 解析策略 + 原始文件」三元组；`expire_at` 判定新鲜度时也要能追到该版本快照，二者共用同一条血缘链。
- **可量化验收方式**：自建 1 个含新旧两版冲突的样本，验收断言：按任一 `msg_id` 回放能取到「回答 → `chat_sources` 分块 → `DocumentVersion` 版本 → `parsing/` 策略标识 → `source_uri` 原始文件」完整五段且各段非空，链路缺任一段即判不通过。

### 第 2 名 · C02 引用可验证性与逐句 grounding

- **为什么现在做**：`chat_sources` 已经把分块级引用做扎实了，往 claim 级推一小步就能把「怎么证明不是编的」讲透；前端逐句高亮 + 来源卡片是面试现场最直观的演示面。
- **与新鲜度 / 冲突检测的依赖关系**：冲突检测比较的是「原子声明」而非整段答案；同一问题若两版证据给出互斥声明，正是靠逐条 claim + 各自引用把冲突定位到具体句子，新鲜度裁决也才能落到「这句采信哪一版」。
- **可量化验收方式**：自建含 1 处错误引用的样本，验收断言：答案被拆成多条 claim、每条都能回连到 `chunk_text` 中的具体分块；被注入的那条无依据声明被标记为「未支持」或触发弃答，且标记结果在 `chat_sources` 侧可查询。

### 第 3 名 · C11 as-of / 时间旅行查询

- **为什么现在做**：`expire_at` + 不可变 `DocumentVersion` 快照 + `restore()` 追加式回滚已经把最难的版本语义做完了，as-of 只是补一个「按时间点筛选」的检索入口，复用度极高；前端一条时间轴即可演示「同问不同答」。
- **与新鲜度 / 冲突检测的依赖关系**：新鲜度回答「现在还有效吗」，as-of 回答「当时是什么样」，是同一份时效字段的两种查询方式；冲突检测也可借 as-of 把「两版并存」还原成「各自生效区间」，冲突判定从静态比对升级为带时间上下文的裁决。
- **可量化验收方式**：自建同一文档的两个带生效区间的版本样本，验收断言：切换两个 as-of 时间点，两次回答各自引用的 `DocumentVersion.version_no` 不同且与时间点匹配；查询时间点被写入 `chat_sources` 以便回放。

### 第 4 名 · C04 检索可解释性（分数拆解）

- **为什么现在做**：`search_debug()` 已把三阶段摊开，只差把每条命中的词法分 / 向量分 / rerank 分分列带出；成本最低，却是前三项的「放大镜」——降权、核验、as-of 过滤做得对不对，全靠这张调试页让人看见。
- **与新鲜度 / 冲突检测的依赖关系**：新鲜度降权系数、冲突标记的介入位置、as-of 过滤发生在召回前还是后，都必须在分数拆解里显式留痕，否则治理逻辑不可复核、面试追问「怎么证明生效了」无从答起。
- **可量化验收方式**：断言调试页对每条命中同时给出三路分数与所用 `retrieval_mode`；构造 embedding 不可用场景，断言 `fallback_reason`/`rerank` 被如实标注为降级、且前端不显示「已用向量」的假状态。

### 第 5 名 · C01 近重复与文档去重

- **为什么现在做**：冲突检测最典型的误报源就是「同一政策被多部门各传一份、仅页眉不同」；先去重能让冲突判定干净，且相似度矩阵 / 指纹对照在前端很好演示，正好呼应 2025–2026 工业流水线里 MinHash LSH 的高频做法。
- **与新鲜度 / 冲突检测的依赖关系**：去重产出「内容指纹 → 代表文档」的映射，新鲜度只需对代表版本判定有效期，冲突检测也先剔除伪冲突（重复副本）再比对真冲突（不同版本、互斥声明）。
- **可量化验收方式**：自建若干份仅页眉/落款不同的近似副本样本，验收断言：去重后进入索引的分块数少于去重前、各副本中的唯一段落全部仍在（无误删）、每次去重动作在 `audit_logs` 留一条可查记录。
