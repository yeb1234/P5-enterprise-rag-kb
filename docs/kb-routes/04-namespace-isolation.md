# P5 图谱检索的跨项目隔离：属性命名空间 + 查询层强制

编制：2026-11-27 ｜ 状态：**属性隔离与入口强制检查已实现并加单测；Enterprise RBAC 只是设计方向，未实现。演示切片，不是上线交付版。**

> **事实基线**：Neo4j **5.26.34 community** + 官方 Python 驱动 **6.4.1**。
> community 版只有**一个业务库**，没有多数据库，也没有 RBAC
> （`CREATE ROLE` / `GRANT` / `CREATE DATABASE` 都是 Enterprise 特性）。
> 任何把「Neo4j 权限隔离」说成**已实现**的口径都是错的。

---

## 1. 为什么用属性隔离，而不是多数据库

直观的隔离方案是「一个项目一个库，用账号权限挡住」——但那需要 Enterprise。
P5 跑的是 5.26.34 **community**，只有一个业务库。若硬要多库，就得换版本、加许可证，
与「开发框架骨架 + 可运行演示切片」的定位不符。

所以在 community 上能落地的隔离只有一条路：**同一个库里，所有节点自带归属属性
`kb='p5kb'`**（`kgraph/contracts.py:GRAPH_NAMESPACE`），查询必须显式按 `$kb` 过滤。
过去的做法是「靠约定」——模板和 Text2Cypher 提示词里都写了 `{kb: $kb}`，
但谁来写漏了，脚本照样能跑、静默读到别的项目数据，没人拦得住。

这次把约定升级为**存储层强制**：`Neo4jStore` 的所有执行入口在连库之前先做静态检查，
没带 `$kb`、或任一业务节点模式没带 `kb` 的语句直接 `ValueError`，根本到不了驱动。

> 代价要认：这是**同一实例内的软隔离**，不是数据库级硬隔离。它能挡住「写漏了」，
> 挡不住「拿到库凭证的人手工执行一条不带 kb 的 Cypher」——后者要靠第 4 节的
> 真正 RBAC 方案，社区版做不到。

## 2. 三道防线

| 防线 | 位置 | 管什么 | 拦什么 |
|---|---|---|---|
| ① 数据层：节点 `kb` 属性 | `kgraph/builder.py:apply()`；每条写入都带 `{kb: $kb, ...}` | 给每条数据打归属标记 | 让「按项目过滤」有据可依；不同项目的数据即使同库也不混 |
| ② 存储层：入口静态检查 | `kgraph/store.py` 的 `read()` / `run()` / `explain()` → `kgraph/cypher.py:assert_namespaced()` | **所有**被执行的 Cypher（模板、写入、LLM 生成、内省） | 没带 `$kb`、或 `:(Entity\|Chunk\|Document)` 模式没带 `kb` 的语句，连库前拒 |
| ③ 生成层：三关 | `kgraph/cypher.py:validate_readonly()` + `kgraph/retriever.py:_text2cypher()` | LLM 生成的 Cypher | 关键词白名单（写操作/ CALL 全拒）→ EXPLAIN 预检（不碰数据）→ 只读会话（驱动层再拒写） |

②是关键升级：它不区分语句来源，模板漏了、模型写歪了、后人加了新查询忘了带 kb，
都在同一个入口被拦。①和③是原有机制，②把「约定」变成了「强制」。

---

## 3. 静态检查的规则与局限

### 3.1 规则

`assert_namespaced()`（`kgraph/cypher.py`）的规则：

1. **放行**纯 schema / introspection：`CALL db.` / `CALL dbms.` 前缀（如探针的
   `CALL dbms.components()`、`_has_typed()` 的 `CALL db.relationshipTypes()`），
   以及 `CREATE/DROP INDEX|CONSTRAINT` DDL——它们不读业务数据、也没有 `$kb` 的概念。
   用**前缀**匹配而非宽松子串，避免把夹在中间的 `CALL db.` 当白名单放行。
   容忍可选的 `EXPLAIN` / `PROFILE` 开头（调用方可能已拼好前缀）。
2. 其余语句必须出现 `$kb` 参数。
3. 每个 `:(Entity|Chunk|Document)` 节点模式，要么大括号里带 `kb` 键
   （如 `{kb: $kb}`），要么紧随其后有 `WHERE <alias>.kb = $kb`。
   退路必须**认准同一个 alias**——否则「上半句守规矩、下半句换别名偷读别的项目」
   会蒙混过关。这一条有专门的回归测试钉住。

### 3.2 局限（必须诚实）

- **不是完整的 Cypher 解析器**。它是一组保守正则，覆盖不了子查询、模式理解、
  路径变量、反引号标识符等复杂语法。复杂写法可能被误判——这里的原则是
  **宁可拒绝也不放行**；真误伤了要评审后调整检查逻辑，不能靠放宽标准绕过。
- **白名单有风险面**。`CALL db.` / `CALL dbms.` 与 DDL 不读业务数据，所以放行；
  但理论上若有人注册了 `db.*` 名字的自定义过程，仍可能借前缀绕过。所以②不是单点，
  ③的关键词白名单、EXPLAIN、只读会话仍然必须保留。
- **只检查语句引用了 `$kb`，不校验运行时参数值**。参数值由各调用方统一从
  `store.namespace`（= `GRAPH_NAMESPACE`）注入；这一环仍靠代码约定，静态检查管不到。
- **只覆盖三种业务标签** `Entity` / `Chunk` / `Document`。将来新增业务标签要同步
  扩充正则，否则新标签模式不会被检查——这是已知的扩展点。
