0 · 边界与三条硬事实（先看这段）

最显眼的一条：腾讯云 API 网关「共享实例」有单服务 500 QPS 硬上限，超限会「丢请求」而不是「排队」

共享实例单服务上限约 500 QPS、请求体 ≤ 16MB、不支持 VPC；达到 QPS 上限时请求可能被丢弃（不是排队等）。演示够用；只要你有稳定高并发或要接 VPC/专线/WAF/EIAM，就必须上专享实例。这一点在 §2 与 §5 反复标注。

三条必须先讲清的事实（避免把设计说成已实现）

① 本页引用的是主理人 2026-11-15 联网核实的公开信息，规格与价格以腾讯云控制台实时价为准，全文金额为「估算 + 假设前提」，不是账单、不是报价。
② 本页是部署与加固指导，不是上线证明；未做等保测评、WAF 规则调优、真实压测、DDoS 高防、数据合规审批。
③ 页面里的「已实现 / 仅预留 / 未做」逐条标注，并按 webapp 与 backend 两列分列不合并：已实现 有代码 + 实测可查，仅预留 是接口/占位存在但无调用点，未做 是既无代码也无设计。webapp 演示切片本轮已完成五项网关加固，backend 骨架同名能力仍以「仅预留」标注。

本项目「多用户」能力在哪、演示站又在哪

实查：多用户鉴权与多用户加固能力在 webapp/（PBKDF2 口令 + HMAC-JWT + 三维限流 + 预算 + 审计）与 backend/（decide() 权限判定、部门/owner 过滤、审计只追加）；showcase/ 解析工作台是单用户离线演示站（8767 端口，无登录体系），它演示「解析→入库 JSON」，本身不承担多用户隔离。因此「多用户加固」要落在真正有多用户体系的 webapp/ 或 backend/ 上，别把单用户演示站说成多用户系统。

1 · 分层加固图（DNS → WAF → CLB → CVM → 数据层）

每一层只解决自己该解决的问题；不要指望某一层包打天下。四层纵向叠加，越靠上越「粗」、越靠下越「懂业务」。

DNS / 域名腾讯云 DNSPod
拦什么：解析到哪台机器、CNAME 指向（接 WAF 时域名要 CNAME 到 WAF）。不做业务鉴权。入口寻址
↓ 请求进入
WAFWeb 应用防火墙
拦什么：OWASP Web 攻击（SQL 注入 / XSS / 命令执行）、CC 攻击（频率 + 人机校验）、IP 信誉库、地理围栏、0day 虚拟补丁；企业版再加 API 安全与 BOT 管理。支持 CNAME / SDK 插件 / 透明接入，有旁路检测与一键 Bypass。应用层攻击
↓ 清洗后转发
CLB负载均衡
拦什么：四层 TCP/UDP + 七层 HTTP/HTTPS；做 HTTPS 卸载、权重 1–100、按域名/URL 路由；依托大禹做 DDoS / CC 清洗；配连接数 / 新建连接速率 / 带宽规格。不做业务鉴权。流量分发 + 抗量
↓ 转发到后端
CVM + Docker应用层
拦什么：认证（口令/JWT）、四维限流（user/endpoint/model + ip 附加维度）、权限判定（decide()）、数据隔离（owner/部门）、用户级预算、审计、PII。这是唯一懂业务的一层，也是最后一道闸。业务鉴权 + 配额
↓ 访问数据
数据层PG/Redis/VectorDB/COS
拦什么：网络隔离（只允许 CVM 内网访问、不暴露公网）、账号最小权限、连接数上限、备份加密。用云数据库 PostgreSQL / TDSQL-C、Redis、VectorDB、COS、日志服务 CLS。数据边界
一句话分工

DNS 找路 → WAF 挡坏请求 → CLB 分发并抗量 → 应用层认人 + 算配额 → 数据层守边界。安全是叠加的，任何一层都不能替代另一层。

2.3 为什么「两层都要有，不能只靠一层」

云网关管入口，应用层管业务配额

云 API 网关做不到的事：不知道谁是「部门 A 的用户」、不知道某用户今天用了多少 token、不能按 endpoint 与 model 组合限流、不能在 429 里告诉你「是哪个维度、还剩几秒」、不能和权限判定 decide() 联动。
应用层做不到的事：挡不住 10 万 QPS 的 DDoS、做不了 TLS 卸载、做不了多机负载均衡、扛不住真实 CC 洪峰（单机令牌桶先被打满）。
结论：入口限流（网关/CLB/WAF）负责「不让洪水进来」，业务限流（应用层三维 + ip 附加维度）负责「让每个用户公平、可追责、可退避」。缺任何一层都会留下真实缺口。

上云后必踩的坑：X-Forwarded-For 与「按 IP 限流」的信任链webapp 已校验

坑在哪：backend/app/middleware/rate_limit.py 用 request.client.host 取 IP。这在「浏览器直连应用」时没问题，但一旦前面挂了 CLB / WAF，request.client.host 会变成代理的内网地址——于是「按 IP 限流」要么把所有人算成同一个 IP（全站共用一个桶），要么对伪造的 X-Forwarded-For 照单全收（攻击者换头就绕过）。
webapp/ 已用 TRUSTED_PROXY_IPS 白名单校验（security.py::client_ip(host, xff, trusted)，默认 127.0.0.1,::1）：只有直连对端是可信代理时，才采信 X-Forwarded-For 最左值；直连时伪造 XFF 不生效（实测：伪造 X-Forwarded-For: 1.1.1.1，第二次仍 429 key=testclient，伪造头没有换 key；可信代理下 5.5.5.5 / 6.6.6.6 各自计数）。可复现：pytest -q webapp/tests/test_gateway_hardening.py → 18 passed。
上云仍要做：把 WEBAPP_TRUSTED_PROXY_IPS 设为你自己的 CLB/WAF 回源网段（默认只含本机回环，别把 0.0.0.0/0 配进去）；backend/ 骨架仍是直接取 client.host，接代理前需自行补同等校验。不要无脑取 XFF 最左值。

bash · 2) CLB 挂后端 + 证书 + NGINX 反代（七层）
# 控制台：CLB → 创建七层 HTTPS 监听 → 后端组指向 CVM:8765（和/或 8767）
# 权重 1–100；证书在「证书管理」上传后绑定到 443 监听（腾讯云托管可自动续期）

# CVM 内：nginx 反代到本机容器（CLB 到 nginx，nginx 到容器，双保险可控）
# /etc/nginx/conf.d/kb.conf
server {
    listen 80;
    server_name _;
    client_max_body_size 64m;
    location / {
        proxy_pass http://127.0.0.1:8765;      # 多用户完整功能页
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        # 与 CLB 的转发头对齐后再决定是否信任 X-Forwarded-For（见 §2.3）
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
        proxy_buffering off;                    # 流式/SSE 需要关缓冲
    }
    location /showcase/ { proxy_pass http://127.0.0.1:8767/; }
}
sudo nginx -t && sudo systemctl reload nginx

#   - 透明接入：在 CLB/实例侧挂载，不改 DNS（按版本支持情况选）
#   - 先开「观察/旁路」模式看规则命中，再切「拦截」；保留一键 Bypass 应急
# 日志：日志服务 CLS → 采集 nginx / 容器 stdout；设置保留期与检索
# 告警：云监控 → 对 CPU/带宽/5xx/429 设阈值告警，通知到你的手机/邮件
# CAM：子账号 + 最小权限策略；部署脚本用独立子账号，不用主账号 AK
这一步最容易出的错

① 安全组开了 8765/8767 到公网（等于绕过 WAF/CLB，直连容器）；② WAF 直接切拦截没先观察，误杀正常流量；③ 只挂了 CLB 没配 XFF 信任链，应用层把所有人当一个 IP；④ 用主账号 AK 跑脚本；⑤ 忘了给 22 限来源 IP。

5 · 费用估算表（估算 + 假设前提，不是账单）

怎么读这张表

「演示」几乎只花服务器 + 域名的小钱；「小规模生产」的成本大头是 WAF 高级版，而不是机器——很多人低估这一项。API 网关共享实例在低调用量下基本免费，但别用它承载稳定 >500 QPS（会丢请求），那时要上专享。建议开通前在控制台设费用告警，并每日核对账单与调用量。

6 · 上线检查单（可勾选）

  • 入口与网络
  • 安全组只放行 443（公网）与 22（仅你的 IP/32）；8765/8767 未暴露公网
  • 域名已备案并解析；HTTPS 证书已绑定、可自动续期；HTTP→HTTPS 301
  • WAF 先观察模式跑过一轮，再切拦截；Bypass 应急流程已演练
  • CLB 健康检查通过；后端权重与超时合理
  • 限流与容量（重点验证）
  • 用 ab / wrk 压 600 QPS，观察 429 与 503 是否符合预期（应用层应返回 429 + Retry-After；网关/CLB 层超限可能是 503/丢请求）
  • 伪造 X-Forwarded-For 验证不被采信 —— 已可复现 pytest -q webapp/tests/test_gateway_hardening.py → 18 passed（换头不应绕过按 IP 限流）
  • WEBAPP_TRUSTED_PROXY_IPS 已设为 CLB/WAF 回源网段（默认只含 127.0.0.1,::1；切勿配 0.0.0.0/0）
  • 三维限流 user/endpoint/model 各自触发一次 429，且响应头含维度与剩余窗口
  • IP 附加维度已生效：匿名请求按 ip 计数，命中返回 RATE_LIMIT_IP_EXCEEDED / X-RateLimit-Dimension: ip（已复现）
  • 并发闸：MAX_INFLIGHT 调小后压并发 → 超限返回 503 SERVER_BUSY + Retry-After（已实测 [200,503]）
  • 用户级预算：A 用户超支不影响 B；问答入口 429 QUOTA_EXCEEDED，离线评估入口 200 + {ok:false,reason:"budget_exceeded"}（形态不同、语义一致）
  • 请求体上限三层保险：nginx client_max_body_size + MAX_BODY_BYTES（10 MiB → 413）+ 后端 MAX_UPLOAD_SIZE_MB 都生效
  • 多用户与数据
  • 越权用例集全绿（跨用户 / 部门边界 / owner 过滤）
  • 审计只追加已验证；拒绝请求也有记录
  • 预算默认 warn、需要时切 block；成本归因可查
  • 数据层（PG/Redis/VectorDB/COS）均不暴露公网，账号最小权限
  • 运维与安全
  • CAM 子账号 + 最小权限；主账号未创建 AccessKey；AK 未硬编码/未入 Git
  • 容器 --restart unless-stopped + systemctl enable docker nginx
  • 日志轮转生效（docker inspect 查 LogConfig）；CLS 采集正常
  • CPU/带宽/5xx/429 告警已设并实测能收到
  • 回滚路径可用：上一版镜像 tag + .env 副本已留存
