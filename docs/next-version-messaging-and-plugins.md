# 下一版本改进方案 v0.2 · 消息层职责重划与插件清单

**定位**：只给结论与谈资，不写配置步骤与代码实现。
**现状**：v0.1 骨架里 Redis 同时兼任缓存、限流、进度通道、Celery broker 与 result backend；
Celery 用 `acks_late + visibility_timeout + PG 台账 + beat 捞回` 补可靠性。
**本版要回答的**：RabbitMQ 进来之后，三者到底各管什么、为什么值得多养一个中间件。

---

## 0. 一句话结论

> **按「数据能不能丢」分层：不可丢的任务投递交给 RabbitMQ，可重建的实时状态交给 Redis，
> 执行语义交给 Celery，状态真值始终在 PG。**

v0.1 用 Redis 兼任 broker 是**对的取舍**（少一个中间件、学习期排障成本低）；
v0.2 引入 RabbitMQ 也不是「改一个 broker 配置项」，而是**职责边界重划**：
投递确认、ack 时机、死信治理、beat 降级、可观测口径都要跟着变。
能把这个「不是改配置、是改边界」讲清楚，比背下任何参数都值钱。

---

## 1. 三者职责边界

| 组件 | **只负责** | **明确不负责** | 数据能否丢 |
|---|---|---|---|
| **RabbitMQ** | 任务消息持久化投递、publisher confirm / consumer ack / nack、死信队列（DLQ）、按队列隔离与配额、失败重投 | 缓存、事件广播、结果查询、进度流 | **不可丢** |
| **Redis** | 搜索结果缓存、限流令牌桶、进度快照 + pub/sub、幂等键、租户并发闸、短期锁 | 任务排队、任务结果存储、状态真值 | **可丢、可重建** |
| **Celery** | chain / chord 编排、队列路由、重试退避、worker 分工（light / heavy / maintenance）、beat 定时 | 结果真值、长期状态、审计留痕 | 执行过程可重放 |
| **PostgreSQL** | `ingest_jobs` 台账、审计日志、日报预聚合、全文检索 | 实时推送、消息投递 | **唯一真值** |

**判断准则（一句话背下来）**：
> 丢了要重跑的 → RabbitMQ；丢了重算就行的 → Redis；用来判断「到底成没成」的 → PG。

三者不是互为备选，也不存在「谁替代谁」：
RabbitMQ 做不了缓存与 pub/sub 的数据结构，Redis 的 AOF 不是投递确认，Celery 不持有状态。

---

## 2. 协作关系（以一次大文件上传为例）

```
① API 写 PG：upload_sessions / documents / ingest_jobs(queued) —— 先有真值
② 事务提交后投递 RabbitMQ（持久化 + confirm）—— 先落库再投递
③ Celery worker 消费，按 queue 分流（ingest / ingest_heavy / maintenance）
④ 每阶段：写 PG（真值）→ 推 Redis pub/sub（实时）→ SSE 到浏览器
⑤ ack 只在「PG 状态落库成功」之后发出
⑥ 失败：带退避重试 → 超限进 DLQ → 人工/补偿任务；beat 退为二次兜底
⑦ 前端只订阅 Redis，不查 RabbitMQ、不依赖 Celery result
```

**三条红线**（v0.1 已确立，v0.2 不变）：
1. **先写 PG 再投递**，反过来会「worker 先跑、读不到文档」；
2. **先滤权限再召回、再进模型**，消息层再可靠也替代不了权限层；
3. **向量是派生数据**：PG 文本落库后才写 Milvus，跨库不一致靠每日对账，不追求分布式事务。

## 3. 设计取舍（面试最值钱的六条）

| # | 结论 | 为什么 | 代价 / 反例 |
|---|---|---|---|
| T1 | 选 **at-least-once + 幂等**，不追 exactly-once | 跨 PG 与消息中间件不存在廉价 exactly-once；`chunk_id = uuid5(doc, version, seq)` 让重复执行只覆盖不新增 | 必须给每个任务设计幂等键，偷懒就会重复计费/重复向量 |
| T2 | **ack 在业务落库之后** | 崩溃时宁可重复执行一次，不可丢任务 | 重复执行会多花一次 embedding 调用，属于可控成本 |
| T3 | **进度真值在 PG，Redis 只是加速** | Redis 挂了 SSE 降级轮询，进度不会「假死」或归零 | 多一次节流落库设计（0.5s，关键状态强制写） |
| T4 | **`visibility_timeout` 问题消失**是换 RabbitMQ 最实在的收益 | v0.1 里 900s 大文件任务必须把可见性超时设成 2 倍，仍有误重投风险；RabbitMQ 的 ack 是消费者确认，不靠计时猜 | 需要真正治理 consumer 超时与心跳 |
| T5 | **故障域分离** | 缓存抖动不再拖垮入库队列；队列积压不再打爆缓存 | 多一个有状态中间件，运维与监控成本上升 |
| T6 | **迁移不是改一处配置** | 要重划 ack 时机、DLQ 归属、beat 职责、结果后端退役、可观测口径 | 「只改 broker URL」是常见错误答案，说出来会减分 |

**迁移触发条件（满足任一才升 v0.2）**：任务不可丢 / 任务时长接近可见性超时量级 /
多租户需要队列级配额隔离 / 需要死信审计与人工补偿。
**当前 A 档骨架保持 Redis broker 不变**——这是有意取舍，不是技术债；
在面试里主动说明「现在为什么不做」和「什么条件下才做」，比堆组件更能体现判断力。

## 4. 落地分阶段（结论级）

| 阶段 | 动作 | 完成标志 |
|---|---|---|
| A · 先解耦 | 结果后端退役：Celery result 不再作为状态来源，统一读 `ingest_jobs` | 删掉 result 依赖后链路仍可跑通 |
| B · 换投递 | RabbitMQ 接管 broker，按队列建 DLQ；ack 时机改为业务落库后 | 投递确认、死信、重投三条路径都有演练记录 |
| C · 收尾 | Redis 只留状态类职责；beat 从「捞回僵死任务」降级为对账与日报 | 故障注入下无重复向量、无幽灵片段 |

## 5. 插件改进清单（按面试讲解价值排序）

> 「插件」指**可插拔、可单独开关、可单独讲解**的能力单元；每项都能独立做 A/B 与回归，
> 与 `eval/` 的版本化对象、对比实验、闸门天然对齐。

### P0 · 优先纳入（讲得出「为什么这么做」）

| 改进项 | 一句话结论 | 面试讲解要点 | 预期收益 |
|---|---|---|---|
| **中文分词插件（zhparser 类）** | 把全文检索从 `simple + ilike` 换成中文分词配置，业务代码零改动 | 中文不做分词时 `to_tsvector` 基本失效；用 PG 扩展 vs 自建分词服务的运维/一致性取舍；触发器改一处、索引不动 | 召回可解释、可量化；MRR/NDCG 有基线可谈 |
| **ParserProvider 解析插件** | 把 pypdf 规则分块抽象成可替换 provider，逐步接入更强解析器 | 「质量源头决定上限」；换解析器不动 chunks 表、Milvus schema 与引文契约；解析质量评估集才是证据 | PDF 双栏/表格/扫描件覆盖；页码引文可信度 |
| **Rerank 重排插件** | 在 RRF 融合后加一层可降级重排 | 双塔召回便宜、交叉编码器准但贵；先召回后重排的成本曲线；**必须带降级开关**，否则 P95 兜不住 | 排序质量提升，同时能讲延迟预算与开关策略 |
| **可观测插件（OTel / LangSmith 等价）** | 从 JSONL+manifest 升级为 trace/span 体系 | `trace_id` 贯穿到逐 span 的 `object_refs`；托管 vs 自托管的**数据出域**取舍；排错从「看日志」变「看链路」 | 从「能复现」升级到「能定位瓶颈」，可直接展示一条完整 trace |

### P1 · 有证据价值（讲得出「怎么验证」）

| 改进项 | 一句话结论 | 面试讲解要点 | 预期收益 |
|---|---|---|---|
| **Prometheus + 告警 / SLO** | 指标从 `metric_events` / `daily_stats` 出，不重复埋点 | 三项 SLO（首 token、整答、错误率）怎么定；压测报告与告警阈值的关系；**先有指标口径再接告警** | 上线级证据：P95、错误率、瓶颈结论 |
| **评测 CI 闸门插件** | 把 `eval/` 的 L0–L3 接进 CI，L4/L5 审批后跑 | 占位结果 `comparable=false` 绝不参与闸门；变体只在内存生效、采纳后必须升对象版本；配额成本 vs 回归频度的取舍 | 每次改动可验证；「改了配置怎么保证没退化」有答案 |
| **缓存与配额治理插件** | 缓存 key 带 `tenant/user/role` + `config_snapshot_hash` 前缀 | **缓存串租户是最隐蔽的越权**；对象版本变更让缓存自动失效；限流从按 IP 升级到按租户分级 | 性能与权限双收益；能讲一个真实越权案例 |

### P2 · 扩展能力（讲得出「边界在哪」）

| 改进项 | 一句话结论 | 面试讲解要点 | 预期收益 |
|---|---|---|---|
| **MCP 工具网关 / 多 Agent 路由** | 现有 `ToolRegistry` 升为白名单网关，工具调用仍走同一个 `decide()` | 换 LangGraph 只改编排层，鉴权/审计/工具层不动；**绝不开放自由 SQL 与任意 HTTP**；按意图分流而非全量放权 | 能力可扩展且不破坏权限红线 |
| **渠道入口插件（飞书 / 企微）** | 渠道只做适配，问答编排与权限判定完全复用 | 入口增多不等于权限放宽；回调验签与审计同源；为什么不放进核心链路 | 演示闭环更完整，场景从「能跑」变「有人用」 |

**明确后排**（不是不做，是性价比低）：PII 三道闸模型级检测、审计按月分区与冷归档、
worker 优雅停机 / drain。三者都属「团队质量工作」，在 A 档骨架里做只会分散证据。
**这条「主动列出不做什么」本身就是谈资**：说明你分得清 Demo、骨架与上线交付。

## 6. 面试 30 秒讲法（可直接背）

> 「消息层我按『数据能不能丢』拆成三块：RabbitMQ 管不可丢的任务投递和死信，
> Redis 管可重建的缓存、限流和进度推送，Celery 只负责编排和重试，真值一直在 PG。
> 我没有追 exactly-once，而是用 at-least-once 加幂等键，ack 放在业务落库之后——
> 崩溃时宁可重跑一次，也不能丢任务。进度不放在消息里，Redis 挂了就降级轮询 PG。
> 当前骨架阶段我故意还用 Redis 兼 broker，因为多一个中间件在这个规模不划算；
> 等任务不能丢了、或者任务时长逼近可见性超时，才升 v0.2，而且那不是改一个配置项，
> 是重划 ack、死信和 beat 的职责边界。插件上我优先做能用评测体系量化收益的：
> 中文分词、解析 provider、重排、可观测，每一项都有 A/B 和回归闸门，不靠感觉说话。」

## 7. 本轮落地映射（可运行演示切片 `webapp/`）

方案本身不改变 v0.1 运行行为；本轮另外补了一个**可直接打开界面**的演示切片，
用来把「职责边界」讲成看得见的东西，并补齐问答 badcase 数据流闭环。详见 `webapp/README.md`。

| 方案里的结论 | 切片里的替身 | 面试讲解要点 |
|---|---|---|
| PG 是唯一真值 | SQLite 单库，文档/分块/badcase/评估任务/聊天日志全落库 | 换库不动契约；「先落库再投递」在这里变成「先落库再入队」 |
| Celery + broker（v0.2 RabbitMQ） | 进程内信号量队列 + `/api/system/busy` | 队列只决定「能不能立刻跑」，状态真值仍由库表回答；**繁忙提示显示排队位置**正是「进度不放在消息里」的可视化 |
| Redis 进度通道 | 前端 2.5s 轮询 + SSE 心跳 | 真通道挂了就降级轮询，进度不会假死或归零 |
| 先滤权限再进模型 | admin 门禁（普通用户 403）+ 检索前只读 `ready` 分块 | 消息层再可靠也替代不了权限层 |
| 可观测插件 P0 | 繁忙横幅、连接状态、降级原因留痕 | 演示级，**不是** OTel trace/span，讲的时候要说清档次 |
| 评测 CI 闸门 P1 | badcase 采集 → 查看 → 导出闭环 + 完成度看板 | 只落地**数据侧**；闸门接 CI 仍未做，占位结果仍 `comparable=false` |
| 插件清单 P0/P1 的可讲解性 | 侧栏由 3 项扩为 9 项分 3 组：概览 / 检索调试 / 任务中心 / 评测中心 / 审计日志 / 系统边界 | 导航层按 README §4 已有模块补齐；**只读真实数据，纯设计项明确标注**，故意不做的入口也列出理由 |

**导航层补充结论**：补齐依据不是「看起来像企业级」，而是文档里已写好的模块
（看板、任务、审计、组织、检索、版本化对象）。新增 5 条 API
（`/api/overview`、`/api/search/preview`、`/api/eval/objects`、`/api/admin/users`、
`/api/admin/audit`）全部读 SQLite 现有业务表或 `eval/config/registry.json`，不造数据。
概览按角色分级统计、审计只追加台账，是对 P1「缓存/配额治理」与 C 档「谁能查什么」
的最小可演示回应；监控大盘、trace 瀑布、空间管理、权限编辑等入口**故意不加**，
理由写在 `webapp/README.md` §2.1——空壳入口会削弱「已实现 / 只设计」的边界。

**本轮新增能力的设计结论**：badcase 与评估任务共用一张关联表，创建时校验 `eval_task_id`
存在（不存在直接 400），完成度由关联计数派生，因此「查看」与「进度」不可能对不上；
下载与列表复用同一套筛选参数，保证「所见即所下载」。采集对所有登录用户开放、
查看/导出/完成度仅 admin 可见——**采集与查看权限分离**，是最小权限原则的直接体现。

**诚实边界**：中文分词、Rerank、ParserProvider、真实 OTel/Prometheus、RabbitMQ、MCP 网关
仍是设计，未在切片中实现；所有真实 API 字段保持 `__TBC__`。
主动讲「哪些做了、哪些只是设计」，比把 A 档说成 C 档更有说服力。

## 8. 验收口径与边界

- 本版是**改进方案**，不改 v0.1 运行行为；现有 `eval/` 离线评测与演示物料保持可用。
- 每项插件必须能回答三问：**挂哪个版本化对象？用哪个指标判定收益？怎么回滚？**
  答不上来就不进版本。
- 所有真实 API 相关字段仍为 `__TBC__`；本方案不涉及任何具体服务地址、鉴权、配额或模型名。
- 质量阈值仍 `NOT_COMPARABLE`，插件收益必须等真实 API 基线冻结后才给数值结论。
- 演示切片 `webapp/` 的自测结论独立于 `eval/` 体系：`python webapp/selftest.py` → 26/26 `DEMO_READY`。
