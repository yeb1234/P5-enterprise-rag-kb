## 2. 为什么不是「在展示层打码」

实查结论：改造前 webapp 演示切片的 `chat_logs`、`audit_logs`、`badcases`、
`chat_sources`、CSV/JSON 导出**全是明文**；backend 骨架只有两条 PII 正则
（手机号、身份证，且无校验位），`verify_node` 只在输出侧替换。
`docs/knowledge/02-candidates.md` 的 C09 明确写着「只做一层反而容易被追问成漏洞，本期不做」。

所以把「一层」理解为**一套规则、四个出口**，而不是一个替换点：

| 出口 | 真实接入点 | 做了什么 |
|---|---|---|
| 入库前 | `webapp/rag.py::analyze_document` | 分块之前脱敏，写进 `chunks` 的就是脱敏文本；异常 **fail-closed 阻断整份入库** |
| 进模型前 | `webapp/routers_chat.py::chat_stream` | 检索用原文（保召回），question 与来源片段在送进 LLM 前脱敏 |
| 输出前 | 同上 + `webapp/static/app.js` | SSE 逐 token 过 `StreamRedactor`，尾部由 `done.tail` 补齐 |
| 日志与导出前 | `webapp/db.py::log_action`、`routers_badcase.py` | 审计 `target/detail`、badcase 采集/列表/CSV/JSON 全走 `audit` |

顺序是关键：**先检索、后脱敏**。把问题先打码再检索会破坏词法召回，
但脱敏后的文本必须在进模型、落库、下发、导出之前生效。

## 3. 本轮抓到并修掉的两个真实缺陷

这两个不是文档里写的「假想风险」，是实跑复现出来的：

**① 校验位非法的身份证被误报成银行卡。**
`11010119900307193X` 的 MOD 11-2 校验位不合法，身份证规则正确地拒绝它；
但旧的 `BANK_CARD` 正则 `(?<!\d)\d{16,19}(?!\d)` 会匹配前 17 位数字，
而这一串**恰好通过 Luhn**，于是被当成银行卡打码——一个负向对照被当成了正向命中。
修法：BANK_CARD 改为 `(?<!\d)\d{16,19}(?![\dXx])`，末尾跟 X/x 的交给身份证规则。
同时把演示样本全部换成按算法算出的**合法**校验位
（身份证 `110101199003071938`、银行卡 `6222021234567894`），
不再用随手编的号码——否则演示本身就在骗人。

**② 长文本下流式闸把身份证原文整段发了出去。**
旧 `StreamRedactor` 只保留尾部 `HOLD=24` 个字符。逐字符下发长文本时，
滑动窗口每轮只扫前 2 个字符，永远看不到完整 18 位标识符，
结果 `员工身份证号是 110101199003071938，…` **一字不改地出现在输出里**。
修法：`push()` 先找出横跨下发边界的连续候选串（数字/字母/邮箱分隔符，
中文天然充当边界），把边界收缩到它的起点**整串扣住**，等它完整进入缓冲区再扫描脱敏。
现在长文本逐字符下发 `leaked=false`，7 种 chunk 大小（1/2/5/9/17/31/64）零泄漏，
且无 PII 文本的流式拼接与原文**逐字相同**（不悄悄丢字）。

## 4. SSE 契约怎么保住的

`webapp/selftest.py` 的 C13 要求断线续传的 token 包索引连续
（`t3[i]["index"] == resume_from + i`）。脱敏会改变文本长度，
如果按「安全片段」重新组包，这个契约立刻破。

解法：

- `StreamRedactor.push()` 返回的安全片段作为**当前包**的 `token`（可能为空串）；
- 包数不变、`index` 仍用原始索引；
- `flush()` 的尾部放进 `done.tail`，前端在 `ev==='done'` 时
  `insertAdjacentText('beforeend', obj.tail)` 补齐；
- `done.answer` 与 `chat_logs` 落的是完整脱敏答案。

**如实标注的剩余边界**：真实浏览器断线重连时，客户端 `lastIndex` 已推进到
那些「还没下发、只是被扣住」的 token，重连后服务端按原始 index 跳过它们，
尾部可能少几个字。生产做法是把续传游标改成基于**安全输出字节偏移**，
而不是原始 token 序号。这个取舍在 02-design 里单独一节。

## 5. 现场演示（前端「内容安全 / PII」页）

- **策略与规则清单**：规则版本、默认动作、最小置信度、拦截类别、可逆 token、
  哈希盐是否已配置；11 条检测规则逐条列出校验器与置信度。
- **四出口命中台账**：真实链路里每个出口各拦了多少条；台账只存类别与数量。
- **一键规则演示**：9 条合成样本（身份证/手机号+邮箱/API 密钥/工号+姓名/银行卡
  + 4 条防误报负向对照），逐条给出命中类型与脱敏后文本；再展示同一段文本
  依次穿过四出口的结果，以及逐字符流式下发的 `leaked=false` 实测。
- **任意文本四出口检测**：粘一段自己的文本，立刻看四层结果。
- **策略开关（admin）**：启停、默认动作、最小置信度，保存即时生效；
  关闭启用会在返回里明确警告「四个出口全部放行原文，仅限对照演示」。

内置样本里的证件号 / 手机号 / 卡号都是**按校验位算法合成的教学用号码**，
不是任何真实个人的信息。

## 6. 验证（全部实跑）

| 项 | 结果 |
|---|---|
| 单测 | **248 / 248**（webapp 101、parsing 22、knowledge 23、cache 19、guardrails 27、backend 26、eval 14、evalbench 16） |
| 新增单测 | guardrails 27 + webapp 安全 API 11 + backend 检索契约对拍 10 = **48 项** |
| 端到端自测 | **33 / 33 `DEMO_READY`**（含 C13 续传索引连续、C12 降级话术、C14 badcase 字段） |
| 四出口真实链路冒烟 | 隔离库实跑：入库 chunks、SSE answer、chat_logs、chat_sources、audit_logs、badcase 采集/CSV/JSON 导出 **均无原文残留** |
| 防误报 | 4 / 4 负向对照零命中（非法校验位身份证、18 位订单号、13 位长号子串、普通技术文档） |
| 流式 | 长文本 `leaked=false`；7 种 chunk 大小零泄漏；无 PII 文本 roundtrip 逐字相同 |
| 前端 | `node --check` ×3 通过；新增 60 个 i18n 键与既有字典零冲突；资源版本 `?v=16` |
| 冻结区 | `eval/` `demo/` 零改动；自测报告按字节还原 |

三次单测失败（命中数硬编码 4、流式跨界、误报）都是**定位到实现 bug 后修实现**，
没有放宽断言。

**关于「只设计清单没具体测一测么」的追问**：实查 `backend/tests/` 发现，
`rrf_fuse()` / `decide()` / 进度权重其实**早有 16 项单测**，但缺「召回前 expr → 召回后逐条 `decide()` → RRF 融合」的**顺序纪律**对拍。
故本轮补 `backend/tests/test_retrieval_contract.py` 10 项离线用例（含 A13 双向一致性、
以及「不过滤时跨部门片段会排第一、先过滤后融合则彻底不回来」的对照实验），
`backend` 由 16 → **26 passed**，全量由 238 → **248**。
同时把 `interview/index.html` 的「只设计」卡片从笼统的「未落地」改成**契约层已实测 / 集成层未测**的分层描述。
真实 PG / Milvus / Redis / Celery 仍未接入、未集成测，**不因补测而改口**。

## 7. 边界，不夸大

- **规则级检测，不是模型级 NER**：语义上下文识别、重标识、k-匿名只是设计讨论，未实现；
  中文姓名/工号/护照只认带字段名词的写法。
- **未做**：图片/扫描件/表格单元格里的 PII、OCR 前处理、模型级脱敏、
  合规审计与留存策略、法务审批、SIEM 对接、密态检索、压测与阈值标定。
- **backend 骨架没接本包**：`backend/app/agent/orchestrator.py` 仍是两条正则 +
  `verify_node` 输出替换；本包只覆盖 webapp 演示切片。
- **默认盐只是占位**：`demo-salt-change-me` 用于 hash 动作等于没脱（彩虹表可反推），
  生产必须换成密钥管理系统里的值。
- **可逆 token 默认关闭**：映射本身就是新的泄漏面；开启后目前只放内存，
  生产需加密存储 + 独立授权 + 保留期。
- **文件名不脱敏**：磁盘文件名参与路径查找，直接改会破坏读取；
  它进入审计日志时由 `log_action` 的 audit 出口兜底。
- **actor 不脱敏**：审计里是内部账号标识；生产若用邮箱当账号需单独加规则。
- 演示切片是 SQLite + 进程内队列，阈值是经验起始值，不是压测结论。
