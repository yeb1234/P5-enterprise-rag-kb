### 0.2 术语首现表

| 术语 | 中文解释 |
| --- | --- |
| PDF（Portable Document Format） | 便携式文档格式，本质是「页面绘制指令 + 资源字典」的容器，不是纯文本 |
| 对象（object） | 编号的数据块，如 `1 0 obj ... endobj`；字体、页面、图像都是对象 |
| 交叉引用表（xref，cross-reference table） | 记录每个对象的字节偏移，支持随机跳页；新版也可用交叉引用流（xref stream） |
| 内容流（content stream） | 一页的绘制指令序列，压缩后存放，描述「画什么、画在哪」 |
| 字形（glyph）与字形子集（font subsetting） | 字形是字符的视觉形状；子集只嵌入用到的字形，字形名常被重编号为 `/G1`、`/G2` 而失去语义 |
| 字符映射表（CMap，Character Map） | 编码到字符的映射规则；`ToUnicode CMap` 专指把字形编码映射回 Unicode 的那张表 |
| 文本层（text layer） | 以「字符编码 + 字体资源」形式存在、能选中和检索的文字 |
| 扫描件 / 图片型页面 | 文字只以像素存在于位图中，没有任何字符编码 |
| 外部对象（XObject，eXternal Object） | 可复用资源；图像 XObject 是扫描件承载文字的主要方式 |
| 栅格化（rasterize） | 把矢量页按分辨率渲染成位图，是 OCR 前的必要一步 |
| 版面分析（layout analysis） | 把页切成标题/正文/表格/图注等区域，并推断阅读顺序（reading order） |
| 可微二值化（DB，Differentiable Binarization）/ CTPN（Connectionist Text Proposal Network） | 前者把「哪里是文字」学成分割图再取框，后者用密集小框加连接检测横向文字行，均为业界常见的文字检测思路 |
| CRNN（Convolutional Recurrent Neural Network）/ CTC（Connectionist Temporal Classification） | 前者是卷积循环神经网络识别骨架，后者做不等长序列对齐，常搭配用于文字行识别 |
| 纠偏 / 去噪 / 二值化（deskew / denoising / binarization）、对象存储（object storage）与幂等（idempotency） | 前三者是 OCR 预处理典型操作（摆正、去脏点、转黑白）；对象存储以「键 → 字节」存大对象；幂等指重复执行同一输入不产生额外副作用 |

## 1. PDF 内部结构：为什么「看起来有字」不等于「能提取出字」

### 1.1 物理结构：对象、交叉引用表、内容流

```
startxref → 交叉引用表(xref) → 各对象字节偏移
  ├─ /Catalog（目录）→ /Pages（页面树）→ /Page（页对象）
  │                                  ├─ /Contents → 内容流
  │                                  └─ /Resources → /Font（字体字典）、/XObject（图像等）
  └─ 字体程序流 / ToUnicode CMap 流 / 图像流 ...
```

- **对象（object）**：内容都是编号对象，读取器靠编号引用而非顺序。
- **交叉引用表（xref）**：告诉读取器「第 7 号对象在第 12345 字节处」，这正是「按页范围解析」能成立的前提。
- **内容流（content stream）**：真正画了什么的指令集合，通常经 FlateDecode 压缩，解压后是文本形式的绘制算子。

### 1.2 文字是怎么被「画」出来的

```
BT                          % BT = begin text（开始文本对象）
/F1 12 Tf                   % Tf = set font（选 /F1 字体，字号 12）
72 700 Td                   % Td = move text position（移到坐标 (72,700)）
<00480065006C006C006F> Tj   % Tj = show text（显示一串「字形编码」）
ET                          % ET = end text（结束文本对象）
```

关键认知：`Tj` 后面是**字形编码（code）**，不是 Unicode 字符串。内容流只记「用哪个字体、哪几个字形、画在哪个坐标」，字符语义要靠字体字典里的映射补回来。其他算子：`TJ` 显示带间距调整的文本数组；`Do` 绘制外部对象（如整页扫描图）；`m/l/c/re/f` 画路径（文字「转曲」后就是这些）。

### 1.3 字体与编码：`ToUnicode CMap` 是语义的门

| 字体资源 | 作用 | 缺失后果 |
| --- | --- | --- |
| `/Subtype` | 字体类型（Type1 / TrueType / Type0 / Type3 等） | 读取器选错解码路径 |
| `/Encoding` | 编码方案（WinAnsiEncoding、Identity-H 等） | 编码被误读成别的字符 |
| `/ToUnicode` | 指向 `ToUnicode CMap`，把字形编码映射回 Unicode | **能取到编码但映射不回文字 → 乱码或空** |
| 内嵌字体程序 | 字形轮廓数据 | 只影响显示，不保证可提取 |

`ToUnicode CMap` 里大致是 `<03A9> <03A9>`（编码 → U+03A9「Ω」）这样的映射。子集字体又常把字形名重编号为 `/G1`、`/G2`，若同时缺 `ToUnicode CMap`，提取器拿到的就是一堆无语义编号。

### 1.4 「有文本层」与「扫描件」的本质区别

| 维度 | 原生 / 有文本层 PDF | 扫描件 / 图片型 PDF |
| --- | --- | --- |
| 内容流 | `BT/ET` + `Tj/TJ` + 字体资源 | `Do` + 图像 XObject，或整页一张位图 |
| 文字载体 | 字形编码 + 字体字典 | 像素 |
| 能否选中 / 检索 / 复制 | 能 | 不能 |
| 放大后 | 不失真 | 锯齿、模糊 |
| `extract_text()` 结果 | 文本（可能乱码） | 空字符串或极少量图注 |
| 正确路径 | 直接抽取 + 编码修复 | 栅格化 → OCR |

一句话：**扫描件里根本没有「字」这个对象，只有「字的照片」。** 任何基于文本层的提取器对它只能返回空。

### 1.5 `extract_text()` 返回空或乱码的原因清单

| # | 原因 | 机制 | 表现 |
| --- | --- | --- | --- |
| 1 | 整页是图片 | 只有图像绘制算子，没有文本算子 | `""` |
| 2 | 缺 `ToUnicode CMap` | 编码无法映射回 Unicode | 乱码、问号、私用区字符 |
| 3 | 字形子集 + 自定义编码 | 字形名被重编号，无语义 | 乱码或空 |
| 4 | 文字被矢量化 / 转曲（outline） | 变成路径绘制指令 `m/l/c` | `""`，但视觉上字很清晰 |
| 5 | Type3 字体用图形画字 | 每个「字」是一段绘图小程序 | `""` 或碎片 |
| 6 | 文字藏在 Form XObject / 透明组 | 简单提取器不递归子资源 | 部分文字丢失 |
| 7 | 加密 / 权限限制 / 内容流损坏 | 读取被拒或解码失败 | 抛错或空 |
| 8 | 竖排、旋转、多栏混排 | 抽取顺序与阅读顺序不一致 | 有字但顺序错乱 |

### 1.6 本项目当前基线（已实现）

`backend/app/services/parser.py:77` 的 `parse_range()`：

```python
pages = [PageText(page_no=i + 1, text=reader.pages[i].extract_text() or "", headings=[])
         for i in range(start_page, end)]
```

`PageText`（`parser.py:27`）只带 `page_no`、`text`、`headings`，没有坐标、置信度、来源区分；`ParsedDoc`（`parser.py:34`）的 `source_level` 固定 `"L1"`。

**结论（已实现）**：对有文本层的原生 PDF 可用；对扫描件会**静默产出空页文本**，不报错，也不提示「本页可能需要 OCR」。这正是 §2 要补的判定层。

## 2. 判定「是否需要 OCR」：可量化信号

### 2.1 为什么需要判定，而不是「一律上 OCR」

- OCR 有算力与时间成本、且会**降低**原生 PDF 质量（无损文字被重新识别，反而引入错字、丢字、错序）；混合 PDF 很常见（前几页原生文本、中间几页盖章扫描件、末页又是文本），所以**判定必须是页级的**。

### 2.2 信号清单

| 信号 | 计算方式（示意） | 想抓住什么 |
| --- | --- | --- |
| 可提取字符数 / 页面积 | `len(text.strip())` 与页面面积之比 | 页面是否「无字」或字极少 |
| 字符密度 | 可提取字符数 ÷ 页面面积（按渲染尺寸归一化） | 字少但页面大 → 疑似图片 |
| 空白页比例 | 近空白页数 ÷ 总页数 | 文档级扫描件嫌疑 |
| 图片 XObject 占比 | 图像 XObject 覆盖面积 ÷ 页面面积 | 页面主体是否是一张图 |
| 可搜索文本覆盖率 | 有文本的文本框面积 ÷ 页面面积 | 文字是否只存在于零星图注 |
| 乱码率 | 替换字符 `U+FFFD`、控制字符、私用区字符占比 | 有编码但映射坏了 |

> `PageText` 目前不含坐标与字体信息（`parser.py:27`），故「密度 / 图片占比 / 覆盖率」几项在骨架里属**只设计**，需扩展页级元数据或让解析器回传统计值后才能算。

### 2.3 阈值建议（经验起始值）

> **下表所有阈值均为经验起始值**，用于让人能开始写判定逻辑，**不是实测结论，也不代表本项目跑过任何语料**。上线前须用真实语料（原生 PDF、纯扫描件、混合 PDF、转曲 PDF 各若干）跑分布、画直方图后重新校准。

| 信号 | 起始阈值 | 触发含义 |
| --- | --- | --- |
| 每页可提取字符数 | `< 50` | 疑似无文本层或转曲页 |
| 字符密度（归一化） | `< 0.02` | 字相对页面过少 |
| 空白页比例 | `> 0.30` | 文档级扫描件嫌疑升高 |
| 图片 XObject 面积占比 | `> 0.70` | 页面主体是一张图 |
| 可搜索文本覆盖率 | `< 0.10` | 文字只覆盖零星区域 |
| 乱码率 | `> 0.30` | 编码映射损坏，优先修编码而非 OCR |

反向（「看起来像文本层」）信号，同样为起始值：每页字符数 `>= 200`、乱码率 `<= 0.05`、图片占比 `<= 0.30`。

### 2.4 组合判定逻辑（只设计，示意伪代码）

单信号会误判：「一大图 + 一行图注」有少量文字但主体是图；纯公式页字极少却是原生文本。所以用「投票 + 分层」：

```python
# 只设计：示意逻辑，阈值取自 §2.3 经验起始值，未经真实语料校准
def need_ocr(s):  # s = 页级统计字典
    votes = (s["chars"] < 50) + (s["density"] < 0.02) \
          + (s["image_area_ratio"] > 0.70) + (s["searchable_coverage"] < 0.10) \
          + (s["garbled_ratio"] > 0.30)
    if s["chars"] >= 200 and s["garbled_ratio"] <= 0.05:  # 反向证据否决
        votes -= 2
    return votes >= 2, min(abs(votes) / 3.0, 1.0)  # 是否需 OCR、示意置信度
```

分两层：**页级判定**决定该页走抽取还是 OCR，结果写回 `source_level`；**文档级聚合**在空白页比例超阈值时给整篇打「扫描件嫌疑」标签，用于调度优先级与用户提示，但不覆盖页级结论。

## 3. OCR 原理链：五步，以及每步「做不好会怎样」

### 3.0 全链概览

```
输入位图 → ① 预处理 → ② 版面分析（区域 + 阅读顺序）→ ③ 文字检测（DB / CTPN 类思路）→ ④ 文字识别（CRNN+CTC / Transformer 类思路）
        → ⑤ 后处理（纠错 + 坐标回写 + 顺序串接）→ 带坐标文本行 → 对齐到 PageText / ChunkSpec
```

### 3.1 ① 预处理：去噪、纠偏、二值化

- **为什么需要**：扫描件常有噪点、摩尔纹、倾斜、光照不均、装订阴影，会被下游当成笔画。
- **做不好会怎样**：不纠偏 → 文字行基线倾斜，检测框歪、切行错；不去噪 → 噪点被当成小字，冒出大量「·」「丶」垃圾字符；二值化阈值不当 → 细笔画被抹掉（衬线、细体）或墨块粘连（相邻字连成一团）。
- **常见做法**：灰度化 → 自适应二值化 → 投影/霍夫估倾角并旋转 → 形态学去噪。印章盖字、彩色底纹对参数很敏感，须按语料调。

### 3.2 ② 版面分析：区域检测与阅读顺序

- **为什么需要**：OCR 只认「一行字」，不认「哪块是标题、哪块是表、先读哪一栏」。
- **做不好会怎样**：区域漏检 → 表格/图注被当正文塞进段落；阅读顺序错 → 双栏文档左右栏交替拼接，语义断裂，RAG 命中即错答；表格没被单独切出 → 按行线性化后行列关系全丢（见本系列表格专题）。
- **常见做法**：投影/连通域等规则，或版面检测模型，输出带类别与层级的区域框，再按「先上后下、先左后右、跨栏合并」推断顺序。

### 3.3 ③ 文字检测：DB / CTPN 类思路

- **为什么需要**：先定位「哪里有字、每行占哪个框」，识别器才能逐行喂图。
- **做不好会怎样**：漏框 → 整行文字直接消失（最致命，下游无从补救）；框过松 → 邻行或表格线被框进来，串进噪声；框过紧 → 切掉上下延伸笔画（声调、上下标）；长行被断开 → 一行碎成两段，顺序与语义一起坏。
- **常见思路**：DB（可微二值化）把文字区域学成分割图再取轮廓，对不规则形状较友好；CTPN（连接文本提议网络）用密集小框加连接，对横向长行较友好。此处只描述**业界常见思路**，不代表本项目选型或实现。

### 3.4 ④ 文字识别：CRNN + CTC / Transformer 类思路

- **为什么需要**：把文字行图块映射成字符序列，这是「像素 → 文本」真正发生的一步。
- **做不好会怎样**：形近字混淆（「己/已/巳」「0/O」「1/l/I」）→ 编号与金额错，对财务报表是硬伤；不等长对齐失败 → 漏字、重字、乱序；中英混排、竖排、公式、手写 → 错字率上升；没有逐字符置信度 → 下游不知道哪个字不可信，也就无法做升级策略。
- **常见思路**：CRNN（卷积循环神经网络）提特征 + CTC（连接时序分类）做不等长对齐；也有基于注意力 / Transformer 的序列识别。中文大字符集与生僻字是常见难点。

### 3.5 ⑤ 后处理：语言模型纠错、坐标回写、顺序串接

- **为什么需要**：识别器逐行独立输出、缺上下文；RAG 又需要「这句在原文哪一页哪一块」用于溯源。
- **做不好会怎样**：不纠错 → 「己经」「l0O 万」直接进向量库，永远匹配不到正确写法；不回写坐标 → 回答给不出页码/区域引用，「可溯源」就讲不出来；不按顺序串接 → 分块把不相邻段落拼一起；纠错过度 → 语言模型把专业术语、产品型号「改」成常见词，属静默数据损坏。
- **常见做法**：词典 / n-gram 或轻量语言模型做受限纠错（只改高置信度的明显错）、保留原串与新串两份、把每行包围盒（bounding box）随文本一起写入中间产物。

### 3.6 输出契约（只设计）

OCR 不应只返回字符串，理想最小输出是「带坐标的文本行」：

```json
{"page_no": 7, "source_level": "ocr",
 "lines": [{"text": "合计", "bbox": [72, 700, 130, 718], "confidence": 0.93, "order": 3}]}
```

`bbox`（包围盒）、`confidence`（置信度）、`order`（阅读顺序序号）分别支撑溯源、降权、顺序串接。把它们对齐到 `PageText`（页文本）与 `ChunkSpec.confidence`（置信度）是**只设计**的适配工作，骨架尚未实现。

## 4. 分支处理：扫描件、图片 PDF、多页大文件

### 4.1 三类分支与处置路径

本项目把解析能力分两层：**P1（收费 OCR 层，负责精确取字）** 与 **P2（多模态兜底层，负责版面 / 图表语义）**，两者状态不同，不可混为一谈。

| 分支 | 识别依据 | 处理路径 | 三态 |
| --- | --- | --- | --- |
| 有文本层 PDF | 字符数/乱码率达标 | `extract_text()` + 编码修复 | 已实现（抽取部分） |
| 扫描件 PDF | 页级判定为图片型 | 逐页栅格化 → OCR（精确文字）→ 坐标回写 | 只设计（P1 未接通） |
| 图片型文件（单图 / 多图） | `mime_type`（MIME 类型）为图像 | 精确文字 / 数字以 OCR 为准；版面与图表语义可走 P2 多模态兜底 | OCR 只设计 / P2 已接通 |
| 混合 PDF | 部分页文本层、部分页扫描 | 页级分别走上述路径后合并 | 只设计 |

> **关于「解析图片」的边界（已按 2026-11-14 网关实测修订）**：后端网关**具备视觉输入能力的模型已接通 P2 多模态兜底**（实测见 §6.2.1），「把图片交给多模态模型理解」这条路是存在的；但 **P1 收费 OCR 仍未接通**。技术判断必须保留并强化：图片里的**精确文字与数字仍应以 OCR 结果为准**，视觉模型适合版面 / 图表语义，不应用来复述关键数值 —— 视觉理解能答对演示图里的 `73492`，不等于能稳定抄准财报里的金额。多文件批量上传时每个文件有独立 `object_key`（对象存储键）与 `document_id`（文档标识），天然互不干扰，并发由任务队列承载；但批量入口是否已覆盖图片 MIME 属集成层工作，本文不宣称已实现。

### 4.2 扫描件 PDF：栅格化再 OCR

每页先按约定分辨率栅格化（过低丢笔画、过高徒增算力，须按语料权衡）→ 走 §3 全链 → 产出带坐标文本行 → `source_level`（来源层级）标为 `ocr`，与原生文本层页区分，便于整体降权或提示复核。这条精确取字路径依赖 P1，**当前未接通**。

### 4.3 图片型文件：少一步探测

单张图片或「每页一张图」的 PDF 没有文本层可探，跳过 §2 的乱码判定。这里分两条路：**精确文字 / 数字**走 OCR，而 **P1 收费 OCR 仍未接通**（属只设计）；**版面 / 图表语义**可走已接通的 P2 多模态兜底（`image_url` 以 data URI 传入图像，实测见 §6.2.1），`structured_fallback()`（结构化降级）只保留为调用失败时的兜底，不作主路径。这一步呼应「支持解析图片」与「支持多文件」的诉求。

### 4.4 多页大文件：按页范围并行（已实现的工程骨架）

这是本项目**已经写好、可以直接讲**的部分。用户说「支持多文件、大文件」，关键不在「一次读完」，而在「切开、并行、落盘、合并」。调度入口 `backend/app/tasks/ingest.py:96`（`enqueue_ingest`）：

```python
needs_split = is_large and page_count > settings.LARGE_FILE_PAGE_THRESHOLD
if needs_split:
    step = settings.PARSE_PAGE_BATCH
    ranges = [(s, min(s + step, page_count)) for s in range(0, page_count, step)]
    header = group(parse_page_range.s(ctx, start, end).set(queue="ingest_heavy")
                   for start, end in ranges)
    body = chain(merge_parsed.s(ctx).set(queue="ingest_heavy"), *tail.tasks)
    result = chord(header)(body)
```

要点：先 `probe_page_count()`（`parser.py:65`）拿总页数，按 `PARSE_PAGE_BATCH`（每批页数）切 `ranges`（页范围列表）→ `group` 把每片变成独立子任务投到 `ingest_heavy` 队列并行 → `chord` 全部完成后回调 `merge_parsed`，继续同一条下游链（分块 → 向量化 → 索引），下游对「大文件」无感。

页级子任务 `backend/app/tasks/ingest.py:242`（`parse_page_range`）：

```python
parsed = parse_range(ctx["object_key"], ctx["mime_type"], start_page, end_page)
key = _intermediate_key(ctx["tenant_id"], ctx["document_id"],
                        f"pages-{start_page:05d}-{end_page:05d}.json")
_put_json(key, _pages_to_dict(parsed))
```

只解析自己那段 `[start_page, end_page)`，独立重试，某几页失败不影响其他页；文件名带零填充页范围（`pages-00000-00050.json`），合并时靠它排序保证阅读顺序（`ingest.py:266`）；Redis 计数器上报「已完成页 0-50」。合并回调 `merge_parsed`（`ingest.py:262`）：按文件名页范围排序 → 再按 `page_no` 排 → 合并为一份 `parsed.json` → 清理中间分片（失败不阻断主链路）。

### 4.5 中间结果落对象存储，避免内存爆炸

`_temp_file()`（`backend/app/services/parser.py:54`）与 `_put_json()` / `_intermediate_key()`（`ingest.py:43`）是同一原则的两处体现：

```python
def _temp_file(object_key: str) -> Path:
    """流式写临时文件，内存占用恒定为 1MiB。"""
    store = get_object_store()
    tmp = Path(tempfile.gettempdir()) / f"kb_{abs(hash(object_key))}{suffix}"
    with tmp.open("wb") as out:
        for block in store.stream(object_key):   # 逐块拉取，不 get() 整文件
            out.write(block)
    return tmp
```

- **绝不把整个文件读进内存**：`store.stream()` 逐块写本地临时文件，内存占用由块大小而非文件大小决定；解析完 `tmp.unlink(missing_ok=True)` 清理。
- **中间产物不经过 Celery result**：解析/分块结果以 JSON 写入对象存储的 `intermediate` 前缀，任务间只传 `parsed_key`（解析结果对象键）、`chunks_key`（分块结果对象键）这类短字符串，避免大对象撑爆 Redis。
- 这条原则对 OCR 与视觉兜底同样成立：中间位图、逐行结果、传图请求也应按页落盘，不能攒在 worker 内存里。**P1 收费 OCR 链未接通、P2 多模态兜底已接通，但「流式 + 按页落盘 + 只传键」的骨架已实现**，是接入更强解析器时必须复用的工程约束。

### 4.6 页级幂等与失败隔离

中间键按页范围命名（`pages-{start:05d}-{end:05d}.json`）保证重复写不产生新数据（幂等）；子任务独立 `autoretry`（`_task_kwargs()`，`ingest.py:188`）让单页失败只重试该片；阶段台账 `IngestJob` + `report_stage()` 使失败阶段可查、前端可一键重试；`merge_parsed`（`ingest.py:279`）合并后清理分片，失败不阻断主链路。

### 5.3 适配器契约草案（只设计）

「可插拔」的落点：把「怎么把一页变成文本」抽象成后端（backend），下游 `PageText` / `ChunkSpec` / Milvus schema / citation 契约都不用改。

```python
# 只设计：契约草图，不在仓库中，不代表已实现
class ParserBackend:
    name: str
    capabilities: set[str]        # {"text_layer", "ocr", "layout", "table", "vision"}
    def probe(self, object_key, mime_type) -> dict: ...   # 页级统计，供 §2 判定
```

## 6. 四段式收尾：原理 → 本项目怎么落 → 评审怎么讲 → 诚实边界

### 6.1 原理

PDF 存的是「字形编码 + 绘制坐标」，不是 Unicode 字符串；`ToUnicode CMap`（字符映射表）把编码翻译回文字，缺了它就乱码，压根没有文本算子（扫描件或转曲）就返回空。OCR 是把像素重新变成文字的链路：预处理弄干净图 → 版面分析定区域与阅读顺序 → 检测框出行 → 识别转成串 → 后处理纠错并回写坐标。判定「要不要 OCR」必须页级、多信号、可校准；大文件的解法是切开并行、逐块流式落盘、任务间只传对象键。

### 6.2 本项目怎么落（三态对齐）

| 事项 | 状态 | 落点 |
| --- | --- | --- |
| 原生 PDF 文本抽取 | **已实现** | `parser.py:77` `parse_range()` + pypdf |
| 按页范围并行 / chord 合并 / 中间产物落对象存储 / 流式临时文件 | **已实现** | `ingest.py:96,242,262` / `parser.py:54` |
| P2 多模态兜底（视觉语义，非精确取字） | **已实现**（P2 已接通） | §6.2.1 实测；`PARSING_VISION_*` / `DISCOVERY_*` 配置 |
| `source_level`、`confidence` 字段位 | **已实现（字段）/ 只设计（取值）** | `parser.py:38,50` |
| OCR 需求信号判定、页级分支、坐标元数据 | **只设计** | §2 / §3.6 |
| `ParserBackend` 可插拔适配器 | **只设计** | §5.3 |
| P1 收费 OCR 接入、真实 OCR 引擎、阈值语料校准、生产级视觉质量评测 | **未做** | §5.2 / §4.1 |

一句话：**工程骨架已经通了（能切、能并行、能落盘、能合并），P2 视觉语义兜底也已接通；但精确取字依赖的 P1 收费 OCR 仍留在契约层，且整体尚未做质量基线评测。**

### 6.3 评审怎么讲（2–3 句）

「PDF 里存的是字形编码和坐标而不是文字本身，所以扫描件 `extract_text()` 必然返回空、缺 `ToUnicode CMap` 必然乱码 —— 我会先用字符数、图片占比、乱码率做页级判定，只有真缺文本层的页才走 OCR。OCR 不是一步，是预处理、版面分析、检测、识别、后处理五步链，其中版面分析和坐标回写直接决定 RAG 能不能溯源；大文件则按页范围用 chord 并行、中间结果只以对象键在任务间传递，避免内存和 Redis 被撑爆。另外 P2 多模态兜底虽已接通，我只让它做版面 / 图表语义，精确文字与数字一律以 OCR 为准 —— 视觉理解跑通不等于可以拿它抄金额。」

### 6.4 诚实边界

1. 当前**扫描件 PDF 会静默解析成空文本**，不产生可读内容，也不提示「本页需 OCR」—— P1 收费 OCR 链未接通。
2. **P2 多模态兜底已接通且经双图对照实测**（§6.2.1），但这只是功能连通性，**不是质量基线**；未做真实语料集评测、未做压测，也不代表具备生产级 OCR 质量。**图片里的精确文字与数字仍应以 OCR 结果为准**，视觉模型适合版面 / 图表语义，不应用来复述关键数值。
3. **P1 收费 OCR 未接通**，凭证未提供，接口地址、鉴权、请求/响应结构、配额、错误码、模型版本、价格一律 `__TBC__`；P2 的连通不代表 P1 已接通。
4. §2.3 阈值是**经验起始值**，未经真实语料校准，不是实测结论；§3 的 DB / CTPN / CRNN+CTC / Transformer 都是**业界常见思路**，不代表本项目选型或实现。
5. §4 的并行、落盘、幂等属于**入库可靠性**，不等于 OCR 识别质量；「任务不丢」和「字认得准」是两件事。
