## 一、原理：异步链路与进度真值

### 1.1 七步链路

多文件 / 大文件上传不能同步等，必须拆成异步流水线：

```text
分片上传 → 落对象存储 → 任务入队 → 按页范围并行 → 中间结果合并 → 向量化 → 状态回写
```

| 步 | 做什么 | 真值在哪 | 失败怎么办 |
| --- | --- | --- | --- |
| 1 分片上传 | 大文件切片传输，支持续传 / 秒传 | 上传会话（`UploadSession`） | 断点续传，缺失分片重传 |
| 2 落对象存储 | 原文件与中间产物落对象存储，**不走 Celery result 传大对象**（避免撑爆 Redis） | 对象存储 key | 重放入队即可 |
| 3 任务入队 | 按 `is_large`（是否大文件）分 `ingest` / `ingest_heavy` 双队列 | `IngestJob` 台账 | 失败可一键重试 |
| 4 按页范围并行 | 大文件用 `chord` 把页范围拆成多个 `parse_page_range` 分片并行 | 各分片中间产物 | 分片独立重试，不影响其他页 |
| 5 中间结果合并 | `merge_parsed` 按文件名里的页范围排序后合并，保证阅读顺序 | 合并后的 `parsed.json` | 合并失败可重建 |
| 6 向量化 | `chunk_document → embed_and_index`，先写 PG 文本再写 Milvus 向量 | PG + Milvus | 向量写失败不回滚文本，交每日对账补齐 |
| 7 状态回写 | `finalize_document` 回写文档状态，`finalize_batch` 重建权威快照并广播完成 | PG | 从 PG 重建 |

以上链路在 `backend/app/tasks/ingest.py` 里是**成型的框架骨架** `【已落地·框架骨架】`：`enqueue_ingest()` 双队列、`parse_page_range` 页级并行、`merge_parsed` 合并、`IngestJob` 重试台账、`retry_failed_job` 前端一键重试，都是可读的真实代码。

### 1.2 PG 真值 / Redis 实时通道 / Redis 快照：三层分工

`backend/app/services/progress.py` 开头就把分层写死了 `【已落地·框架骨架】`：

| 层 | 职责 | 特点 |
| --- | --- | --- |
| PostgreSQL（`IngestJob` / `BatchUpload` / `UploadSession`） | **进度真值**、状态、重试台账 | 可重建、可审计；worker 崩溃、浏览器刷新、Redis 重启都不丢 |
| Redis pub/sub（`progress_channel`） | **实时推送**，前端 SSE 订阅 | 毫秒级、不落库 |
| Redis snapshot（`progress_snapshot_key`） | **断线重连时立刻给最近一次快照** | 避免进度回退 / 空白进度条 |

三条关键机制：

- **节流**：`PROGRESS_THROTTLE_SECONDS`（中文说明：进度写库节流秒数）对高频小事件做节流，但「阶段切换 / 完成 / 失败」三类事件**强制落库**——高频小事件不压垮业务库，关键状态又绝不丢。
- **权重可解释**：`compute_document_progress` 把「分片传输」与「后端入库」按阶段权重合成一个 0~100 的文档进度；`compute_batch_progress` 按文件体积加权，避免一个超大 PDF 和一个 2KB 文本各占一半进度。
- **权威快照**：`build_snapshot` 从 PG 重建完整进度快照，SSE 重连、轮询降级、任务中心都用它；`snapshot_from_cache` 在建连瞬间先发一条缓存快照，避免用户盯着空白进度条。

### 1.3 SSE 进度推送与断线重连

```text
建连 → 先发 snapshot_from_cache（缓存快照，避免空白）
     → publish_progress 每条事件带自增 seq（用作 SSE 的 id）
     → 事件类型：progress / done / batch
断线 → 浏览器带 Last-Event-ID 重连
     → 服务端按 seq 续传；必要时用 build_snapshot 从 PG 重建权威快照
     → 进度不回退、不丢状态
```

`publish_progress` 返回自增 `seq`（中文说明：事件序号，来自 Redis `INCR`），正是为 `Last-Event-ID` 续传准备的 `【已落地·框架骨架】`。这一层还埋了一个和「部门」有关的设计伏笔——**进度 key 不带部门**，留到 2.4 讲。

### 1.4 双队列（light / heavy）划分理由

| 维度 | `ingest`（light，轻队列） | `ingest_heavy`（heavy，重队列） |
| --- | --- | --- |
| 触发 | `is_large = false` 普通文件 | `is_large = true` 大文件 |
| 执行 | 单条 `chain` 顺序执行 | `chord` 按页范围并行后再合并续链 |
| 占用 | 短、交互式 | 长、批量占 worker |

**为什么要拆**：大文件按页并行会长时间占住 worker。若和小文件挤同一队列，一个几百页的扫描件就能把「秒级可完成」的交互小任务**饿死**。拆双队列 + 各自并发上限，做的是**隔离与背压**，让两类任务互不拖累。

- **大文件阈值**：`is_large`（是否大文件）由上传侧判定；是否进一步拆分页范围由 `LARGE_FILE_PAGE_THRESHOLD`（中文说明：大文件拆分页数阈值）决定，分片步长由 `PARSE_PAGE_BATCH`（中文说明：每次解析的页批大小）决定。源码注释里对「大文件」有既有口径描述，**具体数值以 `settings` 配置为准、属演示默认值需用真实语料与压测校准**，本篇不写死 MB / 页数结论。`【占位·配置值待校准】`
- **并发与背压**：`webapp/queue.py` 的 `MAX_CONCURRENT_INGEST = 2`（中文说明：演示切片最大并发入库数）刻意设小，用进程内信号量制造「上传分析繁忙，请排队」的真实体感 `【已落地·演示替身】`；框架骨架侧则由 worker 并发上限形成天然背压 `【已落地·框架骨架】`。
- **优先级**：light 队列优先保证交互小文件；heavy 可被降级 / 限流；再叠加部门维度的公平调度（见 2.3）。

### 1.5 失败重试、指数退避、幂等键、卡死检测

| 机制 | 落地情况 `【已落地·框架骨架】` | 说明 |
| --- | --- | --- |
| 重试与退避 | `_task_kwargs` 的 `autoretry_for` / `retry_backoff` / `retry_backoff_max` / `retry_jitter` / `max_retries` | 指数退避 + 抖动 + 次数上限，避免重试风暴 |
| 超时 | `soft_time_limit` / `time_limit` | 软 / 硬超时双保险 |
| 异常出口 | `_stage_guard` | 把「重试中 / 最终失败 / 心跳」统一写进 `IngestJob` 台账，记 `failed_stage` 与 `error` |
| 幂等键 | `chunk.id = uuid5(doc_id, version_no, seq)`；`IngestJob.idempotency_key` | 跨 PG / Milvus 幂等，重试不产生重复向量 |
| 一键重试 | `retry_failed_job` | 复用同一 `document_id` 与 version，前端触发 |
| 心跳 | `IngestJob.heartbeat_at`（`report_stage` 写入） | 供卡死判断使用 |
| 卡死检测 | `【占位·设计】` | 思路：看门狗扫描 `heartbeat_at` 超时任务 + 软/硬超时兜底；**当前未声称已有完整看门狗**，属设计 / 待补 |

> 幂等是这条链路的可靠性地基：`uuid5` 让「同一文档同一版本同一分块序号」永远得到同一个 id，重试、合并、对账都据此收敛。

## 二、本项目怎么落：多部门维度与口径对齐

### 2.1 口径前提：部门是「归因与配额标签」，不是隔离边界

| 维度 | 部门（本项目口径） | 多租户（**明确不做**） |
| --- | --- | --- |
| 作用 | 归因、配额、成本、公平调度 | 数据 / 索引 / 权限**强隔离** |
| 边界强度 | 不隔离数据，只是标签 | 强隔离，跨租户不可见 |
| 进度 key | **不带部门**（见 2.4） | — |
| 组织模型 | 单组织 + 多用户多部门 | 多组织并存 |

> 一句话：**不实现多租户 ≠ 没有部门维度**。这是两个不同层的问题。权限 / 可见性边界是另一套机制，本篇不展开。

### 2.2 部门作为归因与配额标签

- 任务入队时把 `department_id`（中文说明：部门标识）作为**事件发生时的快照**写进台账 / 成本记录，用于按部门聚合配额与成本。`【占位·演示维度】`
- 承载点已部分存在：`embed_and_index` 从 `doc.department_id` 取出 `dept_id`（中文说明：部门标识，写入分块的归因字段）并写进 chunk `【已落地·部分维度】`。这正对应「webapp 演示切片已按 department 口径对齐统计维度」。
- 配额按**部门**聚合，不按 `tenant_id`；成本与限流统计维度已从 tenant 改为 department（团队既有交付事实）。

### 2.3 按部门排队 / 加权公平调度（防单点打爆）

`【占位·设计】`，只讲思路，不给实测数字：

- **共享 worker 池**，按部门维护虚拟子队列，用**加权公平队列**思路（加权轮询 / deficit 之类）决定下一个取谁的任务；权重按部门配额 / 规模配置，具体值 `__TBC__` / 待定。
- **每部门在途上限 + 信号量**：某部门一口气上传一批扫描件时，最多占用自己的份额，**不会占满全部 worker**，其他部门仍有可用额度。
- **先粗分再细分**：先按 light / heavy 双队列分流，再在每层内部做部门公平。二维复杂度被拆成两次一维决策，避免调度逻辑失控。
- 与预算闸门联动：某部门升级页过多时，先撞 05 篇的 `VISION_ESCALATION_RATIO` 熔断线，再撞部门配额，双重护栏。

### 2.4 进度 key 为什么不带部门（重点）

`progress_channel`（中文说明：SSE 频道）、`progress_snapshot_key`（中文说明：进度快照键）、`progress-seq`（中文说明：进度事件序号）等键以 `batch_id`（中文说明：上传批次标识）为主，**不拼 `department_id`** `【已落地·框架骨架 + 设计如此】`。

理由：

- 用户**转岗 / 部门调整是常态**。若进度 key 带部门，转岗后订阅的频道名就变了 → SSE 断连、进度丢失、要重新订阅。
- 一个 `batch_id` 是**一次上传会话**，跟「谁发起」绑定一次即可；部门变化不应影响在途任务的进度通道。
- 因此：**部门进「成本 / 配额台账」，不进「实时通道键」**。这是**归因与通道解耦**——一个维度负责「事后算账」，一个维度负责「此刻推进度」，互不污染。

### 2.5 成本按事件发生时的部门快照记，且不回溯

- 每次计费 / 配额事件记录 `department_id_at_event`（中文说明：事件发生时的部门快照）。`【占位·演示维度】`
- 用户后续转岗，**不回写、不重算**历史成本；否则历史报表会随组织变动漂移，无法审计。
- 与 2.4 呼应：进度 key 干脆不带部门；台账里带了就**冻结成快照**。一个「不进键」，一个「进了就锁」，共同保证进度不断连、账目不漂移。

### 2.6 明确写清技术债口径

> **当前 backend 的 `tenant_id` 是历史命名技术债，webapp 演示切片已按 department 口径对齐统计维度，但完整 13 步数据模型改造尚未执行。**

展开成命名对照表：

| 历史键名 | 中文 | 目标语义 | 状态 |
| --- | --- | --- | --- |
| `tenant_id` | 历史租户标识 | 单组织下退化为组织 / 命名空间，**不再表示多租户** | `【已落地·技术债，未重命名】` |
| `tenant_key()` | Redis 键前缀函数 | 保留兼容，语义为命名空间 | `【已落地·技术债】` |
| `progress_channel(tenant_id, batch_id)` | SSE 频道构造 | 仍用历史命名，但**不带部门**（设计如此） | `【已落地】` |
| `IngestJob.tenant_id` / `Chunk.tenant_id` | 台账 / 分块上的历史字段 | 待数据模型改造收敛 | `【已落地·技术债】` |
| `department_id` / `dept_id` | 部门标识 | 归因 / 配额 / 成本维度 | `【已落地·部分写入点已带】` |
| 完整 13 步数据模型改造 | 字段重命名、迁移、索引、回归用例等 | 统一到 department 口径 | `【未接通·尚未执行】` |

> 说明：`tenant_key` / `progress_channel` / `IngestJob` 等仍是历史命名（`【已落地】` 事实），webapp 侧统计维度已按 department 对齐（`【已落地·演示切片】`），但**完整 13 步数据模型改造尚未执行**（`【未接通】`）。本篇不假装它已完成，也不把 `tenant_id` 讲成「还在做多租户」。

## 三、面试怎么讲

**30 秒版**

> 「上传是七步异步链路：分片、落对象存储、入队、按页并行、合并、向量化、回写。进度是三层——PG 存真值、Redis pub/sub 推实时、Redis 快照做断线重连。大文件拆 light/heavy 双队列防饿死。部门只是归因与配额标签，不是隔离边界；进度 key 特意不带部门，因为转岗不该让 SSE 断连。」

**2 分钟版**（按顺序）

1. 画七步链路，点出「中间产物落对象存储、不走 Celery result 传大对象」这个细节。
2. 讲三层分工：真值 / 实时 / 快照，再补节流（高频小事件不落库，阶段切换/完成/失败强制落库）。
3. 讲 SSE 断线重连：建连先发快照、`seq` 当 `Last-Event-ID`、必要时从 PG 重建。
4. 讲双队列与背压：大文件按页并行会饿死小任务，所以拆开；演示切片用 `MAX_CONCURRENT_INGEST = 2` 制造排队体感。
5. 讲可靠性：指数退避 + 抖动、`_stage_guard` 统一异常出口、`uuid5` 幂等键、心跳（卡死检测属设计待补）。
6. 收在多部门：部门是标签不是边界、加权公平防打爆、**进度 key 不带部门**、成本按事件快照不回溯，最后主动亮 `tenant_id` 技术债与 13 步改造未执行。

**高频追问与应答**

| 追问 | 应答要点 |
| --- | --- |
| 「PG 和 Redis 各干嘛？」 | PG 真值、Redis pub/sub 实时、Redis 快照断线重连，三层分工。 |
| 「断线重连进度会回退吗？」 | 不会：先发缓存快照 + `Last-Event-ID` 续传 + 必要时 PG 重建。 |
| 「大文件为什么拆双队列？」 | 按页并行长占 worker，会饿死交互小任务；拆开做隔离与背压。 |
| 「进度 key 为什么不带部门？」 | 转岗后频道名变了会断连；批次跟发起者绑一次即可，部门只进台账。 |
| 「成本按哪个部门记？」 | 按事件发生时的部门快照，不回溯、不随转岗重算。 |
| 「你们做了多租户吗？」 | 明确不做，单组织多部门；`tenant_id` 是历史命名技术债，13 步改造未执行，如实说。 |
| 「怎么防一个部门打爆 worker？」 | 加权公平队列 + 每部门在途上限，先 light/heavy 粗分再部门细分。 |

## 四、诚实边界

- **演示切片用的是进程内 `threading.Semaphore` + SQLite**（`webapp/queue.py`，`MAX_CONCURRENT_INGEST = 2`），是 Celery 的**演示级替身**，**不是真 Celery / Redis 集群**；backend 侧 Celery / Redis 代码是**框架骨架源码**，二者不要混为一谈。
