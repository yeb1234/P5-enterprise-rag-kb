## 1. 先认清坐标：你手上是什么

| 维度 | 现在（`webapp/`） | 生产要求 | 差在哪 |
|---|---|---|---|
| 存储 | **真 PG 16 单实例**（SQLite 已移除，连接每次新建、无连接池） | PostgreSQL 主从 + 备份 + PITR | 主从/备份/PITR/连接池 |
| 向量 | **Milvus 2.5.10 已迁入 83 条**，但主链路仍读 PG 文本列 | Milvus 集群 + 索引 + 对账 | 召回接入、索引策略、对账 |
| 队列 | 进程内 `deque` + 单协程 | Celery + Redis broker + 多 worker | 重启丢任务、无法横向扩 |
| 限流 | 进程内滑动窗口（可选 Redis） | Redis Lua 原子窗口 | 多副本各算各的 = 配额翻倍 |
| 监控 | `/metrics` 文本端点 | Prometheus + 告警 + 值班 | 没人看 = 等于没有 |
| 安全 | 规则级 PII + 参数化 SQL | 等保/WAF/审计留痕/密钥托管 | 合规资质 |
| 部署 | `docker compose up` | 反向代理 + TLS + 进程守护 | 单点故障 |

**关键认知**：这些不是「优化项」，是**四类不同的风险**——
丢数据（01/05）、撑不住（02）、被刷穿（03）、看不见（04）、不合规（06）。
它们之间**有严格依赖**，顺序错了会返工。

## 2. 依赖关系：为什么不能并行乱做

```
                    ┌─────────────────────────────┐
                    │ 01 数据迁移（PG + Milvus）   │  ← 地基
                    └──────────────┬──────────────┘
                                   │ 没有真 PG，后面全是空谈
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
    ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
    │ 05 备份与灾备     │  │ 02 压测与容量     │  │ 03 多副本限流     │
    │ （依赖 PG 的 WAL）│  │ （依赖真实存储）  │  │ （依赖 Redis）    │
    └────────┬─────────┘  └────────┬─────────┘  └────────┬─────────┘
             │                     │                     │
             └─────────────────────┼─────────────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │ 04 监控与告警（观测前面三项）│
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │ 06 备案 / 证书 / 等保        │  ← 只有要对外才需要
                    └─────────────────────────────┘
```

**三条硬依赖**（不看会返工）：

1. **`05` 必须等 `01`**。备份策略取决于存储引擎：SQLite 是「拷文件要停写或用备份 API」，
   PG 是「`pg_basebackup` + WAL 归档做 PITR」。在 SQLite 上设计 PITR 是白做。
2. **`02` 必须等 `01`**。压测 SQLite 得到的 QPS 数字，对 PG 毫无参考价值 ——
   SQLite 是**单写者**模型，写并发天然为 1。压它只能得到「串行有多快」，不是「系统能扛多少」。
3. **`03` 的 Redis 必须等 `01` 的 infra**。两者共用 `docker-compose.infra.yml` 里的 Redis 实例；
   先起 Redis 再改限流，比反过来省一次环境折腾。

**可以不做的**：`06` 只在**对外提供服务**时才需要。纯内部试用、评审演示、本地开发，
备案和等保都是零收益。**不要为了「看起来完整」去办备案。**

## 4. 三阶段路径（按「你现在想干什么」选）

### 阶段 A：本地跑通 + 评审演示（**当前状态，已完成**）

- 需要：`docker compose up`、`python -m uvicorn webapp.main:app --port 8765`
- 六项里只需要 **`04` 的 `/metrics` 端点**（证明你懂可观测，不需要真接 Prometheus）
- 验收：`webapp/selftest.py` 33/33、`demo/selftest.py` 16/16
- **不要做**：备案、等保、多副本、压测报告 —— 收益为零

### 阶段 B：小规模真实使用（10–50 人，单机）

目标：**能承受真实用户，且出问题能定位**。

| 顺序 | 做什么 | 为什么这个顺序 | 验收判据 |
|---|---|---|---|
| 1 | `01` 迁到 PG（先不迁 Milvus，向量留 SQLite） | PG 是并发写的前提；向量可以后补 | 逐表行数一致 + e2e 全绿 |
| 2 | `05` 配 `pg_dump` 每日全备 + 保留 7 天 | 有数据了就必须能恢复 | **手工恢复到一个空库并跑通查询** |
| 3 | `04` 接 Prometheus + 至少 3 条告警（5xx / P99 / 磁盘） | 没监控时故障靠用户投诉发现 | 拔掉数据库能收到告警 |
| 4 | `02` 用真实流量分布压一次 | 现在才知道 `MAX_INFLIGHT` 该设多少 | 有 P99 曲线，不是单个数字 |
| 5 | `03` 只在**要多副本时**才做 | 单副本时进程内限流就够 | 双副本下配额不翻倍 |

**单机阶段的容量上限判断**：SQLite → PG 后，瓶颈通常先出现在**模型调用**（外部 API 延迟 1–10s），
不是数据库。所以 `02` 压测要**分层注入**（只压检索 / 只压上传 / 只压问答），混着压得到的数字没法归因。

### 阶段 C：对外提供服务（要域名、要备案）

在阶段 B 全部完成后，追加：

| 顺序 | 做什么 | 前置 |
|---|---|---|
| 1 | 买域名 + 实名 | 需要主体证件 |
| 2 | `06` ICP 备案（**服务器在大陆才需要**） | 域名 + 大陆服务器 |
| 3 | `06` TLS 证书（Let's Encrypt 免费，配自动续期） | 域名已解析 |
| 4 | 反向代理（Nginx/Caddy）+ **只暴露 443** | 证书 |
| 5 | 判断是否需要等保 | 看行业与数据敏感度，见 `06` §4 |

**备案的硬约束**：备案期间**网站不能对外提供内容**（会被驳回）。所以要**先备案、后上线**，
不要先开站再补备案。这一步通常 7–20 个工作日，是整条路径上**唯一不能压缩的等待**。

## 5. 成本估算（月度，人民币，**区间估算非报价**）

按「单机 4C8G + 托管 PG + 对象存储 + 外部 LLM API」估：

| 项 | 区间 | 说明 |
|---|---|---|
| 云服务器 4C8G | ¥150–400 | 包年更便宜；突发性能型更省但压测不可用 |
| 托管 PG（2C4G） | ¥200–600 | 也可以自建在同一台机器上，省这笔但要多做备份 |
| 对象存储 + 流量 | ¥10–100 | 取决于上传量；图片/PDF 是大头 |
| 域名 | ¥30–80/年 | — |
| TLS 证书 | ¥0 | Let's Encrypt 免费 |
| **LLM API（大头）** | **¥100–3000+** | 完全取决于用量与模型。演示档 `minimax-m3` 便宜；`deepseek` 推理档贵数倍 |
| Milvus | ¥0（自建）– ¥800（托管） | 10 万级切片自建单机够用 |
| 备案 | ¥0 | 官方免费，代办收费 |
| 等保测评 | ¥2–8 万 | **一次性**，只在需要时做 |

**省钱的三条**：
1. **LLM 是唯一会失控的成本**。所以本项目做了 `budgets` 表 + `check_budget()` + 按 `department_id`
   的事件快照 —— 不是「记账好看」，是**防止一张账单打爆**。
2. **向量库先别上托管**。10 万切片以内，Milvus standalone 单机完全够；等到召回延迟成为瓶颈再说。
3. **监控先用手写 Prometheus**，不要一上来买 APM。`/metrics` 端点已经在，接入成本极低。

## 6. 六个最常见的误区（每条都是真实会犯的）

| 误区 | 为什么错 | 正确做法 |
|---|---|---|
| 「先把代码写完再考虑部署」 | 部署会反过来改代码（配置外置、日志到 stdout、健康检查、优雅停机） | 从第一天就按「可容器化」写：配置用环境变量、日志不写本地文件、有 `/health/live` |
| 「迁完数据就切过去」 | 读路径的问题只在真实查询里暴露（`NULL` 排序、时区、`numeric` 精度） | 先影子读双跑比对，再切写（`01` §7） |
| 「压测就是刷 QPS」 | 得到的数字无法归因，也不知道该改哪里 | 分层注入 + 看 P99 斜率 + 区分 429/503 |
| 「限流是防攻击」 | 限流防的是**配额被单个用户吃光**；防攻击是 WAF/IP 层的事 | 业务配额（user/endpoint/model）+ 接入层 IP 防刷，两者分开 |
| 「有备份就安全了」 | 备份文件可能是坏的、可能没权限恢复、可能没人会恢复 | **定期真恢复演练**，记录恢复耗时（RTO）与丢数据量（RPO） |
| 「备案/等保是技术活」 | 是**行政流程**，需要主体资质，技术上无法加速 | 提前排期，别卡在上线前一晚 |

## 7. 评审怎么讲这条路线

**不要说「我做了 6 个生产化模块」。要说「我知道这 6 件事的依赖顺序，以及为什么是这个顺序」。**

三层递进：

1. **风险分层**：把生产化拆成「丢数据 / 撑不住 / 被刷穿 / 看不见 / 不合规」五类风险，
   每类对应一组措施。这样讲，听的人立刻知道你是在**管风险**，不是在**堆功能**。
2. **依赖推理**：`05` 为什么必须在 `01` 之后？因为备份策略由存储引擎决定。
   `02` 为什么必须在 `01` 之后？因为压 SQLite 得到的数字对 PG 没有参考价值。
   **能讲清「为什么不能并行」，比讲清「我做了什么」更能证明你做过。**
3. **诚实边界**：我做了脚本和设计，真机 `--apply` 没跑，Milvus 迁移只设计，恢复演练没做。
   **把「未做」说清楚，比把「设计」说成「实现」更能建立信任。**

**如果被追问「那你为什么不做完」**：因为做完需要真实硬件与备案主体，
而这套东西的价值在于**决策依据**，不在于「跑过一次」。真给我一台机器，我知道按什么顺序、验什么判据。

**基础设施自检脚本**（起完容器先跑它，比逐个 `docker ps` 快）：

```bash
python scripts/verify_infra.py \
  --pg-dsn    "postgresql://kb:kb_demo_only@127.0.0.1:55432/kb" \
  --redis-url "redis://127.0.0.1:56379/0" \
  --milvus-uri "http://127.0.0.1:19530"
# PG：表 20 张 / 无限流种子偏差 / created_at 真的是 timestamptz / documents JOIN chunks 有数据
# Redis：limit=3 时内存 2 进程 6 次 vs Redis 3 次 → 放大 2.0×
# Milvus：存活向量数 / 错 tenant 必须 0 条 / 按 doc_id 收窄后文档数必须变少
# 末尾输出 {"verdict": "INFRA_READY"}，退出码 0
```

它验的不是「容器起来了」，而是「**起来之后对业务是可用且正确的**」：
种子值跟代码是否一致、时间列有没有被搬成 text、多副本限流到底有没有共享窗口、
Milvus 的权限表达式到底有没有真的在过滤。
