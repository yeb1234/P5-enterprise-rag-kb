# 05 · 备份与灾备：从概念到演练

> 定位：**教程与方案**，不是已落地能力。本项目当前没有真实备份任务、没有异地副本、没有演练记录。
> 读者假设：没做过灾备，但需要工程精度。全文用「一句话结论 + 表格 + 类比」推进，每个类比后都回到工程定义。
> 事实源（本次实读）：`webapp/recovery.py`、`cache/recovery.py`、`webapp/db.py`。
> 三态纪律：本系列文档统一标 `已实现` / `只设计` / `未做`。本文绝大部分是 `只设计` 与 `未做`，逐节注明。

## 0. 三句话结论

1. **备份不是「复制文件」，是「能恢复出可用数据」**——没验证过恢复的副本，只是占空间的字节。
2. **高可用、备份、灾备解决三个不同的问题**，混为一谈就会出现「有备库但误删照样同步过去」的事故。
3. **RPO 决定你多久备份一次，RTO 决定你恢复方案能有多复杂**；两者都由业务定，不由技术定。

## 1. 三组最容易混的概念

### 1.1 高可用（HA）vs 备份（Backup）vs 灾备（DR）

| 概念 | 解决什么问题 | 类比 | 工程定义 | 关键指标 | 反面教材 |
|---|---|---|---|---|---|
| **高可用 HA** | 机器/进程挂了，服务还能继续 | 备用发电机：市电断了自动切换 | 冗余 + 故障转移，让**服务不中断** | 可用性 99.9% / 99.99%、故障切换时间 | 有备库但主库误删，备库同步执行，**HA 把错误也高可用地复制了** |
| **备份 Backup** | 数据丢了/坏了，还能找回到某个时间点 | 保险箱里的账本复印件 | 周期性产生**独立于生产库**的可恢复副本 | RPO、备份成功率、恢复验证通过率 | 备份和生产库在同一块盘上，盘坏两份一起丢 |
| **灾备 DR** | 整个机房/区域没了，还能恢复营业 | 厂区被淹后去备用场地复产 | 异地副本 + 切换预案 + 人员流程，让**业务能重建** | RTO、跨区复制延迟、切换演练结果 | 有备份但没异地，区域故障时备份也一起不可用 |

**一句话结论**：HA 保「不停」，备份保「找回」，DR 保「重建」。三者互补，缺一不可，但**不能互相替代**。

> 最常见的错误：以为「上了主从复制就是有备份」。主从复制是 HA，误删、逻辑错误会同步到从库；勒索软件加密主库后，从库也会被加密。**备份必须是独立、可离线、可回溯的**。

### 1.2 RPO 与 RTO

| 指标 | 含义 | 类比 | 由谁决定 | 本项目举例 |
|---|---|---|---|---|
| **RPO**（Recovery Point Objective，恢复点目标） | 最多能接受丢多少数据，即「恢复到哪个时间点」 | 你最多能接受账本丢几页 | 业务/财务/合规 | 每小时复制一次 → **RPO ≈ 1 小时**；PG + WAL 归档 → **RPO 可到秒级** |
| **RTO**（Recovery Time Objective，恢复时间目标） | 最多能接受停多久，即「多久必须恢复服务」 | 多久必须重新开门营业 | 业务连续性要求 | 从备份文件恢复到新目录并启动 → **RTO ≈ 分钟级**（小库）；大库 + 异地 + 人工核对 → 小时级 |

**一句话结论**：RPO 是「往回看多远」，RTO 是「往前赶多快」。RPO 靠备份频率与日志归档，RTO 靠恢复方案的自动化程度。

| 方案 | RPO | RTO | 代价 | 三态 |
|---|---|---|---|---|
| 不备份（本项目当前状态） | 全部丢失 | 不可恢复 | 0 | **未做** |
| 每日停服 `cp app.db` | ≤24h | 分钟级 | 需停机窗口 | 只设计 |
| 每小时复制 + 保留 N 份 | ≈1h | 分钟级 | 存储 + 一致性处理 | 只设计 |
| `sqlite3 .backup` 每小时（在线一致） | ≈1h，且副本一致 | 分钟级 | 需脚本与校验 | 只设计 |
| PG `pg_dump` 每日 + WAL 归档 | 秒级（取决于归档频率） | 分钟~小时 | 需 WAL 归档链路 | 只设计 |
| PG 流复制 + 备库 | 秒级甚至更低 | 秒~分钟 | 高可用，**不是备份** | 只设计 |

### 1.3 备份 vs 归档

| 维度 | 备份 Backup | 归档 Archive |
|---|---|---|
| 目的 | **恢复**到某个时间点 | **留存**以备查证/合规 |
| 保留期 | 短（天~月），滚动覆盖 | 长（年~十年） |
| 访问频率 | 恢复时才用，平时不读 | 极少读，但要能检索 |
| 失败后果 | 数据丢了找不回 | 合规审计不通过 |
| 一句话 | 备份是为了「回去」 | 归档是为了「留着」 |

> 混用的典型后果：把归档当备份（保留十年但不能快速恢复），或把备份当归档（七天就滚动覆盖，出事时已经没历史）。

## 2. 备份类型与 3-2-1 原则

### 2.1 全量 / 增量 / 差异

| 类型 | 定义 | 恢复路径 | 存储代价 | 恢复速度 | 风险 |
|---|---|---|---|---|---|
| **全量 Full** | 每次完整复制全部数据 | 直接恢复一份 | 大 | 快 | 无链式依赖 |
| **增量 Incremental** | 只备份「自上次任意备份以来」的变化 | 全量 + 逐条增量按序重放 | 小 | 慢（链越长越慢） | **链断则后续全废** |
| **差异 Differential** | 只备份「自上次全量以来」的变化 | 全量 + 最后一次差异 | 中 | 中 | 只依赖一份全量 |
| **日志归档 WAL / binlog** | 连续记录事务日志 | 基础备份 + 重放日志到目标时间 | 随写入增长 | 慢但可精确到秒 | 依赖日志连续性 |

**一句话结论**：周全量 + 日差异 + 连续日志归档，是兼顾存储、恢复速度与 RPO 的常见组合。

### 2.2 3-2-1 原则

| 数字 | 含义 | 防的是什么 |
|---|---|---|
| **3** 份副本 | 生产 1 份 + 备份 2 份 | 单份意外删除/损坏 |
| **2** 种介质 | 如本地磁盘 + 对象存储 | 同一类介质/同一套系统的批量故障 |
| **1** 份异地 | 至少一份在另一个物理位置/区域/账号 | 机房、区域、账号级故障 |

> 进阶版常写作 **3-2-1-1-0**：额外 **1 份离线或不可变**、**0 错误**（每次备份都校验）。对勒索场景，第 4 个「1」比前三个更关键。

### 2.3 不可变备份（防勒索）

**定义**：备份写入后，在保留期内**任何凭证都无法修改或删除**（对象存储的 WORM / Object Lock / 保留策略 / 合规模式）。

| 项 | 说明 |
|---|---|
| 为什么需要 | 勒索软件拿到管理员凭证后，第一件事就是删除或加密备份。可变备份等于没有 |
| 实现方式 | 对象存储「一次写入多次读取」+ 保留期（如 30 天）；或物理离线介质（磁带/离线盘） |
| 代价 | 保留期内无法删除误备份，存储成本刚性；需要规划保留期 |
| 配套 | 备份账号与生产账号分离，备份凭证不给生产系统 |

## 3. 一致性：为什么不能直接 `cp`

### 3.1 热备的问题

**一句话结论**：数据库文件不是「一整块不变的字节」，写入过程中不同页可能处于不同时间点，直接复制可能拿到**互相矛盾的半成品**。

| 场景 | 直接 `cp` 的风险 |
|---|---|
| 复制时有写事务在跑 | 副本内部页版本不一致，打开时报 `database disk image is malformed` 或静默读出错误数据 |
| SQLite 有回滚日志 `-journal` | 只复制 `app.db` 漏掉日志，副本可能处于「热日志」状态，恢复行为不可预期 |
| SQLite 开了 WAL | 数据可能还在 `app.db-wal` 里未合并，只复制主文件会**丢掉最近的事务** |
| PG 数据目录 | 数据文件 + WAL 必须同一时间点，必须用 `pg_basebackup` 或文件系统快照 |

### 3.2 SQLite 的正确做法（含本项目实查）

**实查结论**：`webapp/db.py` 只有 `PRAGMA foreign_keys = ON`（第 279 行），**没有任何 `journal_mode` 设置**，`grep -c journal_mode webapp/db.py` 返回 0。因此本项目 SQLite 使用**默认回滚日志模式（DELETE）**，事务期间存在 `app.db-journal`，**不是 WAL**。

| 做法 | 命令 | 是否需要停机 | 一致性 | 适用 |
|---|---|---|---|---|
| **在线备份 API（推荐）** | `sqlite3 app.db ".backup '/backup/out.db'"` | 否 | 由 SQLite 保证 | 本项目首选 |
| 停服后复制 | 停进程 → `cp app.db /backup/` | 是 | 天然一致 | 最简单，演示够用 |
| checkpoint 后复制（仅 WAL 模式） | `sqlite3 app.db "PRAGMA wal_checkpoint(TRUNCATE);"` 再复制三件套 | 否（但会阻塞写入） | 一致 | 未来若开 WAL |
| 文件系统快照 | LVM / ZFS / btrfs 原子快照 | 否 | 一致 | 有快照能力时 |

> **WAL 三件套**：一旦启用 WAL，备份必须同时处理 `app.db`、`app.db-wal`、`app.db-shm`，或先做 checkpoint 把 WAL 合并回主文件。**只复制 `app.db` 会丢最近事务**。本项目当前不涉及，但换库/调优时要注意这个坑。

### 3.3 PG 的基础备份

| 方式 | 命令 | 特点 |
|---|---|---|
| 逻辑备份 | `pg_dump -Fc appdb > /backup/appdb.dump` | 单库、跨版本可恢复、可选择性恢复表；大库慢 |
| 物理备份 | `pg_basebackup -D /backup/base -Ft -z -P` | 整个实例、快、PITR 的基础 |
| 文件系统快照 | 停库或用 `pg_start_backup`/`pg_stop_backup` 包裹 | 需要存储支持 |

## 4. PostgreSQL 的时间点恢复（PITR）

### 4.1 三个要素

| 要素 | 作用 | 关键配置/命令 |
|---|---|---|
| **基础备份** | 恢复的起点 | `pg_basebackup` 产出的数据目录 |
| **WAL 归档** | 从起点重放到目标时刻 | `wal_level = replica`、`archive_mode = on`、`archive_command` |
| **恢复目标** | 停在哪个时刻 | `recovery_target_time` / `recovery_target_lsn` / `recovery_target_xid` |

### 4.2 配置与恢复命令（示意，需按 PG 版本核对）

```conf
# postgresql.conf —— 开启 WAL 归档（示意）
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'
archive_timeout = 60          # 最多 60 秒强制切换一个 WAL 段，限制 RPO 上限
```

```conf
# 恢复：在空数据目录解压基础备份后，追加以下配置并创建 recovery.signal（PG 12+）
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2026-11-15 10:29:59+08'
recovery_target_action = 'promote'
```

```bash
# 恢复流程（示意）
tar -xzf /backup/base/base.tar.gz -C /var/lib/pg/restore
touch /var/lib/pg/restore/recovery.signal
pg_ctl -D /var/lib/pg/restore start
# 观察到 "recovery stopping before ..." 与 "database system is ready to accept connections" 即完成
```

> PG 11 及更早用 `recovery.conf`，PG 12+ 用 `recovery.signal` + `postgresql.conf` 里的参数。**版本差异必须核对官方文档**，本文不作为可直接照抄的脚本。

### 4.3 能恢复到「误删表之前那一秒」

**一句话结论**：能，但有三个前提——① WAL 已连续归档到那一刻；② 你能说清误操作的准确时间或 LSN；③ 你接受「该时刻之后的所有数据一并丢失」。

| 要点 | 说明 |
|---|---|
| 恢复粒度 | 取决于 `archive_timeout` 与 WAL 切换频率；归档越频繁，可恢复点越密 |
| 常见做法 | **恢复到新实例**（不同端口/目录），人工核对后再决定是否回切生产，避免二次事故 |
| 不可逆 | PITR 是「回到过去」，不是「挑出坏数据」；误删之后写入的**正常数据也会消失** |
| 前置条件 | 基础备份必须比目标时刻更早；WAL 链不能断 |

## 5. 故障场景矩阵

| 场景 | 靠什么恢复 | RPO | RTO | 演练方式 |
|---|---|---|---|---|
| **误删数据**（`DELETE` 漏 `WHERE`） | PITR 到误操作前；无 WAL 时退化为「最近备份 + 人工补录」 | 取决于备份频率 / WAL 归档间隔 | 分钟~小时 | 季度演练：在隔离库故意误删，验证能恢复到误删前一刻 |
| **磁盘损坏** | 从备份恢复到新盘；RAID 只防单盘故障，不防误删与勒索 | 最近一次备份 | 小时级 | 模拟只读/摘盘，验证从备份盘拉起 |
| **机房断电** | 重启后由 journal / WAL 自动恢复未提交事务 | 0（已提交事务不丢，取决于 `synchronous` 设置） | 分钟级 | 低峰期断电演练（谨慎，需评估风险） |
| **勒索加密** | **不可变备份 / 离线副本**；被加密的在线备份不可用 | 最近一份不可变副本 | 小时~天 | 桌面演练：模拟凭证泄露，验证保留策略与隔离账号是否生效 |
| **逻辑错误**（代码 bug 写坏数据） | PITR 到发版前；或备份 + 代码回滚 | 取决于发现时间（**最难的一种**） | 小时级 | 灰度发布 + 数据校验；演练：用备份恢复到 bug 引入前 |
| **区域性故障**（机房/云区域不可用） | 异地副本 + DNS/流量切换 | 取决于跨区复制方式 | 小时~天 | 年度演练：在另一区域完整恢复一次并计时 |

> **逻辑错误最难**：它写入的是「合法事务」，HA 会同步到备库，备份如果产生在 bug 之后也是坏的。唯一出路是**保留足够久的历史备份 + 能 PITR**，以及发布前的数据校验。

## 6. 演练：没演练过的备份等于没有备份

### 6.1 季度演练清单

|---|---|---|

### 6.2 SQLite 最小演练脚本（示意，不落地）

```bash
#!/usr/bin/env bash
# scripts/dr_drill.sh —— 仅示意，本项目未落地此脚本
set -euo pipefail
SRC="${1:-.data/webapp/app.db}"
DST="/tmp/dr_drill_$(date +%s).db"

# 1) 在线一致备份（不锁库、不裸 cp）
sqlite3 "$SRC" ".backup '$DST'"

# 2) 完整性校验
sqlite3 "$DST" "PRAGMA integrity_check;" | grep -qx ok && echo "integrity: ok"

# 3) 关键表行数对比
for t in documents chunks users usage_events; do
  a=$(sqlite3 "$SRC" "SELECT COUNT(*) FROM $t;")
  b=$(sqlite3 "$DST" "SELECT COUNT(*) FROM $t;")
  printf "%-16s src=%-8s dst=%-8s\n" "$t" "$a" "$b"
done

echo "restored_to=$DST  # 记得记录耗时并销毁"
```

> 这个脚本同时演示了两件事：**用 `.backup` 而不是 `cp`** 保证一致性；**恢复后必须校验**，否则你只是复制了一个可能损坏的文件。

## 7. 与本项目的关系：重启恢复 ≠ 灾备

### 7.1 `recovery.py` 解决什么、不解决什么

**实查**：`webapp/recovery.py` 的 `startup()` 调用 `cache/recovery.py::run_startup_checks()`，产出 7 项检查：

| # | check id | 分类 | 解决什么 | **不解决什么** |
|---|---|---|---|---|
| 1 | `schema_ready` | must_persist | `cache_entries` / `runtime_state` 表是否齐备 | 表齐备不等于数据完整；**文件损坏时这一项直接失败** |
| 2 | `volatile_state_discarded` | discardable | 声明限流窗口/轨迹 deque/SSE 连接重启即丢，属可安全丢弃 | 不涉及持久数据 |
| 3 | `orphan_tasks_recovered` | rebuildable | 扫 `documents.status IN ('queued','analyzing')` 重新入队（幂等） | 只能重建「未完成态」，**已丢失的文档内容无法重建** |
| 4 | `ghost_vectors_reconciled` | must_persist | 清理 `chunk_embeddings` 里 chunk_id 不在 `chunks` 的幽灵向量 | 不恢复被删的正确向量 |
| 5 | `data_version_consistent` | must_persist | 文档集合指纹变化 → 递增 `data_version`，让旧缓存 key 失效 | 只保证缓存一致性，不保证数据正确性 |
| 6 | `policies_persisted` | must_persist | 从 `runtime_state` 恢复策略与版本号（`grant_version` / `policy_version`） | 不涉及业务数据 |
| 7 | `expired_cache_purged` | must_persist | 清理过期缓存 + 容量淘汰 | 不涉及业务数据 |

**一句话结论**：这 7 项全部在**同一个 SQLite 文件内**做「重启后状态是否自洽」的检查。如果 `app.db` 本身被误删、损坏、加密，第 1 项就失败，后面 6 项无从谈起——**它不解决数据丢失**。

| 容易误解的点 | 事实 |
|---|---|
| `simulate_restart()` 是灾备演练 | 不是。它只清 L1 内存缓存 + 重跑检查，**不碰数据文件**，用于演示「重启后缓存仍可命中」 |
| `last_shutdown_at` 能判断是否崩溃 | 只能判断「上次关闭时是否写过时间戳」（`was_graceful()` 用 `state_get(LAST_SHUTDOWN_KEY, "")` 非空判定），**无法区分优雅关闭与崩溃前恰好写过一次**，是已知弱信号 |
| 有 `runtime_state` 就等于有备份 | 不是。它在同一个 SQLite 文件里，文件丢了它一起丢 |

|---|---|---|
| 备份方式 | `sqlite3 .backup`（在线一致），**禁止裸 `cp`** | 只设计 |
| 频率 | 每小时 + 每日快照 | 只设计 |
| 保留 | 小时级 24 份 + 每日 7 份 | 只设计 |
| 异地 | 每日快照同步到对象存储（另一个账号/区域） | 只设计 |
| 加密 | 对象存储服务端加密；密钥单独管理 | 只设计 |
| 校验 | 每次备份后 `PRAGMA integrity_check` + 行数比对 | 只设计 |
| WAL 处理 | 当前**未开 WAL**，无需三件套；未来若开，必须 checkpoint 或同时备份 `-wal`/`-shm` | 已实现（未开 WAL，实查确认） |

### 7.3 上 PG 后换成什么

| 层 | 做法 | RPO | 备注 |
|---|---|---|---|
| 每日全量 | `pg_dump -Fc` 或 `pg_basebackup` | 24h | 基础备份 |
| 连续归档 | `archive_mode=on` + `archive_command` 上传对象存储 | 秒~分钟（受 `archive_timeout` 限制） | PITR 的前提 |
| 周度基线 | 每周一份完整 `pg_basebackup` 长期保留 | — | 缩短恢复链 |
| 异地 | WAL 与全量跨区域复制 | 取决于复制 | 防区域性故障 |
| 演练 | 季度恢复到隔离实例并计时 | — | 验证 RTO |

## 8. 成本与取舍

| 维度 | 选项 | 代价 | 取舍建议 |
|---|---|---|---|
| **保留多久** | 7 天 / 30 天 / 1 年 / 10 年 | 存储线性增长 | 演示项目 7–30 天足够；生产按行业合规（财务类常要求多年） |
| **存哪** | 本地盘 / 对象存储 / 异地 | 本地快但同故障域；对象存储便宜耐用；异地防区域故障 | 至少「对象存储 + 异地一份」 |
| **加密** | 服务端加密 / 客户端加密 | 客户端加密更安全但运维复杂 | 静态加密必做，**密钥不能和备份放一起** |
| **人力** | 备份自动化 / 演练人工 | 演练是主要成本（每次数小时） | 备份自动化，演练排进季度计划 |
| **恢复速度** | 全量直恢复 / 增量链重放 | 链越长越慢 | 控制链长（周全量） |

### 小团队最低可行灾备（3 条）

1. **每日自动备份到对象存储**（SQLite 用 `.backup`，PG 用 `pg_dump`），保留 ≥7 天，每次校验与行数比对。
2. **每周把一份备份复制到另一个区域/另一个账号**，并开启对象锁保留期（不可变）。
3. **每季度真恢复一次**到隔离环境，记录实际 RTO 与发现的问题，更新本文档的 RPO/RTO 声明。

## 9. 三态与边界

| 项 | 状态 | 说明 |
|---|---|---|
| `recovery.py` 启动自检 7 项 | **已实现** | 解决「重启后状态自洽」，不解决数据丢失 |
| `simulate_restart()` 重启演练 | **已实现** | 只清 L1 内存缓存，非灾备演练 |
| `webapp/db.py` 的 `DB_PATH` 与连接参数 | **已实现** | `WEBAPP_DB_PATH` 可注入；仅 `PRAGMA foreign_keys = ON`，未开 WAL |
| 真实备份任务 / 定时任务 | **未做** | 无 cron、无备份脚本、无对象存储上传 |
| 异地副本 / 不可变备份 | **未做** | 无跨区、无对象锁 |
| 加密与密钥管理 | **未做** | 无 KMS、无密钥轮换 |
| 演练记录 | **未做** | 无任何 drill 记录 |
| PITR 链路（PG + WAL 归档） | **只设计** | 本文第 4 节为示意，未在本项目落地 |
| 本文档 | **已实现（文档）** | 是方案与教程，**不是已落地能力** |

> 讲解口径：被问到「你们有灾备吗」时，正确回答是「演示切片有**重启一致性自检**（7 项），**没有**备份任务、异地副本与演练记录；生产化需要补每日备份 + 异地 + 季度演练」。把 `recovery.py` 说成灾备，会在追问「误删数据怎么恢复」时立刻暴露。
