**物料编号**：`DEMO-KBQA-EVAL-001` ｜ 与 [演示文档](01-demo-guide.md)、[配套工具](03-demo-tools.md) 共用同一份 `demo/scenario.json`

## 3. 正常场景测试话术

### 3.1 主用例 `C-001`（六链路钻取）

> 「先看一条最普通的：问题是『DPI 切换按键在哪里？』。这不是真实产品资料，是我们造的合成说明书
> `FIX-MANUAL-A`。六链路从 `chunk` 一路走到 `score`，每步都有 `object_refs` 说明它消费了哪些版本化对象。
> 注意 `recall_at_k=1.0` 这里**只能读成『金标证据被这条链路找到了』**，不能读成『检索效果很好』——
> 因为 embedding 是占位实现，`comparable=false`。」

**观众可能问**：「`recall_at_k=1.0` 是不是说明效果不错？」
**标准回答**：「不是。占位向量不具备语义能力，这个 1.0 只证明金标映射与召回链路是通的，
质量结论要等接真实 API、冻结基线之后才有。现在结论是 `NOT_COMPARABLE`。」
**兜底**：若该步显示不一致，念：「这一步的【实际】和【预期】有差异，台本已经把预期值和实际值并排列出来了，
我们先按这一条排查，不把它包装成通过。」

### 3.2 全量批次 S5

> 「26 条用例一次跑完，状态是 OK 23、降级 2、未完成 1。这里**降级和未完成不是失败**，
> 它们是我们故意注入的边界场景，而且都被完整记录下来了。真正要盯的是 `determinism_pass=true`
> 和 `stage_1_pass=true`：同一个种子跑两次，去掉耗时后的结果哈希一致；链路健康 7 项阈值全过。」

**观众可能问**：「为什么有 2 个 degraded、1 个 incomplete 还能 `OFFLINE_READY`？」
**标准回答**：「`OFFLINE_READY` 判的是链路健康，不是质量。这两类状态是预期收敛结果，
台本 S7 会逐条展示证据；如果异常被静默吞掉，闸门反而会 BLOCK。」

### 3.3 对比实验 S8

> 「把 `top_k` 从 8 改成 3 再跑一次，工具按 `case_id` 把 26 条逐条配对。
> 但输出里明确写着 `comparable=false`——**这一步演示的是比对工具能用，不是哪个参数更好**。」

## 4. 边界情况测试话术（逐条可念）

| 用例 | 话术（逐字） | 指给观众看 | 观众可能问 / 标准回答 | 兜底 |
|---|---|---|---|---|
| `C-013` 空文档 | 「把文档换成空的，链路不报错、也不编造，`chunk_count=0`，回答走拒答短语。」 | S7 实际里 `C-013: ok / chunk_count=0` | 「会不会直接崩？」→「不会，六步记录照样齐全，只是召回为空。」 | 「如果这里出现非空回答，说明拒答规则被改过，按变更记录查对象版本。」 |
| `C-015` 检索为空 | 「这里我们**主动强制空召回**，模拟检索没结果；系统选择拒答而不是拼一个答案。」 | `forced_empty=true` | 「线上检索为空怎么办？」→「同一条策略：拒答 + 记录 `empty_retrieval`，不编造。」 | 「若没看到 `forced_empty=true`，先确认跑的是默认档位 `offline_placeholder`。」 |
| `C-016` 提示词溢出 | 「长行文档会把提示词顶爆，我们只做一件事：留痕。`prompt_overflow=true` 且带 warning，原始提示词不进日志，只记 `prompt_hash`。」 | `prompt_overflow=true` | 「为什么不直接截断不说话？」→「静默截断会让结果无法解释，可排查性优先。」 | 「若 warning 缺失，检查 `OBJ-PROMPT-RAG-ANSWER` 是否被改过版本。」 |
| `C-018` 超时 | 「注入一个超时，最终状态是 `degraded`，错误码 `E_PLACEHOLDER_TIMEOUT` 留在记录里，用例**没有丢**、**没被当成通过**。」 | `errors: ["E_PLACEHOLDER_TIMEOUT"]` | 「这是不是真实错误码？」→「不是。这是评测框架内部占位分类，真实错误码映射仍是 `__TBC__`。」 | 「若显示 `ok`，说明故障注入没生效，重跑 `python eval/run_eval.py`。」 |
| `C-020` 评分不可用 | 「最容易被糊弄的一条：评分器不可用时，状态是 `incomplete`、`composite_score=null`，**绝不静默记 0 分**。」 | `scoring_status=unavailable` / `composite_score=null` | 「记 0 分有什么问题？」→「会把『没测』伪装成『测得很差』，污染基线和阈值。」 | 「若 `composite_score` 是 0，按自测报告第 12 项判定为不对齐并停止演示。」 |
| 注入 / 敏感对照 | 「另有 `C-022` 提示词注入和 `C-023` 敏感信息负向对照：后者故意让占位生成器回显问题，用来验证规则 `R5` 真的能检出泄漏，不代表真实系统行为。」 | 自测报告中的负向对照检查 | 「这是缺陷吗？」→「是负向对照用例，目的是证明评分规则有效。」 | 「不要把它讲成系统泄漏，它是设计好的检测试剂。」 |

**边界段落收尾（逐字）**：
> 「五条边界都想说明同一件事：**不静默**。异常、空输入、溢出、评分缺失，全部留状态、留原因、留记录。
> 演示里最怕的不是出错，是错了以后页面上什么都没留下。」

## 5. 观众常见提问 Q&A

| 提问 | 标准回答 |
|---|---|
| 「接了真实 API 会怎样？」 | 需要先消解 26 项 blocking 的 `__TBC__` 契约字段、确认权限与配额、跑首轮基线、评审冻结阈值；门槛和步骤在 `docs/evaluation-plan.md`。当前 `real_api` 档位被明确阻断。 |
| 「14 个对象改一个会怎样？」 | 必须新建版本并写 8 项变更记录；`config_snapshot_hash` 和 `code_hash` 会变，`run_id` 也随之变化，不会覆盖历史结果。 |
| 「为什么 `NOT_COMPARABLE`？」 | 占位 embedding 无语义能力、质量阈值全为 `null`、基线未建立；冻结前一律不判 PASS。 |
| 「两端对齐指什么？」 | 演示侧 `demo/out/demo_run_result.json` 与验证侧 `eval/results/` 的 manifest / summary / records 逐字段一致，明细在[第四部分](04-selftest-and-alignment.md)。 |
| 「多久能接真实 API？」 | 不预设时间；取决于开通与契约确认，方案里列了必需项与可选项清单。 |

## 6. 应急话术（实际输出与预期不符时）

> 「这一项【实际】和【预期】不一致，台本已经把两个值并排列出来了。我们不跳过它：
> 先按【操作】里的命令单独复现，再对照自测报告里对应的检查项。演示的价值恰恰是这些值能被逐项核对。」

- 不要说「大概是缓存」「可能是网络」——本档位零网络。
- 不要临时改文档里的预期值来迁就输出。
- 时间不够就念第 8 节收尾话术，把 S4 / S8 用一句话带过。

## 7. 严禁说的话

- 严禁说「准确率已达 X%」「生产可用」「已上线」「真实模型实测」「召回率提升百分之 X」。
- 严禁把 `__TBC__` 读成某个具体服务名或模型名。
- 严禁把 `degraded` / `incomplete` 说成「测试失败」，也严禁说成「全部通过」。

## 8. 收尾话术（逐字）

> 「这一轮从场景卡走到结果确认，证明了三件事：六链路跑得通、异常不静默、
> 结果能用 `config_snapshot_hash`、`code_hash`、`dataset_hash` 和 `run_id` 四把钥匙复现。
> 它没有证明质量——那是接真实 API、冻结基线之后的下一轮工作。结论就写在最后一行：`NOT_COMPARABLE`。」
