一、结论先行

在测试集（未参与调参的 1570 条 query）上，最佳一阶段配置是 向量 bge-m3，nDCG@10 = 33.93%， 比词法基线（BM25 16.29%）高 +17.63 个百分点。

三个参数各自的收敛结论： 查询前缀 无收益，不采用 （31.05% vs 纯向量 33.93%）； BM25 与向量的融合 无收益，不采用 （加权 w=0.85 时 31.98%）； 重排深度取 top20（两档只差 0.06 个点，按成本取浅的）：在同一批 400 条 query 上， 重排把 nDCG@10 从 32.79% 提到 36.09%（+3.30 个百分点）。

注意：重排那一行是子集数字（400 条），只能和它的同子集基线比， 不能和右边全量测试集的数字横向比。

重排是唯一一个在数量级上明显的成本项，换来的是 +3.30 个点。它用的是现场真调 API 的计时（20 次），不是缓存跑的 0.0s——缓存命中记成 0 会让报告看起来像「重排免费」。本机单线程，不含服务端排队；换机器绝对值会变，相对量级不会。

顺带一个反直觉的结果：词法基线比向量检索慢 40 倍（79.57 ms vs 2.03 ms）。原因是 BM25 要在 Python 里扫倒排项、逐个累加分数，而向量检索是一次 BLAS 矩阵乘。所以「用词法兜底更省资源」这句话在 10 万文档规模上不成立——它既更不准，又更慢。这与第四节扫描表里的总耗时（27.7s / 400 条 ≈ 69ms/条）互相印证，差异来自缓存预热与系统负载。

RRF 只用名次不用分数，避免两路分数量纲不同。但等权融合是个陷阱： BM25 在这套数据上弱得多，等权等于把噪声按 50% 掺进来。扫描结果单调上升（24.73% → 28.28% → 30.46%），而再往上就是纯向量本身（33.93%）：权重越大越接近纯向量、指标越好，说明 BM25 在这套数据上只贡献噪声，正确做法是不融合，而不是把权重调小一点意思一下。

重排接在一阶段最优配置「向量 bge-m3」的候选上， 不是接在 RRF 上——如果一阶段就该用纯向量，从更差的候选集里重排毫无意义。 对照行「不重排」用的是同一批 400 条 query，所以增益是干净的。 深度是成本项：每次要把 top-N 条候选原文发给 cross-encoder。 「本次耗时 0.0s」表示分数全部命中磁盘缓存；冷跑实测 top20 约 150s、top50 约 280s （400 条 query、单条约 0.38s）。 top20 与另一档只差 0.06 个百分点，这在 400 条 query 上属于噪声，不该说成「调出了最优深度」；按成本取更浅的那档。

八、口径与局限（如实说明）

  • 不与 C-MTEB 榜首直接可比：数据与 qrels 来自公开数据集，但嵌入走硅基流动 API （BAAI/bge-m3）、重排只对候选 top-k 做、没有官方 corpus 清洗流程。 能说的是「同一套数据、同一套指标下的相对差异」，不是「我们打平了 SOTA」。
  • 重排只在子集上测：400 条 query，因为每次要发 top-20 条候选给 cross-encoder。子集数字会略高于全量，方向可信、绝对值偏高。
  • 相关性是二值的：qrels 只有 score=1，nDCG 用二值增益算；原数据没有分级相关性。
  • BM25 是自己实现的（字符单字+二元组、k1=1.2 / b=0.75、词项预算是上面调出来的）， 不是 Lucene。它的作用是提供同数据上的参照，不代表工业级 BM25 的上限。
  • 调参集/测试集按 query-id 哈希切分，不是随机种子——换机器、换 Python 版本切分都一样。
  • 绝对分数偏低是数据特性：CmedqaRetrieval 平均每条 query 只有 1.86 条 gold， 且 passage 是长回答、query 是长问题描述，中文语义匹配本身就吃力。 所以看的是配置之间的相对差，不是「0.4 算不算及格」。

一句话总结：这套评测能回答「向量比词法强多少、前缀有没有用、融合与重排值不值」， 不能回答「我们的系统在中文检索里排第几」。

九、两张成绩单不能互相替代

本项目有两套评估，对外说明时不要混着说：

  • 本页（公开集 10 万篇）回答「检索算法选得对不对」—— 有官方 qrels、有 BM25 同数据基线、有调参/测试切分，所以数字可对外比。
  • evalfmt.run_eval（自建 10 份多格式语料 / 9 道正例题）回答「整条链路通不通」—— 上传→解析（含 PDF、表格、无字图片）→分块→检索→生成→脱敏，能抓出「PDF 解析失败」 「内网 IP 被误判成隐私」这类工程缺陷，但样本只有 9 题，它的 100% 不证明系统强。

一句话：公开集证明「检索能打」，自建集证明「管道没漏」。前者怕样本作弊，后者怕样本太少。

十、复现

python -m evalfmt.publicbench download → 从 hf-mirror 拉 3 个 parquet

python -m evalfmt.publicbench embed → 全量向量化并缓存到磁盘（断点续跑）

python -m evalfmt.publicbench run → 扫参 + 五组配置 + 生成本页

耗时说明：10 万条向量化约 60 分钟（一次性，之后走缓存）； 重排冷跑约 8 分钟（800 次 cross-encoder 调用），之后走缓存； 扫参与评估本身约 1.5 分钟。本轮脚本耗时 80.8s——这个数字小是因为 向量与重排都命中了缓存，不代表冷跑成本。

原始数字：evalfmt/out/publicbench.json · 重排分数缓存：evalfmt/.cache/rerank_scores.json（重跑不重复调 API）· 只改排版重出本页：python -m evalfmt.publicbench_run --from-json evalfmt/out/publicbench.json
